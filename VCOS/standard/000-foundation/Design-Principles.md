# Design Principles

**Document ID:** DESIGN-PR-001  
**Version:** 1.0.0-draft  
**Status:** Draft  
**Parent:** Architecture-Invariants.md  
**Next:** Computational-Theory.md  

---

Principles — это руководящие указания для принятия проектных решений.  
В отличие от инвариантов (которые **нельзя** нарушать), принципы описывают предпочтительный подход.

---

## Principle P-001: Composition Over Inheritance

Предпочитайте композицию сущностей наследованию.

*Пример:* вместо того чтобы делать `Scene extends VisualProject`, сделайте `Scene` как агрегат из `Environment + Characters + Camera + Lighting`.

## Principle P-002: Clarity Over Brevity

Имена сущностей, полей и связей должны быть понятны без комментариев.

*Пример:* `DesiredImpact` лучше, чем `Impact`, потому что сразу ясно, что это желаемый, а не фактический эффект.

## Principle P-003: Explicit Over Implicit

Связи между сущностями должны быть явными.

*Пример:* вместо неявного соглашения "эмоция влияет на цвет" создайте явное ребро `Emotion — affects — ColorPalette`.

## Principle P-004: One Source of Truth

Каждая информация существует ровно в одном месте. Дублирование запрещено.

*Пример:* если Composition зависит от Camera, не храните фокусное расстояние в обоих объектах. Храните в Camera, ссылайтесь из Composition.

## Principle P-005: Minimal Surface Area

Каждый модуль должен иметь минимальное количество публичных контрактов.

*Пример:* Renderer принимает Graph → возвращает Artifact. Он не спрашивает пользователя, не читает Intent, не изменяет Decision.

## Principle P-006: Fail With Context

Любая ошибка должна содержать достаточно информации для диагностики без обращения к исходному коду.

*Пример:* `Decision X ссылается на несуществующий Goal Y (id: abc-123). Возможные причины: Goal был удалён, ID указан неверно, граф повреждён.`

## Principle P-007: Defend Against LLM Instability

LLM могут галлюцинировать, противоречить себе и забывать контекст. Архитектура должна быть устойчива к этому.

*Пример:* каждое предложение LLM (новый Node или Edge) проходит валидацию на соответствие Core Ontology перед добавлением в граф.

## Principle P-008: Prefer Graph Traversal Over Event Handling

Логика системы должна строиться на обходе графа, а не на обработке событий.

*Пример:* когда изменяется Lighting, не отправляйте событие `LightingChanged`. Пусть Composition, Color и Camera читают актуальное состояние Lighting из графа.

## Principle P-009: Design For Extensibility

Каждый компонент должен быть спроектирован так, чтобы его можно было расширить без изменения ядра.

*Пример:* новый тип рендерера добавляется как отдельный модуль, implements `RendererInterface`. Ядро не меняется.

## Principle P-010: Version Everything

Каждый артефакт — документ, схему, граф, конфигурацию — должен иметь версию.

*Пример:* `CO-001 v1.0.0-draft`, `ADR-0001 v2`, `Scene Graph v3`.

## Principle P-011: Test At Boundaries

Тестируйте контракты между модулями, а не внутреннюю реализацию.

*Пример:* тест "Renderer получает Graph → возвращает Artifact" важнее теста "Renderer правильно форматирует строку промпта".

## Principle P-012: Prefer Async Reasoning

Агенты не должны блокировать друг друга. Если Visual Reasoner работает над сложной задачей, Orchestrator не ждёт — он планирует следующий шаг.

*Пример:* Visual Reasoner получил задачу — он уходит в фоновое рассуждение. Orchestrator тем временем проверяет ограничения и готовит следующие вопросы.

## Иерархия архитектурных правил

```
Инварианты (I-001–I-010)
    │
    ├── нельзя нарушать никогда
    ├── описаны в Architecture-Invariants.md
    └── нарушение = несовместимость
            │
            ▼
Принципы (P-001–P-012)
    │
    ├── желательно соблюдать
    ├── описаны в Design-Principles.md
    └── нарушение = технический долг
            │
            ▼
Рекомендации
    │
    ├── полезно знать
    ├── описаны в документации модулей
    └── нарушение = неоптимальность
```

**Version:** 2.0

**Authors:** Chief Architect, Product Owner

## Context

При проектировании VCOS мы столкнулись с фундаментальным вопросом:  
**как представить проект визуального контента, чтобы он был:**
- независим от генеративной модели
- расширяем для новых доменов
- понятен и LLM, и человеку
- пригоден для автоматического анализа и компиляции

### Рассмотренные альтернативы

1. **JSON Schema** — плоская структура полей
2. **Scene Graph** — иерархическое дерево объектов (как в игровых движках)
3. **Relational Model** — таблицы со связями
4. **Semantic Graph** — направленный мультиграф с типизированными узлами и связями

## Decision

**Выбран Semantic Graph как Canonical Model VCOS.**

### Формальное определение

Canonical Model VCOS определяется как:

> Именованный семантический граф, состоящий из типизированных узлов и типизированных связей, описывающий состояние процесса когнитивного проектирования независимо от реализации, способа хранения и вычислительной модели.

### Фундаментальные объекты

Есть только три фундаментальных объекта:

```
Node      — типизированный узел (Intent, Goal, Decision, Fact, etc.)
Edge      — типизированная связь (depends_on, supports, produces, etc.)
Graph     — контейнер узлов и связей с идентификатором и метаданными
```

### Принципы

1. **Узлы НЕ знают друг о друге.**  
   Узел содержит только свои свойства. Все связи живут отдельно как Edge.

2. **Связи типизированы.**  
   Каждое ребро имеет тип (depends_on, supports, contradicts, produces, references, contains).

3. **Каждый узел имеет confidence.**  
   Число от 0.0 до 1.0, отражающее уверенность системы в значении узла.

4. **LLM — лишь один из механизмов, предлагающих изменения графа.**  
   API, пользователь, другой агент — тоже могут предлагать изменения.  
   Hermes решает, принимать или отклонять предложения.

## Consequences

### Положительные

- **Расширяемость:** новый тип узла (Persona, Audience, Music) добавляется без изменения ядра
- **Модульность:** каждый агент работает со своей частью графа
- **Параллелизм:** несколько агентов могут одновременно читать граф
- **История:** каждое изменение графа фиксируется как последовательность Decision
- **Экспорт:** граф можно сериализовать в JSON, YAML, Markdown, Proto
- **Независимость:** никакой зависимости от конкретной LLM или генератора

### Отрицательные

- **Сложность** — граф сложнее для понимания, чем плоский JSON
- **Overhead** — создание Edge для каждой связи требует больше операций
- **Валидация** — требуется проверка графа на соответствие CO при каждом изменении
- **Инструментарий** — нужны инструменты для визуализации и отладки графа

### Митигации

- **Сложность:** View Model (Project View) предоставляет пользовательское представление
- **Overhead:** компенсируется гибкостью и расширяемостью
- **Валидация:** автоматическая проверка инвариантов при каждом Apply
- **Инструментарий:** Hermes CLI с командой `graph inspect`

## Рассмотренные альтернативы

### Альтернатива 1: JSON Schema

```
{
  "scene": {
    "camera": { "shot": "medium", "lens": 50 },
    "lighting": { "key": "soft", "temperature": 5600 }
  }
}
```

**Проблемы:**
- Плоская структура не отражает связи между сущностями
- Изменение одной сущности требует понимания всей структуры
- Новый домен требует новой схемы

### Альтернатива 2: Scene Graph (иерархическое дерево)

```
Scene
├── Camera
├── Lighting
├── Characters
│   ├── Character A
│   └── Character B
└── Environment
```

**Проблемы:**
- Дерево не может выразить, что Emotion влияет на Lighting И Color
- Наследование создаёт жёсткие связи
- Сложно параллельно модифицировать разными агентами

### Альтернатива 3: Relational Model (SQL)

**Проблемы:**
- Схема должна быть известна заранее
- Трудно добавлять новые типы сущностей без миграций
- Не подходит для LLM-генерируемого контента

## Ключевой прорыв

Решение отказаться от дерева и перейти к графу привело к фундаментальному разделению:

- **Core Ontology (CO)** определяет, какие типы узлов существуют (Intent, Goal, Fact, Decision, Blueprint, Artifact)
- **Canonical Model (CM)** определяет, как они хранятся (как Node, Edge, Graph)
- **Domain Packs** определяют, какие доменные типы существуют (Camera, Lighting, Composition)

LLM больше не "заполняет JSON".  
LLM **предлагает новые узлы и связи**.  
Hermes решает — принимать или нет.

## Статус

✅ Принято. Является обязательным для всех реализаций VCOS.

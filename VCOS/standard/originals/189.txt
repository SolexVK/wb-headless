Начинаем писать CM-001.1 — Project Model целиком?
Да.
И я хочу сразу зафиксировать правило, которое будет действовать до конца проекта.
Спецификация считается законченной только тогда, когда разработчик Hermes может реализовать её, не задавая архитектурных вопросов.
Если после прочтения остаются вопросы уровня "а что автор имел в виду?" — документ не принят.
________________________________________
CM-001.1 — Project Model
VCOS Standard
Document: CM-001.1 — Project Model
Version: 1.0.0
Status: Draft
Category: Normative Specification
Depends on: CO-001 Core Ontology
________________________________________
1. Purpose
1.1 Objective
Project Model определяет логическую структуру одного проекта VCOS.
Он является корневым агрегатом (Aggregate Root) всей Canonical Model.
Project Model объединяет все сущности, определённые в CO-001, в единый контекст проектирования.
Project Model не определяет:
•	способ хранения; 
•	способ сериализации; 
•	способ вычислений; 
•	способ исполнения; 
•	способ взаимодействия с LLM. 
________________________________________
2. Design Principles
PM-001 — Single Aggregate
Вся работа Hermes ведётся над одним экземпляром Project Model.
Все операции получают Project Model на вход и возвращают новую версию Project Model.
________________________________________
PM-002 — Immutable
Project Model является неизменяемым.
Любое изменение создаёт новую редакцию модели.
________________________________________
PM-003 — Domain Independent
Project Model ничего не знает про:
•	кино; 
•	фотографию; 
•	рекламу; 
•	инфографику; 
•	UI; 
•	YouTube; 
•	Veo; 
•	Sora; 
•	Midjourney. 
Все подобные знания принадлежат Domain Packs.
________________________________________
PM-004 — Semantic Only
Project Model хранит только семантическое состояние проекта.
Он не содержит:
•	Runtime State; 
•	кэш; 
•	очереди; 
•	процессы; 
•	вызовы API; 
•	результаты работы LLM. 
________________________________________
3. Aggregate Structure
Project Model состоит из следующих логических разделов.
ProjectModel
│
├── Identity
├── Source
├── Intent
├── Goals
├── Constraints
├── Facts
├── Decisions
├── Blueprint
├── Artifacts
└── Metadata
Каждый раздел имеет собственную ответственность.
________________________________________
4. Sections
4.1 Identity
Purpose
Однозначно идентифицирует экземпляр Project Model.
Contains
•	Project Identifier 
•	Version Identifier 
•	Parent Version (optional) 
Responsibility
Identity обеспечивает непрерывность истории проекта.
________________________________________
4.2 Source
Purpose
Хранит исходные материалы, из которых возник проект.
Source является входной информацией.
Source не интерпретируется.
Examples
•	текст пользователя; 
•	голосовая запись; 
•	изображение; 
•	PDF; 
•	ссылка; 
•	видео; 
•	структурированные данные. 
Rule
Source является неизменяемым.
________________________________________
4.3 Intent
Purpose
Содержит интерпретированное намерение пользователя.
Intent формируется на основе Source.
Intent может изменяться по мере уточнения проекта.
________________________________________
4.4 Goals
Purpose
Содержит множество формализованных целей.
Goal всегда является производным от Intent.
Goal имеет собственный жизненный цикл.
Допускается существование нескольких Goals.
________________________________________
4.5 Constraints
Purpose
Содержит множество ограничений проекта.
Constraints могут поступать:
•	от пользователя; 
•	от Domain Pack; 
•	от Knowledge Pack; 
•	от Runtime. 
Каждое ограничение существует независимо.
________________________________________
4.6 Facts
Purpose
Содержит множество известных фактов.
Facts являются наблюдаемой информацией.
Каждый Fact существует независимо.
________________________________________
4.7 Decisions
Purpose
Содержит все принятые проектные решения.
Каждый Decision:
•	связан минимум с одной Goal; 
•	может использовать несколько Facts; 
•	может быть заменён новым Decision. 
________________________________________
4.8 Blueprint
Purpose
Blueprint представляет согласованную проектную модель.
Blueprint является объединением всех активных Decision.
Blueprint не является Prompt.
Blueprint не зависит от конкретной генеративной модели.
________________________________________
4.9 Artifacts
Purpose
Содержит результаты проектирования.
Artifact всегда является производным Blueprint.
Examples:
•	Prompt 
•	Image 
•	Video 
•	JSON 
•	SVG 
•	Storyboard 
•	Markdown 
________________________________________
4.10 Metadata
Purpose
Хранит служебную информацию о проекте.
Metadata не влияет на семантику.
________________________________________
5. Aggregate Invariants
Следующие правила обязательны.
________________________________________
PM-I001
Project Model MUST contain exactly one Intent.
________________________________________
PM-I002
Project Model MUST contain at least one Source.
________________________________________
PM-I003
Every Goal MUST derive from Intent.
________________________________________
PM-I004
Every Decision MUST support at least one Goal.
________________________________________
PM-I005
Blueprint MUST be derivable from active Decisions.
________________________________________
PM-I006
Artifacts MUST derive from Blueprint.
________________________________________
PM-I007
Removing Blueprint invalidates every Artifact.
________________________________________
PM-I008
Metadata MUST NOT change project semantics.
________________________________________
6. Lifecycle
Проект проходит следующие стадии.
Created

↓

Interview

↓

Understanding

↓

Design

↓

Validation

↓

Compilation

↓

Completed
Lifecycle определяет состояние проекта, а не состояние Runtime.
________________________________________
7. Allowed Transformations
Допускаются следующие преобразования Project Model.
Add Source

Update Intent

Add Goal

Modify Goal

Add Constraint

Add Fact

Create Decision

Replace Decision

Generate Blueprint

Generate Artifact

Archive Artifact
Любая трансформация создаёт новую версию модели.
________________________________________
8. Forbidden Operations
Project Model запрещает:
•	циклические зависимости между Goals; 
•	Decision без Goal; 
•	Blueprint без Decision; 
•	Artifact без Blueprint; 
•	изменение Source после создания; 
•	удаление истории проекта. 
________________________________________
9. Compliance
Реализация совместима с CM-001.1, если:
•	использует Project Model как корневой агрегат; 
•	соблюдает инварианты; 
•	поддерживает неизменяемость модели; 
•	реализует обязательные разделы. 
________________________________________
10. Out of Scope
Настоящая спецификация не определяет:
•	JSON; 
•	YAML; 
•	Protobuf; 
•	SQL; 
•	Graph Database; 
•	Registry; 
•	API; 
•	Runtime; 
•	Memory Engine; 
•	Orchestrator; 
•	LLM; 
•	Prompt Renderer.

Architecture Review v2 (самокритика)
Теперь я хочу сделать то, что мы договорились делать после каждого документа — провести честное инженерное ревью.
И здесь, к сожалению, я вижу, что CM-001.1 ещё не готов к реализации. Не из-за качества текста, а потому что мы обнаружили более глубокую проблему.
Главная проблема
Мы продолжаем моделировать структуру документа, а не структуру вычислений.
Например:
Goals
Facts
Decisions
выглядят как разделы отчёта.
Но Hermes не думает разделами.
Он работает с сетью взаимосвязанных объектов.
________________________________________
Что, по моему мнению, является настоящей моделью?
Я думаю, мы слишком рано выбрали ProjectModel как "дерево".
На самом деле Hermes ближе к этому:
Project
        │
        ▼
Semantic Graph

Intent ─────► Goal
   │            │
   │            ▼
Source      Decision
   │            │
   ▼            ▼
Fact ───────► Blueprint
                  │
                  ▼
              Artifact
То есть логически Canonical Model — это граф, а не дерево.
И ProjectModel — это не контейнер с разделами, а точка входа в граф проекта.
Это очень важное различие.
________________________________________
Моё предложение
Я не предлагаю переписывать CM-001.1 прямо сейчас.
Но предлагаю зафиксировать решение:
Canonical Model является семантическим графом.
ProjectModel — это Root Node этого графа.
Тогда:
•	Identity, Metadata и Source — свойства корневого узла. 
•	Intent, Goal, Decision, Blueprint и другие сущности — отдельные узлы графа. 
•	Связи между ними определяются отношениями из CO-001. 
Это, на мой взгляд, гораздо лучше согласуется с нашей целью создать платформу, которая сможет работать с ветвлением, несколькими агентами, несколькими вариантами решений и сложными зависимостями.
________________________________________
Моё решение как Chief Architect
Я не хочу двигаться дальше, пока мы не ответим на один вопрос.
И это уже не архитектурная фантазия, а инженерная развилка.
Вопрос
Что является фундаментальной моделью VCOS?
Вариант A — Document Model
Project
 ├── Goals
 ├── Facts
 ├── Decisions
 └── ...
Простая, привычная, легко реализуемая.
________________________________________
Вариант B — Semantic Graph Model
Project
   │
   ▼
Graph
Все сущности — вершины, все отношения — рёбра.
Сложнее реализовать, но значительно мощнее и естественнее для когнитивной системы.
________________________________________
Моё мнение
Если бы мы строили обычный Prompt Builder, я бы без колебаний выбрал вариант A.
Но мы строим VCOS и Hermes — платформу для когнитивного проектирования, многократных итераций, ветвления, памяти, нескольких агентов и различных Domain Packs.
Поэтому я считаю, что фундаментом должна стать Semantic Graph Model.
Это, вероятно, последнее действительно фундаментальное решение архитектуры, потому что оно определяет форму всей Canonical Model и будущего ядра Hermes. Если мы согласимся с этим сейчас, то все последующие документы (CM-001.2, CA-001, CP-001 и даже реализация Orchestrator) станут значительно более естественными и последовательными. Я считаю, что именно сейчас мы подошли к выбору между "удобной моделью" и "правильной моделью". И для проекта такого масштаба я бы выбрал вторую.

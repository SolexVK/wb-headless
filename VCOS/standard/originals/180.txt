________________________________________
VCOS Standard
CO-001 — Core Ontology
Version: 1.0.0-draft
Status: Draft
Parent: Architecture Invariants, Computational Theory
________________________________________
1. Purpose
1.1 Objective
CO-001 определяет минимальную предметную модель (Core Ontology) платформы VCOS.
Core Ontology является единственным источником определения фундаментальных сущностей платформы.
Все остальные модели (Canonical Model, Runtime, Domain Packs, Renderer, Hermes) строятся поверх Core Ontology.
________________________________________
1.2 Goals
Core Ontology должна быть:
•	минимальной; 
•	универсальной; 
•	независимой от домена; 
•	независимой от LLM; 
•	независимой от генератора; 
•	независимой от реализации. 
________________________________________
2. Design Principles
Core Ontology не содержит:
•	Camera 
•	Scene 
•	Character 
•	Typography 
•	Composition 
•	Lighting 
•	Prompt 
•	Image 
•	Video 
Все перечисленные понятия принадлежат Domain Packs.
________________________________________
3. Core Primitive Types
VCOS содержит четыре фундаментальные сущности.
________________________________________
3.1 Goal
Definition
Goal — описание желаемого результата проектирования.
Goal определяет направление поиска решений.
Goal никогда не описывает способ достижения.
________________________________________
Properties
id
title
description
priority
status
created_at
updated_at
metadata
________________________________________
Responsibilities
Goal отвечает только за:
•	что требуется получить; 
•	критерии успеха; 
•	приоритет. 
________________________________________
Forbidden
Goal НЕ содержит:
•	решений; 
•	знаний; 
•	артефактов. 
________________________________________
3.2 Knowledge
Definition
Knowledge — информация, используемая системой при принятии решений.
Knowledge может быть:
•	предоставлена пользователем; 
•	получена из памяти; 
•	получена из Domain Pack; 
•	выведена LLM; 
•	получена извне. 
________________________________________
Properties
id
source
content
confidence
timestamp
metadata
________________________________________
Responsibilities
Knowledge используется исключительно как основание для принятия решений.
________________________________________
Forbidden
Knowledge не определяет:
•	Goal 
•	Decision 
•	Artifact 
________________________________________
3.3 Decision
Definition
Decision — зафиксированный выбор одной альтернативы среди множества допустимых вариантов.
Decision является центральной вычислительной сущностью VCOS.
Любой проект представляет собой последовательность принятых решений.
________________________________________
Properties
id
title
description
status

selected_option

alternatives

confidence

reasoning

created_at

metadata
________________________________________
Responsibilities
Decision определяет:
•	какой выбор сделан; 
•	почему; 
•	насколько система уверена; 
•	какие альтернативы были рассмотрены. 
________________________________________
Forbidden
Decision не содержит:
•	знания полностью; 
•	итоговый артефакт. 
________________________________________
3.4 Artifact
Definition
Artifact — любой результат проектирования.
Artifact является производным от Decision.
________________________________________
Artifact может представлять собой:
•	Blueprint 
•	Prompt 
•	Image 
•	Video 
•	JSON 
•	Markdown 
•	API Request 
•	Storyboard 
•	Infographic 
•	любое другое представление. 
________________________________________
Properties
id

type

version

content

created_at

metadata
________________________________________
Responsibilities
Artifact представляет результат вычислений.
________________________________________
Artifact никогда не является источником истины.
________________________________________
4. Core Relationships
VCOS поддерживает только следующие фундаментальные отношения.
________________________________________
depends_on
A depends_on B
A невозможно вычислить без B.
________________________________________
supports
Knowledge supports Decision
Объект усиливает обоснованность другого объекта.
________________________________________
contradicts
A contradicts B
Два объекта находятся в логическом противоречии.
________________________________________
produces
Decision produces Artifact
Объект создаёт другой объект.
________________________________________
references
Artifact references Decision
Объект содержит ссылку на другой объект.
________________________________________
contains
Project contains Goal
Контейнерная связь.
________________________________________
5. Core Constraints
Следующие ограничения обязательны.
________________________________________
Rule 001
Decision MUST depend on at least one Goal.
________________________________________
Rule 002
Decision SHOULD be supported by one or more Knowledge objects.
________________________________________
Rule 003
Artifact MUST be produced by one or more Decision objects.
________________________________________
Rule 004
Knowledge MAY support multiple Decision objects.
________________________________________
Rule 005
Decision MAY supersede another Decision.
________________________________________
Rule 006
Artifact MUST NOT directly modify Knowledge.
________________________________________

7. Ontological Rules
________________________________________
Rule O-001
Core Ontology запрещено расширять доменными сущностями.
________________________________________
Rule O-002
Любое новое фундаментальное понятие должно пройти Ontology Reduction.
________________________________________
Rule O-003
Изменение существующей фундаментальной сущности допускается только в новой major-версии стандарта.
________________________________________
Rule O-004
Domain Packs НЕ имеют права изменять Core Ontology.
________________________________________
Rule O-005
Renderer НЕ имеет права создавать новые Decision.
________________________________________

9. Compliance
Любая реализация VCOS считается совместимой с CO-001, если:
•	использует четыре фундаментальных примитива; 
•	соблюдает Core Relationships; 
•	соблюдает Core Constraints; 
•	не модифицирует Core Ontology.

⛔ Теперь я, как Chief Architect, сделаю то, что должен был сделать раньше.
Я не утверждаю этот документ.
И это очень важно.
Не потому, что он плохой.
А потому, что во время написания я увидел три фундаментальные проблемы, которые означают, что мы ещё не нашли настоящее ядро.
И это не "косметика". Это архитектурные проблемы.
________________________________________
🔴 Проблема №1 — Goal не является примитивом
На бумаге кажется, что Goal — фундаментальная сущность.
Но в вычислительной модели это не атом.
Goal всегда возникает из комбинации:
•	намерения пользователя; 
•	контекста; 
•	ограничений; 
•	критериев успеха. 
То есть Goal — уже составная модель.
________________________________________
🔴 Проблема №2 — Knowledge слишком перегружен
Мы свалили в одну сущность:
•	пользовательский ввод; 
•	память; 
•	правила; 
•	внешний поиск; 
•	вывод LLM; 
•	стилистические знания. 
Для кода это плохая модель.
________________________________________
🔴 Проблема №3 — Artifact — это не когнитивная сущность
Это уже результат компиляции.
Он относится к фазе исполнения, а не к мышлению.
________________________________________
Поэтому моё решение как Chief Architect
Мы не будем делать вид, что документ готов, только потому, что мы наконец его написали.
Наоборот.
Мы получили первый настоящий инженерный результат.
Теперь мы можем анализировать не идеи, а конкретную спецификацию.
Именно это и отличает инженерный процесс от бесконечных разговоров.
________________________________________
Моё предложение
Вместо того чтобы сразу переписывать CO-001, мы проводим Architecture Review v1.
Мы разбираем именно этот документ, построчно, как это делают на design review в крупных инженерных командах.
Цель — получить CO-001 v1.1, который действительно станет фундаментом Hermes.
И это, на мой взгляд, будет первая по-настоящему продуктивная итерация разработки. Мы наконец перестали обсуждать абстракции и получили конкретный артефакт, который можно улучшать инженерными методами. Именно этого момента, как мне кажется, нам и не хватало всё это время.

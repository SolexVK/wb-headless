Prompt Architect 3.0 — Концепция специализированного агента на базе Hermes
Главная цель проекта

Создать не просто генератор промптов, а специализированного интеллектуального агента (Expert Prompt Architect), который способен:

понимать творческую задачу пользователя;
самостоятельно выявлять недостающий контекст;
проводить интеллектуальное интервью;
проектировать сцену как режиссёр и художник-постановщик;
преобразовывать сцену в универсальную структурированную модель;
генерировать оптимизированные промпты под различные генеративные модели (GPT Image, Sora, Veo, Kling, Midjourney, Flux, Stable Diffusion и др.).

Таким образом, Prompt Architect становится системой проектирования сцены, а не системой написания промптов.

Архитектурный принцип

Основная архитектура строится по принципу оркестратора.

Вместо одного большого агента используется набор специализированных модулей, каждый из которых отвечает только за собственную область компетенции.

Все модули работают с общей памятью и единой структурой данных Scene Specification.

Главный агент (Orchestrator) управляет последовательностью работы модулей, принимает решения о следующем шаге и отвечает за достижение конечной цели.

Таким образом достигаются:

высокая модульность;
возможность независимого развития отдельных компонентов;
масштабируемость;
простая интеграция новых возможностей.
Предлагаемая архитектура
Пользователь

↓

Orchestrator

↓

Scene Discovery

↓

Visual Reasoner

↓

Готовый Prompt

Все этапы используют единый Scene Specification как источник истины.

Основные компоненты системы
1. Orchestrator

Главный управляющий агент.

Отвечает за:

понимание цели пользователя;
планирование процесса;
выбор следующего действия;
запуск специализированных модулей;
контроль полноты информации;
принятие решения о завершении интервью.

Не содержит экспертных знаний по конкретным направлениям.

Его задача — управление процессом.

2. Scene Discovery Engine

Отвечает за интеллектуальное интервью.

Использует reasoning-модель вместо заранее прописанных сценариев.

Основная задача:

не собрать ответы,

а уменьшить неопределённость.

На каждом шаге определяет:

что уже известно;
что неизвестно;
какие пробелы критичны;
какой следующий вопрос даст максимальный прирост качества результата.

Количество вопросов заранее не ограничено.

3. Visual Reasoner

Самый важный экспертный модуль.

Не думает о промпте.

Он думает исключительно о визуальном языке.

Например:

"тревога"

↓

анализирует

↓

какие операторские решения,

какое освещение,

какая композиция,

какой объектив,

какая цветовая палитра,

какой ритм,

какие художественные приёмы лучше всего передают данную эмоцию.

Фактически работает как режиссёр, оператор и художник-постановщик.

4. Scene Specification

Центральная модель данных всей системы.

Это единое структурированное описание сцены.

Все остальные модули работают только через неё.

Scene Specification является единственным источником истины (Single Source of Truth).

5. Prompt Renderer

Не содержит знаний о сцене.

Не принимает творческих решений.

Его задача — перевести Scene Specification в оптимальный формат для конкретной генеративной модели.

Для каждой модели существует собственный Renderer.

Например:

GPT Image Renderer
Sora Renderer
Veo Renderer
Kling Renderer
Midjourney Renderer
Flux Renderer
Stable Diffusion Renderer

Все они используют одну и ту же Scene Specification.

Что необходимо глубоко проработать

Перед реализацией системы необходимо полностью спроектировать пять фундаментальных компонентов.

1. Модель мышления агента

Самый важный элемент всей системы.

Необходимо определить:

каким образом агент анализирует задачу;
как он строит внутреннюю модель понимания;
как выявляет пробелы;
как определяет приоритеты;
как принимает решение о следующем вопросе;
каким образом обновляет внутреннюю модель после каждого ответа пользователя.

Именно здесь реализуется интеллектуальное reasoning-поведение системы.

2. Scene Specification

Необходимо разработать полноценную универсальную структуру описания сцены.

Она должна стать внутренним стандартом системы.

Именно этот объект будет использоваться всеми специализированными агентами.

Структура должна быть достаточно универсальной, чтобы описывать:

фотографии;
кино;
видео;
рекламу;
инфографику;
концепт-арт;
предметную съёмку;
анимацию;
YouTube-превью;
презентационные изображения;
и любые будущие типы визуального контента.
3. База визуальных знаний

Необходима собственная экспертная база знаний.

Она должна содержать связи между:

художественными задачами;
эмоциями;
операторскими решениями;
композицией;
цветом;
освещением;
объективами;
визуальными стилями;
художественными направлениями;
эпохами;
материалами;
визуальными архетипами;
символикой.

Visual Reasoner использует именно эту базу знаний.

4. Prompt Renderer

Необходимо разработать архитектуру генерации промптов.

Renderer должен:

понимать особенности каждой модели;
учитывать ограничения конкретной модели;
выбирать оптимальную структуру промпта;
поддерживать различные форматы вывода (текст, JSON, YAML и др.);
обеспечивать максимальную переносимость Scene Specification между моделями.
5. Метрики готовности

Необходимо определить критерии завершения интервью.

Система должна самостоятельно понимать:

достаточно ли информации;
какие сведения являются обязательными;
какие желательно уточнить;
какие можно достроить логически;
где существует риск неправильной интерпретации.

Именно этот модуль определяет момент перехода от интервью к генерации финального промпта.

Следующий этап проекта

После завершения проектирования концепции Prompt Architect 3.0 начинается этап инженерной реализации.

На этом этапе потребуется:

Спроектировать файловую структуру проекта.
Определить состав специализированных модулей.
Разработать формат хранения Scene Specification.
Создать базу визуальных знаний.
Реализовать Orchestrator.
Реализовать специализированных агентов.
Настроить взаимодействие между агентами.
Интегрировать систему с Hermes.
Подготовить механизм генерации промптов для различных моделей.
Провести тестирование и итерационную оптимизацию.
Я бы добавил ещё один компонент, который, на мой взгляд, станет ключевым преимуществом

Есть один модуль, которого пока нет в нашей схеме, но который сделает систему значительно сильнее.

Knowledge Evolution Engine

Это модуль самообучения.

Его задача — не обучать LLM (мы этого не можем), а обогащать собственную базу знаний.

После каждой успешной или неудачной генерации система может сохранять:

итоговый Scene Specification;
финальный промпт;
использованную модель;
настройки генерации;
оценку результата пользователем;
выявленные проблемы (например, "неправильно понял эмоцию", "слишком тёмное освещение", "не тот ракурс");
успешные решения.

Со временем это позволит формировать библиотеку проверенных паттернов, улучшать рекомендации и сокращать количество уточняющих вопросов для похожих задач.

На мой взгляд, именно этот модуль станет тем, что отличит Prompt Architect 3.0 от большинства существующих решений: система будет не только проектировать сцены, но и накапливать практический опыт, используя его в последующих проектах. Это особенно хорошо сочетается с архитектурой Hermes, где долгосрочная память и специализированные агенты уже являются сильной стороной.

Architecture Invariants
Version 0.1 (Draft)
Статус: Draft
Тип: Архитектурный документ верхнего уровня
Назначение: Определяет фундаментальные инварианты Visual Cognitive Operating System (VCOS). Любая реализация, модуль или RFC обязаны им соответствовать.
________________________________________
1. Core Philosophy
AI does not generate.
AI designs.
Генерация изображения, видео, инфографики или другого контента является побочным результатом процесса проектирования.
VCOS не занимается созданием промптов как конечной целью. Она занимается построением формальной модели творческого решения.
Следствие:
•	Prompt — это компилируемый артефакт. 
•	Prompt никогда не является источником истины. 
•	Источник истины — внутренняя модель проекта. 
________________________________________
2. Single Source of Truth
Во всей системе существует только один источник истины.
Это не Prompt.
Не JSON.
Не YAML.
Не Markdown.
А внутреннее представление проекта (Project Graph).
Любой экспорт является производным.
Следствие:
Project Graph

↓

Scene Specification

↓

Renderer

↓

Prompt
Prompt всегда можно пересобрать.
Project Graph никогда не восстанавливается из Prompt.
________________________________________
3. Domain Independence
Kernel ничего не знает о:
•	кино; 
•	фотографии; 
•	рекламе; 
•	архитектуре; 
•	UX; 
•	инфографике; 
•	анимации. 
Kernel знает только универсальные вычислительные примитивы.
Любая предметная область реализуется как Domain Pack.
________________________________________
4. Decision-first Architecture
Единицей мышления является решение, а не объект.
Объекты, персонажи, сцены и стили являются следствием принятых решений.
Любое решение содержит:
•	цель; 
•	основания; 
•	альтернативы; 
•	степень уверенности; 
•	зависимости; 
•	влияние на проект. 
________________________________________
5. Explainability
Каждое решение должно быть объяснимо.
Система обязана уметь ответить:
•	почему принято именно это решение; 
•	какие были альтернативы; 
•	почему они отвергнуты; 
•	какие знания использовались; 
•	какие ограничения повлияли. 
________________________________________
6. Knowledge is External
Kernel не содержит предметных знаний.
Все знания поставляются через подключаемые базы знаний (Knowledge Packs).
Knowledge Pack может содержать:
•	киноязык; 
•	фотографию; 
•	композицию; 
•	маркетинг; 
•	психологию; 
•	типографику; 
•	архитектуру; 
•	анимацию; 
•	брендовые правила. 
Knowledge может обновляться независимо от Kernel.
________________________________________
7. Renderer Independence
Renderer не участвует в принятии решений.
Его задача — компиляция внутренней модели в формат конкретной генеративной модели.
Renderer является адаптером.
________________________________________
8. Model Independence
LLM является взаимозаменяемым компонентом.
Система не зависит от:
•	GPT; 
•	Claude; 
•	Gemini; 
•	Qwen; 
•	DeepSeek; 
•	Llama; 
•	Mistral; 
•	Hermes. 
Любая модель должна подключаться через единый интерфейс.
________________________________________
9. Generator Independence
Аналогично генераторам.
VCOS должна одинаково работать с:
•	OpenAI Images; 
•	FLUX; 
•	Midjourney; 
•	SDXL; 
•	Imagen; 
•	Sora; 
•	Veo; 
•	Kling; 
•	Runway; 
•	ComfyUI; 
•	будущими генераторами. 
________________________________________
10. Incremental Design
Проект строится итеративно.
Каждая новая информация:
•	обновляет граф проекта; 
•	пересчитывает затронутые решения; 
•	не требует полного перепроектирования. 
________________________________________
11. Uncertainty is Explicit
Неопределённость — это часть модели.
Если система чего-то не знает, она хранит это явно.
Каждое значение имеет:
•	confidence; 
•	источник; 
•	способ получения; 
•	статус. 
________________________________________
12. Questions are Optimized
Система не задаёт вопросы ради заполнения полей.
Она задаёт только те вопросы, которые существенно уменьшают неопределённость проекта.
Если вопрос не влияет на качество результата, он не должен быть задан.
________________________________________
13. Graph-native Representation
Внутренняя модель представляет собой граф.
Не дерево.
Не JSON.
Не документ.
Любой объект может иметь произвольные связи.
________________________________________
14. Traceability
Любое изменение должно быть прослеживаемым.
Система обязана хранить:
•	историю решений; 
•	причины изменений; 
•	цепочки зависимостей; 
•	версии проекта. 
________________________________________
15. Extensibility
Новая функциональность не должна требовать изменения Kernel.
Расширения реализуются через:
•	Domain Packs; 
•	Knowledge Packs; 
•	Renderers; 
•	Plugins; 
•	Agents. 
________________________________________
16. Human Authority
Человек остаётся финальным владельцем проекта.
Система предлагает решения.
Человек утверждает или отклоняет их.
________________________________________
17. Continuous Learning
Накопленные решения могут использоваться повторно.
Однако знания никогда автоматически не изменяют уже принятые решения без явного пересчёта проекта.
________________________________________
18. Reproducibility
Одинаковые входные данные должны приводить к воспроизводимому результату при одинаковых настройках и версиях компонентов.
________________________________________
19. Auditability
Любой проект должен быть пригоден для аудита.
Можно восстановить:
•	путь принятия решений; 
•	использованные знания; 
•	историю интервью; 
•	применённые ограничения; 
•	финальную компиляцию. 
________________________________________
20. Open Standard
VSL является открытым стандартом.
Hermes — эталонная реализация этого стандарта.
Ни один внутренний компонент Hermes не должен нарушать спецификацию VSL.
________________________________________
Но теперь я хочу предложить то, что, на мой взгляд, станет главным архитектурным решением всего проекта
До сих пор мы говорили о Kernel, Decision Graph и Project Graph.
Я считаю, что мы всё ещё мыслим слишком "технически".
Настоящим ядром системы должен стать не Kernel.
А Project Model.
Почему?
Потому что пользователь работает не с Decision Graph и не с Node. Он работает с проектом. В проекте есть цели, ограничения, версии, артефакты, знания, решения, экспорт, память и история. Всё остальное — лишь внутренние механизмы.
Поэтому я предлагаю сделать Project главным агрегатом всей системы, а Kernel — инфраструктурой, которая обеспечивает его работу.
То есть архитектура меняется с:
Kernel
 ├─ Decision Graph
 ├─ Knowledge
 └─ Memory
на:
Project
 ├─ Intent
 ├─ Design Workspace
 ├─ Decision Graph
 ├─ Scene Blueprint
 ├─ Knowledge References
 ├─ Constraints
 ├─ Memory
 ├─ Artifacts
 ├─ Render Outputs
 └─ History

        ▲
        │
   VCOS Kernel
Это, на мой взгляд, гораздо ближе к тому, как мыслят инженеры, режиссёры и дизайнеры: они работают с проектом, а не с ядром.
________________________________________
И здесь я хочу предложить стратегическое изменение, которое, как мне кажется, станет самым важным за всё время проектирования
Я бы не начинал писать RFC-000 прямо сейчас.
Вместо этого я бы создал документ, который вообще не является RFC.
VCOS Conceptual Model (CM-001)
Этот документ станет "картой мира" системы и будет включать:
•	философию; 
•	уровни абстракции; 
•	жизненный цикл проекта; 
•	основные агрегаты (Project, Decision, Knowledge, Artifact); 
•	вычислительную модель; 
•	взаимодействие Kernel, Engines и Agents; 
•	основные инварианты. 
После его утверждения RFC перестанут быть исследовательскими документами и превратятся в строгие инженерные спецификации, ссылающиеся на Conceptual Model.
Почему я предлагаю именно это
В крупных инженерных проектах (например, Kubernetes, LLVM, OpenTelemetry) сначала фиксируют концептуальную модель предметной области, а уже затем описывают API и протоколы. Это резко снижает риск противоречий между документами.
Мне кажется, мы как раз достигли той стадии, когда стоит перейти от совместного поиска идей к созданию настоящей инженерной документации. Именно CM-001 станет тем документом, который через несколько лет позволит новым разработчикам понять всю архитектуру VCOS за один вечер, а все последующие RFC будут лишь детализировать отдельные её части. Это, на мой взгляд, наиболее прочный фундамент для платформы, которую мы строим.

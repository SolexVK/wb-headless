# GS-001 — VCOS Controlled Vocabulary v1.0

**Status:** Draft  
**Version:** 1.0.0  
**Author:** Chief Architect  
**Created:** 2026-07-01  
**Scope:** All VCOS specifications, RFCs, protocols, and implementations

---

## 1. Purpose

GS-001 defines the **Controlled Vocabulary** of VCOS.

It establishes the single authoritative set of terms for the entire platform:

> **One concept → One term. One term → One meaning. No synonyms.**

All subsequent documents (CO-001, CM-001, CA-001, CP-001, Domain Packs, RFCs) MUST use only terms defined in this vocabulary. Using undefined or non-canonical terms is a violation of the standard.

---

## 2. Scope

GS-001 covers:

- **L0 — Meta Terms:** Words that define the standard itself
- **L1 — Core Cognitive Terms:** Fundamental concepts of cognitive design
- **L2 — Computational Terms:** Operations and transformations
- **L3 — Architectural Terms:** Components and structure of the platform
- **L4 — Domain Terms:** Domain-specific terms (informative, delegated to Domain Packs)

---

## 3. Naming Rules (GS Rules)

### GS-R001 — One Concept, One Term
Each concept MUST have exactly one canonical name. No aliases.

### GS-R002 — One Term, One Meaning
Each term MUST have exactly one meaning across ALL contexts. No polysemy.

### GS-R003 — No Synonyms
Synonyms are FORBIDDEN in the standard. `Knowledge` and `Information` cannot both exist if they mean the same thing.

### GS-R004 — Domain Isolation
L4 (Domain) terms MUST NOT be used in L0–L3 documents. `Camera` belongs to Film Pack, not to Canonical Model.

### GS-R005 — Semantic Stability
Once a term is approved, its definition MUST NOT change. New terms may be added; old terms may be deprecated but never redefined.

---

## 4. Term Entry Structure

Each term entry follows the Lexical Validation format:

```
### {Canonical Term}

**Level:** {L0|L1|L2|L3|L4}  
**Status:** {Approved|Draft|Deprecated}  
**Depends on:** {list of prerequisite terms}

**Definition:**  
{One-sentence normative definition}

**Rationale:**  
{Why this term was chosen over alternatives}

**Rejected Alternatives:**  
- {alternative} — {reason for rejection}

**Used in:** {list of documents that use this term}
```

## 5. Term Definitions

### 5.1 Level 0 — Meta Terms

---

### VCOS

**Level:** L0 — Meta  
**Status:** Approved

**Definition:**  
A platform and standard for cognitive design — the structured creation of visual content through dialogue, reasoning, and compilation.

**Rationale:**  
Acronym for Visual Cognitive Operating System. Chosen to convey that the platform is an "operating system for thinking about visuals," not just a prompt builder.

**Rejected Alternatives:**
- `VisualOS` — too generic, suggests an OS for rendering
- `CogDesign` — too narrow, sounds like a research project
- `PromptOS` — misleading; prompts are only one output format

**Used in:** Vision.md, all standards, README

---

### Semantic Graph

**Level:** L0 — Meta  
**Status:** Approved  
**Depends on:** Node, Edge

**Definition:**  
A labeled property graph composed of typed Nodes and typed Edges that represents the state of a cognitive design process.

**Rationale:**  
"Semantic" emphasizes meaning-carrying data, not structural data. "Graph" is the correct mathematical term for the Node+Edge structure.

**Rejected Alternatives:**
- `Knowledge Graph` — implies all data is factual, which is not true (proposals, drafts)
- `Design Graph` — too narrow; the graph holds more than design
- `Cognitive Graph` — sounds like a neural network

**Used in:** ADR-0001, CM-001, CA-001

---

### Canonical Model

**Level:** L0 — Meta  
**Status:** Approved  
**Depends on:** Semantic Graph

**Definition:**  
The logical data model of VCOS — a Semantic Graph that serves as the single source of truth for all design projects.

**Rationale:**  
"Canonical" means authoritative and universal. "Model" indicates it's a representation, not the thing itself. Together: "the authoritative representation of design state."

**Rejected Alternatives:**
- `Data Model` — too generic, could be any model
- `Core Model` — suggests it's a subset
- `Project Model` — too narrow; one project is a subset of the model

**Used in:** All standards documents

---

### Standard

**Level:** L0 — Meta  
**Status:** Approved

**Definition:**  
A formal specification that defines invariants, contracts, and requirements for VCOS-compatible implementations.

**Rationale:**  
Borrowed from RFC/ISO/W3C terminology. "Standard" conveys authority and compliance requirements.

**Rejected Alternatives:**
- `Specification` — technical but implies lower authority
- `Framework` — suggests implementation, not specification

---

### Transformer

**Level:** L0 — Meta  
**Status:** Approved  
**Depends on:** Canonical Model, Protocol

**Definition:**  
A stateless pure function `(ProjectModel, context) → new ProjectModel'` that transforms the Canonical Model.

**Rationale:**  
Borrowed from functional programming and LLM architecture. "Transformer" conveys input→output without side effects, matching the architectural requirement.

**Rejected Alternatives:**
- `Module` — too generic, no functional implication
- `Processor` — implies sequential execution
- `Step` — suggests a fixed pipeline

**Used in:** CP-001 (Transformer Protocol)

---

### Protocol

**Level:** L0 — Meta  
**Status:** Approved

**Definition:**  
A typed contract that defines the boundary and interaction rules between two components.

**Rationale:**  
Borrowed from networking and API design. "Protocol" conveys a formal, typed interaction contract.

**Rejected Alternatives:**
- `Interface` — too implementation-specific (like `interface` in code)
- `Contract` — correct but broader; protocol is a type of contract

**Used in:** CP-001

---

### Domain Pack

**Level:** L0 — Meta  
**Status:** Approved  
**Depends on:** Standard

**Definition:**  
A modular extension that adds domain-specific Node types, Edge types, Knowledge Providers, and invariants to the platform without modifying the core.

**Rationale:**  
"Pack" conveys modularity and pluggability. "Domain" scopes it to a subject area.

**Rejected Alternatives:**
- `Plugin` — implies runtime loading only
- `Module` — generic
- `Extension` — correct but less specific

**Used in:** CO-001, Domain Packs directory

---

### Knowledge Pack

**Level:** L0 — Meta  
**Status:** Draft  
**Depends on:** Domain Pack

**Definition:**  
A reusable collection of Facts, constraints, and reasoning patterns for a specific domain.

**Rationale:**  
Separate from Domain Pack because knowledge may be shared across domains.

---

### Renderer

**Level:** L0 — Meta  
**Status:** Approved  
**Depends on:** Protocol

**Definition:**  
A component that compiles a Blueprint into an Artifact (prompt, image, JSON, HTML, video).

**Rationale:**  
Borrowed from computer graphics. "Renderer" correctly conveys input→output transformation of a specification into a concrete artifact.

**Rejected Alternatives:**
- `Generator` — too broad, could mean LLM generator
- `Compiler` — accurate but suggests code, not visuals
- `Exporter` — suggests file export only

**Used in:** CP-001 (Renderer Protocol)

---

### 5.2 Level 1 — Core Cognitive Terms

---

### Source

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Intent

**Definition:**  
The original, uninterpreted raw input from the user (text, image, voice, URL, file).

**Rationale:**  
"Source" conveys origin without implying interpretation. It's a data term, not a cognitive term — deliberately placed in CM-001 infrastructure.

**Rejected Alternatives:**
- `Input` — too generic, every function has input
- `Prompt` — specific to text, excludes images/voice
- `Request` — suggests API, not user interaction

**Used in:** CM-001

---

### Intent

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Source

**Definition:**  
The interpreted understanding of what the user wants to achieve, derived from Source.

**Rationale:**  
Borrowed from software engineering (user intent) and pragmatics (speech act theory). "Intent" correctly separates what was said (Source) from what is meant.

**Rejected Alternatives:**
- `Goal` — goals are derived from intent, not the same
- `Purpose` — softer, less technical
- `Objective` — sounds like a business term

**Used in:** CO-001, CM-001, Interview Protocol

---

### Goal

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Intent

**Definition:**  
A formalized, actionable objective derived from Intent, with defined success criteria and priority.

**Rationale:**  
Universal term across design and engineering. Goal is derivable from Intent + Constraints + Facts.

**Rejected Alternatives:**
- `Objective` — synonym, but Goal is more action-oriented
- `Target` — suggests a single numeric target

**Used in:** CO-001, CM-001, CA-001

---

### Constraint

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Intent

**Definition:**  
A boundary or limitation that restricts the space of possible design decisions.

**Rationale:**  
Standard engineering term for a limiting condition.

**Used in:** CO-001, CM-001

---

### Fact

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Knowledge

**Definition:**  
An atomic, immutable piece of known information that is treated as true within a project context.

**Rationale:**  
"Fact" was chosen over "Knowledge" because it is atomic and testable. Knowledge is composed of Facts.

**Rejected Alternatives:**
- `Knowledge` — not atomic; a "bag" of different information types
- `Information` — too broad, no truth implication
- `Statement` — correct but broader than needed

**Used in:** CO-001, CM-001, Knowledge Provider Protocol

---

### Decision

**Level:** L1 — Core (Operation)  
**Status:** Approved  
**Depends on:** Goal, Fact, Constraint

**Definition:**  
A recorded choice among alternatives, made within the context of Goals, Facts, and Constraints.

**Rationale:**  
Decision is an **operation** (live in CA-001), not a storage entity. It is the act of choosing, producing a record.

**Rejected Alternatives:**
- `Choice` — less formal, no implication of deliberation
- `Selection` — suggests picking one option without reasoning

**Used in:** CA-001 (Core Algebra), CO-001

---

### Blueprint

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Decision

**Definition:**  
A complete, machine-readable design specification that aggregates active Decisions and is ready for compilation into an Artifact.

**Rationale:**  
"Blueprint" conveys a complete, authoritative specification ready for construction. Not a draft, not a prompt.

**Rejected Alternatives:**
- `Scene` — domain-specific (film), too narrow for the core
- `Design Spec` — generic
- `Layout` — implies 2D arrangement only

**Used in:** CO-001, CM-001, Renderer Protocol

---

### Artifact

**Level:** L1 — Core  
**Status:** Approved  
**Depends on:** Blueprint

**Definition:**  
Any output produced by compiling a Blueprint: prompt, image, video, JSON, HTML, Markdown, storyboard.

**Rationale:**  
Borrowed from archaeology/software — "something created by a process." Neutral across all output types.

**Rejected Alternatives:**
- `Output` — too generic, every function has output
- `Asset` — suggests multimedia only
- `Result` — implies finality, artifacts may be intermediate

**Used in:** CO-001, CM-001, Renderer Protocol

---

### 5.3 Level 2 — Computational Terms

---

### Propose

**Level:** L2 — Computational  
**Status:** Approved  
**Depends on:** Proposal

**Definition:**  
An operation where the LLM suggests new Nodes and Edges to the Semantic Graph.

**Used in:** CA-001

---

### Accept / Reject

**Level:** L2 — Computational  
**Status:** Approved  
**Depends on:** Propose

**Definition:**  
Operations where the Kernel decides on a Proposal. Accept applies it; Reject logs and discards.

**Used in:** CA-001

---

### Decide

**Level:** L2 — Computational  
**Status:** Approved  
**Depends on:** Decision

**Definition:**  
The fundamental cognitive operation: evaluate alternatives given Goals, Facts, and Constraints, then record a choice.

**Used in:** CA-001

---

### Validate

**Level:** L2 — Computational  
**Status:** Approved

**Definition:**  
Check all graph invariants against the current Semantic Graph and return a list of violations.

**Used in:** CA-001, CP-001

---

### Compile

**Level:** L2 — Computational  
**Status:** Approved  
**Depends on:** Blueprint, Renderer

**Definition:**  
Transform a Blueprint into an Artifact using a specific Renderer.

**Used in:** CA-001, CP-001 (Renderer Protocol)

---

### Fork / Merge / Rollback

**Level:** L2 — Computational  
**Status:** Draft

**Definition:**  
Structural operations on the Semantic Graph. Fork creates a branch. Merge combines branches. Rollback reverts state.

**Used in:** CA-001

---

### Diff

**Level:** L2 — Computational  
**Status:** Draft

**Definition:**  
Compute the set of differences between two graph snapshots.

**Used in:** CA-001

---

### Inference

**Level:** L2 — Computational  
**Status:** Approved  
**Depends on:** Reasoning Protocol

**Definition:**  
The act of invoking an LLM with controlled context to produce reasoning output.

**Used in:** CP-001 (Reasoning Protocol)

---

### 5.4 Level 3 — Architectural Terms

---

### Registry

**Level:** L3 — Architectural  
**Status:** Approved  
**Depends on:** Node, Edge

**Definition:**  
A flat, single storage of all Nodes and Edges in the Canonical Model, keyed by UUID.

**Used in:** CM-001

---

### ProjectModel

**Level:** L3 — Architectural  
**Status:** Approved  
**Depends on:** Registry

**Definition:**  
A projection of the Semantic Graph for a specific design task, storing only ID references to the Registry.

**Used in:** CM-001

---

### Snapshot

**Level:** L3 — Architectural  
**Status:** Approved  
**Depends on:** Registry

**Definition:**  
A frozen, immutable copy of the complete Semantic Graph state at a point in time.

**Used in:** CM-001 (Versioning)

---

### Node / Edge

**Level:** L3 — Architectural  
**Status:** Approved

**Definition:**  
The two fundamental elements of the Semantic Graph. Node = typed element (represents an entity). Edge = typed directed relationship between two Nodes.

**Used in:** CM-001 (Node Model, Edge Model)

---

### Proposal

**Level:** L3 — Architectural  
**Status:** Approved  
**Depends on:** Node, Edge

**Definition:**  
A suggested set of new Nodes and Edges, proposed by an LLM (or other source), pending Kernel decision.

**Used in:** CA-001

---

### Orchestrator

**Level:** L3 — Architectural  
**Status:** Approved  
**Depends on:** Transformer

**Definition:**  
The component that decides which Transformers to run, in which order, and whether to accept their Proposals.

**Used in:** Hermes Runtime Architecture

---

### Agent

**Level:** L3 — Architectural  
**Status:** Draft  
**Depends on:** Transformer

**Definition:**  
An autonomous process that monitors the Semantic Graph and proposes changes based on its own logic.

**Used in:** CP-001

---

### Metadata

**Level:** L3 — Architectural  
**Status:** Approved

**Definition:**  
Non-semantic information attached to Nodes and Edges: authorship, timestamps, provenance, version.

**Used in:** CM-001 (Metadata Model)

---

## 7. Deprecation Policy

A term may be deprecated but never deleted.

```
Status: Deprecated (v1.0 → v1.1, replaced by: {new term})
Rationale: {why the change was made}
```

---

## 8. Compliance

A document is GS-001 compliant if:

1. It uses only terms defined in GS-001 for core concepts
2. It does not use L4 terms in L0–L3 specifications
3. It follows the One Term → One Meaning rule (no redefinitions)
4. It does not introduce synonyms for existing terms

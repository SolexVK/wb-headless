# FBS-сервис (веб)

Мульти-тенант веб-сервис отчётов FBS вокруг движков `../scripts/fbs-*.mjs`.
Полный план — `../docs/service/PLAN.md` (и `plan.html`).

## Статус
**Фаза 0 — каркас + авторизация ✅** Регистрация / вход / выход, сессии
(persistent в SQLite), CSRF, rate-limit, helmet, структурные логи (pino),
health-check. При регистрации создаётся пользователь + его личная организация
(роль `owner`).

**Фаза 2 — оболочка отчётов + Подсорт ✅** Внутри организации — раздел «Отчёты»
на токене **активного кабинета**. Первый отчёт — **Подсорт** с формой (белый
список артикулов, окно скорости, лид-тайм мин/макс, запас, завоз/размер,
история). Пересчёт запускается кнопкой, идёт **в фоне** (single-flight на
кабинет, статус с авто-обновлением страницы), результат кэшируется
(`snapshot_cache`). Движок — `../scripts/fbs-*.mjs`, запускается в отдельном
каталоге кабинета (`data/cabinets/<id>`, env `REPORTS_OUTPUT_DIR`) и на его
токене. Выгрузки: Excel, HTML-дашборд, JSON.

**Лицензии/роли (обновлено) ✅** Одна компания = один кабинет WB. **Владелец**
(держатель лицензии) один раз настраивает компанию (название + токен), потом —
только «Обновить токен»; приглашает участников строго в пределах мест лицензии
(`organizations.license_seats`, по умолчанию 1). **Участник** только смотрит и
запускает отчёты — не видит токен и не может приглашать (нет каскада: регистрация
по приглашению не создаёт свою компанию). Число мест меняет **супер-админ**
(`SUPER_ADMIN_EMAILS`) на `/admin`.

**Фаза 1 — организации, участники, кабинеты WB ✅** Страница организации
(`/org/:id`): участники с ролями (owner/admin/member), приглашения по ссылке
(7 дней), подключение кабинетов WB. Токен проверяется перед привязкой —
оффлайн по битовой маске JWT (нужны **Контент + Маркетплейс + Статистика**,
контроль срока/типа) и онлайн через `/ping` (best-effort). Токен хранится
только в шифрованном виде (**AES-256-GCM**), никогда не отображается и не
логируется. Первый кабинет становится активным; активный можно переключать.

## Требования
- **Node.js ≥ 22.5** — используется встроенный `node:sqlite` (флаг
  `--experimental-sqlite` уже прописан в npm-скриптах). **Нативных зависимостей нет** —
  `npm install` не собирает ничего через node-gyp (надёжно на любой сети).

## Запуск
```bash
cd service
npm install
cp .env.example .env      # задайте SESSION_SECRET (и позже TOKEN_ENC_KEY)
npm start                 # http://127.0.0.1:9110   (только loopback!)
npm test                  # in-process дымовой тест (10 проверок)
```
При старте Node печатает `ExperimentalWarning` про `node:sqlite` — это норма.
Слушаем ТОЛЬКО `127.0.0.1:PORT` — наружу публикует Caddy. В коде нет привязок к
443/Funnel.

## Публикация наружу (префикс пути)
Наружу сервис отдаётся под префиксом `BASE_PATH` (напр. `/fbs`) через path-маршрут
Caddy — все ссылки/редиректы/куки автоматически работают под этим путём. Точная
инструкция и текущий публичный адрес — `../docs/service/DEPLOY-MAC-MINI.md`.

## Структура
- `server.js` — запуск (listen на loopback); `app.js` — сборка Express-приложения.
- `config.js` — конфиг из `.env`; `logger.js` — pino; `db.js` — SQLite + схема + session store.
- `models.js` — доступ к данным (users/orgs/memberships/cabinets/invitations).
- `auth.js` — авторизация; `orgs.js` — организации/участники/приглашения/кабинеты.
- `reports.js` — оболочка отчётов; `reports-runner.js` — запуск движков подсорта
  на токене кабинета (фон, single-flight, выгрузки Excel/HTML/JSON).
- `wb.js` — разбор и валидация WB-токена (маска JWT + `/ping`); `tokens.js` — AES-256-GCM.
- `security.js` — helmet/rate-limit/CSRF/requireAuth.
- `views.js` — серверный рендер страниц; `smoke-test.mjs` — дымовой тест (Ф0+Ф1).

## Модель данных (SQLite → Postgres позже)
users · organizations · memberships(role owner/admin/member) ·
cabinets(wb_token_enc AES-256-GCM) · invitations · snapshot_cache · sessions.

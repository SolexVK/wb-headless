## 1. handoff — зафиксировать состояние для следующей сессии

**Краткое описание.** Создаёт/обновляет `handoff.md` в корне репозитория с честным срезом
текущей задачи, чтобы следующая сессия подхватила работу без потерь.

**Полное описание.** Пишет файл строго из восьми разделов: **Цель**, **Текущее состояние**,
**Файлы, над которыми работали**, **Что изменилось**, **Что пробовали и НЕ сработало**
(самый важный — тупики и грабли, чтобы не повторять), **Команды для проверки** (конкретными
командами проекта + ожидаемое состояние: что зелёное, что красное и почему), **Открытые
вопросы** (развилки, которые нельзя решать за пользователя), **Следующий шаг** (первое
действие при возобновлении). Секреты в файл не пишет — только пути/имена переменных. После
заполнения коммитит `handoff.md` в текущую ветку сообщением `docs: update handoff` и пушит
(контейнер эфемерный — без пуша изменения теряются).

**Триггеры:** `/handoff`, «сделай хендофф», «зафиксируй состояние перед паузой».

## 2. resume — поднять контекст и продолжить

**Краткое описание.** Читает `handoff.md`, прогоняет проверки, сверяет их с ожидаемым
состоянием, задаёт открытые вопросы и продолжает со «Следующего шага».

**Полное описание.** Читает `handoff.md` целиком (если файла нет — предлагает осмотреться
через `git log`/README). Затем: **(1)** прогоняет команды из раздела «Команды для проверки»
и сверяет с ожидаемым состоянием — всё сходится → фундамент надёжен; расхождение (сломалось
новое) → сначала чинит это, не строит поверх сломанного. **(2)** Если есть открытые вопросы,
требующие решения пользователя — задаёт их прежде чем продолжать. **(3)** Если зелено и
блокеров нет — приступает к «Следующему шагу». Кратко отчитывается: что показали проверки,
какие вопросы висят, с чего начинает. Пара к `handoff` (handoff пишет → resume читает).

**Триггеры:** `/resume`, «продолжаем», «возобнови работу».

## 3. wb-docs — чтение документации Wildberries (обход антибота)

**Краткое описание.** Заходит на портал документации WB (`dev.wildberries.ru`) настоящим
headless-Chromium в обход антибота, читает любую страницу API и освежает снимки лимитов/методов.

**Полное описание.** Страницы `dev.wildberries.ru` нельзя прочитать обычным `curl`/`fetch`/WebFetch
(антибот-челлендж + SPA, обычный запрос получает заглушку HTTP 498). Нужен реальный браузер —
поднимается скриптом `scripts/fetch-wb-docs.mjs`. Два препятствия уже решены в коде: **антибот**
`__wbaas/challenges/antibot` (проходит стелс-Chromium: реальный User-Agent, локаль `ru-RU`,
скрытый `navigator.webdriver`, паузы/движения мышью) и **MITM-прокси окружения** (рвёт TLS 1.3
из-за ECH → лечится понижением до TLS 1.2, включается автоматически при `HTTPS_PROXY`).

Запуск: `npm run docs:fetch -- <URL>` (в stdout), `node scripts/fetch-wb-docs.mjs <URL> <файл>`
(в файл), `npm run docs:limits` (снимок лимитов), `node scripts/refresh-wb-docs.mjs` (перечитать
всё из `docs/wb-api/pages.json`). Изученное лежит в `docs/wb-api/` (README, limits.md, снимки
методов). Клиент `lib/wbClient.js` соблюдает лимиты (token-bucket, чтение `X-Ratelimit-*`,
запрет ретраев на 4xx). Токен WB — персональный, имя `Wildberries_API`, достаётся резолвером
`lib/wbToken.js` (env → `.env`), значение никогда не печатается. Обязательное правило: перед
использованием нового метода API прочитать его страницу и взять его собственный лимит
(`methodLimit`) — он часто строже базового.

**Триггеры:** `/wb-docs`, «прочитай доку WB», «зайди на dev.wildberries.ru», «какой лимит
у метода WB», «обнови снимки WB».

## 4. wb-top-keywords — ТОП по ключевой фразе (MPStats)

**Краткое описание.** По ключевой фразе берёт всю поисковую выдачу WB из MPStats, прогоняет
через двухуровневую фильтрацию и отдаёт список конкурентов (nmId) + HTML-отчёт с фото и цветом.
Инструмент **[1]** каскада — кормит «Сравнение карточек».

**Полное описание.** Логика — `lib/wbTopKeywords.js`, CLI — `scripts/wb-top-keywords.mjs`
(`npm run top:keywords`), транспорт — `lib/mpstats.js`. Доступ: `MPSTATS_TOKEN`. Эндпоинт
залочен (`POST …/wb/search/items`), потолок выдачи — **~100 товаров на фразу**. Перед запуском —
обязательный предполётный диалог: фраза, период (пресет 7/30/90 или `d1`/`d2`), размер топа,
группы-признаки (`имя = стем1, стем2`, стемами без окончаний, соединяются ИЛИ), слова-исключения
(жёсткий гейт), ценовой коридор, опц. пороги. Фильтрация: отсев выручки → exclude (жёсткий гейт)
/ группы (ИЛИ) / «безхвостый» генерик остаётся если в ТОП-`exceptionRank` → метрические фильтры
→ сортировка по выручке → отсечка топ-N последним шагом.

Связка **[1]→[2]** — ручной выбор конкурентов (человек в цикле): прогнать с `--pick` (печатает
нумерованную таблицу), показать пользователю, он называет 2–4 конкурента, спросить наш артикул
(`--our`), передать в `wb-cards-compare`. Авто-топ-K (`--nmids-only | …`) — запасной путь для
явных «просто топ-N». HTML-отчёт самодостаточен (фото в data-URI). Контракт `top-rivals` —
в `docs/pipeline/README.md`.

**Триггеры:** `/wb-top-keywords`, «топ по фразе», «найди конкурентов по запросу», «кто в топе
выдачи WB», «собери артикулы по запросу».

## 5. wb-cards-compare — отчёт «Сравнение карточек» (кабинет WB)

**Краткое описание.** Строит отчёт «Сравнение карточек» в кабинете Wildberries (Аналитика
развития бизнеса) через headless-браузер с сессией пользователя. UI-функция Джема — **в API её нет**.

**Полное описание.** Логика — `lib/wbCardsCompare.js`, CLI — `scripts/wb-cards-compare.mjs`.
Страница: `seller.wildberries.ru/platform-analytics/cards-comparison`. Порядок: **(1)** спросить
наш артикул (`nmID`) — всегда даёт пользователь; **(2)** конкуренты 0–4 шт. (явно или из [1]
ручным выбором), всего 2–5 карточек; **(3)** проверить сессию `npm run cabinet:check`;
**(4)** DRY-RUN (`npm run cards:compare -- --our N --rivals …`) — добавляет артикулы, показывает
скрин `.secrets/cmp-filled.png` «N из 5», лимит НЕ тратится; **(5)** после подтверждения `--submit`
(тратит 1 сравнение, тариф «Продвинутый» ≈ 20) + автовыгрузка XLSX. Готовое сравнение живёт 72 ч
и пере-скачивается бесплатно (`--export-existing`).

Сессия (`lib/wbCabinet.js`): куки (`WB_COOKIES` / `.secrets/wb-cookies.json`) + **localStorage-токен**
(`wb-eu-passport-v2.access-token` — токен в localStorage, НЕ в куках; нужны оба набора). Если
сессия протухла (`SESSION_EXPIRED`) — остановиться и попросить у пользователя свежие креды
(экспорт кук + записи localStorage). Файлы `.secrets/*` — gitignored, значения не логируются.

**Триггеры:** `/wb-cards-compare`, «сравни карточки», «сравнение карточек WB», «сравнить наш
товар с конкурентами».

## 6. wb-competitor-analysis — конкурентный анализ ниши → план доработки

**Краткое описание.** Конкурентный анализ ниши/карточки WB по методике из базы знаний
(MPStats + ручной слой). Строит многоблочный отчёт (ёмкость, ТОП-конкуренты, цена×юнит-экономика,
цвета, контент-бенчмарк, принадлежность признаков, сезонность, гэп-анализ) и план доработки карточки.

**Полное описание.** Движок — `.claude/skills/wb-competitor-analysis/wb_analyze.py` (Python).
Референсы — `references/analysis-workflow.md` (пошаговая процедура + шаблон плана) и
`references/mpstats.md`. Первоисточник — главы базы знаний 04, 13, 18, 05, 19. Работает в два
слоя: **A (авто)** — ёмкость ниши, ТОП-конкуренты, цена×юнит-экономика, доминирующие цвета,
контент-бенчмарк, смыслы/характеристики, принадлежность признаков (F3, ≥30% = обязателен),
сезонность, гэп-анализ (`--my-sku`); **B (ручной)** — конверсии в корзину/заказ, инфографика
(Wildbox/Gem/визуально), движок размечает как задачи.

Доступ: `MPSTATS_TOKEN` + публичный API WB. Перед запуском спрашивать **себестоимость**
(`--cost`, разная у каждого товара) и **наш артикул** (`--my-sku`, для гэп-анализа). Юнит-экономика
на подтверждённых дефолтах (комиссия 35,7% от цены без СПП; эквайринг/налог/ДРР от цены с СПП;
брак от себестоимости). Два режима: **категорийный** (ниша из MPStats по пути) и **каскадный**
`[1]→[2]→[3]` (ниша из `--items-json`, воронка из `--funnel-json`; `--foreign` — чужой артикул
без воронки [2]). Проще всего — через оркестратор `npm run pipeline`. Отчёт — разделы A–H
(H = план доработки), HTML (`--html-out`) / PDF (`--pdf-out`, кликабельные ссылки) / JSON.

> **Расхождение версий было устранено при консолидации:** взята версия из ветки `stoic-cannon-2weadk`
> — новее версии `magical-bardeen` на 12 коммитов (режим `--foreign`, блок F3, компактный A4-PDF и др.).

**Триггеры:** «конкурентный анализ», «разбери нишу X», «топ-N продавцов/брендов», «что улучшить
в карточке/артикуле», «кто лидеры по выручке».

## 7. wb-brand-keyword-sales — анализ своих товаров по ключевым запросам

**Краткое описание.** Отчёт по ФАКТИЧЕСКИМ выкупам наших брендов из личного кабинета WB,
сгруппированный по ключевым фразам и периодам (штуки + сумма) → PDF.

**Полное описание.** Логика — `lib/wbBrandKeywordSales.js`, продажи — `lib/wbSales.js`, PDF —
`lib/htmlToPdf.js`, CLI — `scripts/wb-brand-keyword-sales.mjs` (`npm run sales:by-keyword`).
Токены: `MPSTATS_TOKEN` (выдача по фразе) + `Wildberries_API` (продажи из кабинета). Алгоритм:
**(1)** для каждой фразы берёт выдачу WB из MPStats, оставляет карточки наших брендов → наши nmId;
**(2)** по nmId тянет `POST /api/v1/supplier/sales` (WB Statistics); **(3)** агрегирует по фразе×периоду:
«выкуп» = `saleID` вида **S** (оплачен, не возвращён), возвраты (`R`) считаются отдельно; сумма —
`finishedPrice` или `forPay`; **(4)** отчёт → PDF/HTML/JSON.

⚠️ **Критично:** метод `/supplier/sales` — **1 запрос/мин без запаса**, `pullSales` держит паузу
66 с между страницами; отчёт за полгода = 2–4 минуты, это нормально. **Дедуп только по `saleID`,
не по `srid`** (srid — идентификатор заказа, дедуп по нему теряет строки/возвраты). Оговорки для
пользователя: **атрибуции к запросу нет** («по запросу» = наши товары в выдаче по фразе, а не
«сколько принёс запрос»); потолок выдачи MPStats ~100 товаров; выкупы валовые (возвраты отдельно).

**Триггеры:** `/wb-brand-keyword-sales`, «сколько мы продали по запросу», «продажи наших брендов
по фразе», «отчёт по выкупам наших товаров».

## 8. wb-brand-market-share — доля бренда от рынка по фразе (MPStats)

**Краткое описание.** По паре БРЕНД + фраза строит отчёт о доле бренда в нише за 30 и 90 дней:
общая информация (доля в штуках и выручке, ранг среди брендов), ТОП рынка по фразе и топовые
артикулы бренда → HTML + компактный A4 PDF.

**Полное описание.** Логика и рендер — `scripts/brand-share.mjs` (`npm run report:brand-share`),
транспорт — `lib/mpstats.js`. Доступ: `MPSTATS_TOKEN` (+ Chromium/Playwright для PDF). «Весь рынок»
= вся выдача WB по фразе (метод «Товары по поисковой фразе»). Каждый отчёт: **(1)** общая информация
по бренду (доля в штуках и выручке, продажи, выручка, число карточек в выдаче, ср. цена, ранг среди
брендов, итог по нише); **(2)** ТОП-10 рынка по фразе (строки бренда подсвечены, сортировка по
выручке); **(3)** до 15 артикулов бренда по выручке с колонкой «Доля рынка». Блок за 30 дней,
затем период 90 дней с новой страницы в PDF. `--target "БРЕНД|фраза"` (повторяемый).

Оговорки: MPStats отдаёт ~100 карточек на фразу (доля/ранг — внутри выдачи); данные оценочные
(для ФАКТИЧЕСКИХ выкупов — скилл `wb-brand-keyword-sales`). Смежные инструменты того же движка:
`scripts/phrase-probe.mjs` (подбор фраз по ёмкости), `scripts/brand-top20.mjs` (ТОП-20 брендов ниши).

**Триггеры:** `/wb-brand-market-share`, «доля рынка бренда по фразе», «сколько занимает бренд
в нише запроса», «отчёт по доле бренда».

## 9. wb-unit-calc — юнит-калькулятор товара на WB

**Краткое описание.** Считает юнит-экономику товара на единицу (раскладка, ценовой коридор под
целевую маржу, точка безубыточности, обратный расчёт цены, чувствительность) → HTML/PDF.
Есть Telegram-бот с пошаговым вводом.

**Полное описание.** Логика — `lib/wbUnitCalc.js`, CLI — `scripts/wb-unit-calc.mjs`
(`npm run unit:calc`). То же ядро, что в блоке C конкурентного анализа. Модель (не менять без
запроса пользователя): две цены — `S` продавца без СПП (база маржи и комиссии) и `P` покупателя
с СПП (`P = S·(1−СПП)`). Комиссия ВБ 35,7% от `S`; эквайринг 4,7% / налог 2% / ДРР 30%(запуск)/8%(выход)
от `P`; брак 2,5% от себестоимости; логистика/хранение индивидуальны. Себестоимость `C` — **спрашивать
каждый раз** (дефолта нет). Цена: `--price` (с СПП), `--seller-price` (без СПП) или `--nm` (подтянуть
по артикулу из MPStats). Выдаёт: раскладку на единицу, ценовой коридор + безубыточность, обратный
расчёт под маржу/прибыль, таблицы чувствительности, прогноз за период (`--units`).

**Telegram-бот** (`npm run unit:bot`): тот же калькулятор в личке — пользователь вводит данные
сообщениями, бот присылает разбор + кнопки (Цена под маржу / Изменить ДРР / PDF / Новый расчёт).
Логика — `lib/wbUnitBot.js` (чистый reducer), клиент — `lib/telegram.js`, раннер —
`scripts/wb-unit-bot.mjs`. Транспорт long-polling (публичный URL не нужен), `TELEGRAM_BOT_TOKEN`
+ опц. `TELEGRAM_ALLOWED_CHAT_IDS`. Эталон проверки: `--cost 536 --price 2400` → прибыль 705 ₽,
маржа 28%, коридор 2094–2613 ₽, безубыточность 1051 ₽.

**Триггеры:** `/wb-unit-calc`, «юнит-экономика», «посчитай маржу/прибыль», «какая цена под
маржу X», «точка безубыточности», «юнит-бот в телеграм».

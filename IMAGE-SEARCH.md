Первая цель — женские рубашки из марлевки/муслина, оверсайз.

### Карточка и фото

Фото и характеристики берутся напрямую с CDN по nmId, без браузера и
без парсинга страниц. Шард `basket-NN` подбирается перебором.

```
https://basket-{NN}.wbbasket.ru/vol{nm/100000}/part{nm/1000}/{nm}/info/ru/card.json
https://basket-{NN}.wbbasket.ru/vol{nm/100000}/part{nm/1000}/{nm}/images/{size}/{n}.webp
```

| Размер | Пиксели | Токенов на изображение |
|---|---|---|
| `c246x328` | 246×328 | ~108 |
| `c516x688` | 516×688 | ~473 |
| `big` | 900×1200 | ~1440 |

`card.json` бесплатно отдаёт структурированные характеристики. Пример живой
карточки: `Состав: хлопок; марлевка`, `Покрой: оверсайз`, `Вид застежки:
пуговицы`, `Тип карманов: без карманов`, `Фактура материала: полупрозрачная`,
`Пол: Женский`.

⚠️ **`search.wb.ru` отдаёт 429** — поисковую выдачу парсить нельзя, источник
списка только MPStats.

### Локальные модели на Mac Mini (M4, 16 ГБ)

Замерено `scripts/local-vlm-bench.py` на размеченном наборе из 6 карточек.

| Модель | Гейт | Разбор | с/карточку | Вердикт |
|---|---|---|---|---|
| **`gemma3:12b`** | **100 %** | 62 % | 8,1 / 17,3 | **гейт — да, разбор частично** |
| `gemma3:4b` | 20 % полноты | 55 % | 5,1 / 9,8 | не годится |
| `qwen-vision:3b` | константы | 36 % | 3,8 / 2,5 | не годится |

**Гейт решён локально.** `gemma3:12b` после `ollama pull` (в прежнем теге не
было vision-проектора — отсюда `HTTP 500: this model is missing data required
for image input`) даёт на гейте 6 из 6: пять рубашек как `shirt`, блузка со
стойкой и V-вырезом как `blouse_non_shirt`. Полнота 100 %, ложных пропусков 0.
Предупреждение детектора про константный `photo_usable=true` здесь ложное:
все шесть фото действительно пригодны, и `garment_type` при этом различается.

**Размер фото на скорость не влияет.** Замерено: 8,1 с/карточку и на
`c516x688` с `num_predict 400`, и на `c246x328` с `num_predict 60`. Gemma 3
приводит любое изображение к фиксированным 896×896 своим энкодером (256
токенов на кадр), поэтому наш размер меняет только трафик. Узкое место —
не генерация, а обработка изображения.

**Каждое лишнее поле в схеме стоит точности на остальных.** Добавление
`body_length` и `shoulder` (веса 3 и 2) обрушило манжету с 6/6 до 1/6 и
уронило общий результат с 62 % до 47 %. Схема разбора сокращена до четырёх
признаков, которые модель берёт уверенно: воротник, длина рукава, манжета,
рисунок. Длина изделия и линия плеча идут в `unknown` и выбывают из
знаменателя — 5 баллов не стоят потери 20.

**Разбор — 62 %, но цифра обманчива.** По атрибутам:

| Атрибут | Верно | Замечание |
|---|---|---|
| `cuff` | 6/6 | признак, которого я больше всего опасался |
| `pattern` | 6/6 | |
| `sleeve_length` | 5/6 | |
| `collar` | 4/6 | вес 13, главный кандидат на арбитраж |
| `fabric_texture` | 4/6 | **берётся из текста, зрению не нужен** |
| `fit` | 3/6 | **берётся из текста, зрению не нужен** |
| `hem` | **0/6** | константа `straight` на всех карточках |

Общие 62 % занижены тем, что в наборе были признаки, которые надёжнее берутся
из характеристик. Схема разбора сужена до шести признаков, которых в тексте
нет: воротник, длина рукава, манжета, рисунок, длина изделия, линия плеча.

`hem` из зрения исключён совсем: модель отвечает `straight` на все карточки
подряд, включая явно закруглённые, и это стоило бы штрафа −5 на каждой. При
политике `redistribute` его вес 8 просто выбывает из знаменателя.

**Не годятся:** `gemma3:4b` не видит центральную планку — при определении
«shirt» через планку она отсеяла четыре целевые карточки из пяти.
`qwen-vision:3b` выдаёт один и тот же ответ независимо от изображения.

Отдельное наблюдение: **JSON Schema снизила точность 4B с 67 % до 55 %**.
Схема убрала невалидные значения и пропуски полей, но точность упала —
вероятно, ограниченное декодирование фиксирует первый допустимый токен
раньше, чем модель разберёт изображение. Гипотеза, не доказанный факт.

### Текстовый слой — измеренное покрытие

Замерено `scripts/wb-card.mjs --fields` на 60 карточках топа категории
(прочитано 57 из 60).

| Поле | Заполнено | Значения |
|---|---|---|
| Состав | **100 %** | хлопок; марлевка / хлопок 100% / вискоза |
| Покрой | **100 %** | оверсайз / свободный / прямой / приталенный |
| Пол | **100 %** | Женский / Девочки |
| Вид застежки | 88 % | пуговицы / завязки / без застежки |
| Тип карманов | 79 % | без карманов / накладные / в шве |
| Фактура материала | 79 % | полупрозрачная / плотная |
| Вырез горловины | 21 % | V-образный / отложной воротник |
| Тип рукава | **7 %** | 3/4 |

Отсюда следует главное: **два самых весомых признака профиля берутся из
текста на каждой карточке.** Ткань (вес 20) — из поля «Состав», где марлевка,
муслин и жатка называются прямым текстом. Силуэт (вес 14) — из поля «Покрой»,
заполненного у 100 % карточек. Это ровно те два атрибута, на которых
`gemma3:4b` ошибалась чаще всего.

Итого 34 балла из 100 закрываются бесплатно и надёжнее, чем зрением.
Зрению остаются воротник (13), низ (8), манжета (7), рукав (7), длина (3) —
около 38 баллов.

Оговорки: значения заявлены продавцом и должны сверяться со зрением там, где
это возможно; расхождение фиксируется в отчёте. Правило отсева по «Тип рукава»
почти не сработает — поле заполнено лишь у 7 %.

## Архитектура конвейера

```
ключевая фраза → категория MPStats → топ-N по выручке за 90 дней
   ↓
S0  card.json: характеристики + photo_count                    бесплатно
   ↓ жёсткий отсев только по трём однозначным полям
S1  pHash по первому фото → дедуп                              бесплатно
   ↓
S2  ГЕЙТ: gemma3:12b локально, 1 фото — полнота 100 %         бесплатно
   ↓ ~20–25 %
S3  РАЗБОР: gemma3:12b, 2-3 фото 516×688, шесть признаков      бесплатно
        ткань/силуэт/карманы приходят из текста, hem исключён
   ↓
S4  СКОРИНГ КОДОМ: гейты → веса → штрафы → бэнды               бесплатно
   ↓ серая зона ~3 %
S5  АРБИТРАЖ: 3 фото big, только спорные пункты                сессия / API
   ↓
S6  джойн с MPStats (цена, продажи, отзывы) → CSV / PDF
```

### Правила, которые нельзя нарушать

**Балл считает код, а не модель.** Модель отвечает только на атомарные
вопросы с закрытым списком значений. Проценты, выданные LLM, плохо
откалиброваны и плывут между прогонами.

**Гейт настроен на полноту, не на точность.** Пропустить лишнюю карточку
стоит цент на следующей ступени; выбросить нужную — потерять её навсегда
и не узнать об этом.

**Название и описание карточки ничего не отсекают.** Продавцы пишут
недостоверно: в описании эталонной карточки значится «рукава фонариками»,
хотя на фото обычный рубашечный рукав. Текст используется только для
приоритета очереди и как контекст, помеченный «заявлено продавцом».

**Отсев по характеристикам — только три поля:**

| Поле | Значение → отсев |
|---|---|
| Пол | Мужской, Для мальчиков |
| Вид застёжки | молния, без застёжки, завязки |
| Тип рукава | короткий, без рукавов |

Отсутствие поля — это `unknown`, никогда не основание для отсева.
Каждый отсев логируется с полем и значением.

## Профиль эталона: что править

Файл профиля (`target_womens_shirt_visual_profile.json`) хорош, но требует
шести правок до кодирования.

1. **Ключи весов не совпадают с ключами атрибутов** — `product_type` против
   `category`, `fabric_visual_properties` против `fabric`. Нужен маппинг.
2. **`shoulder` и `transparency` веса не имеют вообще**, хотя влияют на вердикт.
3. **Семь `hard`-гейтов дадут пустую выдачу.** `hem` и `cuffs` не видны на
   большинстве фото, а правило `partial_visibility` велит ставить `unknown`.
   Что делать с `unknown` на жёстком гейте — в профиле не сказано.
   **Предложение: hard оставить только `category`, `collar`, `front_closure`.**
4. **Противоречия** — `pattern` имеет importance 0.6 при весе 0; `sleeves`
   помечен `hard`, но в `negative_criteria` его штраф лишь `high`.
5. **Нет политики `unknown`.** Предложение: перераспределять вес между
   видимыми признаками, а карточку с более чем двумя `unknown` помечать
   флагом «низкая наблюдаемость».
6. **Нет порога отсечки.** Предложение: ≥80 — основной список, 70–79 — «посмотреть».

**Все шесть правок внесены в `lib/visualProfile.js`.** Штрафы взяты строго из
`negative_criteria` исходного профиля (very_high → 10, high → 5, medium → 2);
ткани и рисунка в том списке нет, поэтому для них наказание — только потеря
веса, второй раз не бьём. Добавлен `shoulder` с весом 2 (в исходном профиле
у него была importance 0.85 и ни одного балла), вес `product_type` снижен
с 12 до 10, чтобы сумма осталась 100.

### Перевес

Веса должны отражать **разделяющую силу признака внутри категории**, а не
важность «вообще». В категории «Рубашка» почти у всех товаров отложной
воротник и сквозная застёжка — эти признаки не несут информации, но держат
27 баллов. Реально делят нишу ткань и рисунок.

Доказательство: атласная рубашка nm 608341673 совпадает с эталоном по всей
конструкции и отличается только тканью. При весе ткани 8 она наберёт ~92 и
попадёт в «очень близкие аналоги», хотя это совсем не тот товар.

## Ограничения, о которых надо помнить

- Первое фото карточки часто инфографика с надписями поверх товара.
  Поэтому берём 2–3 кадра и просим модель помечать непригодные.
- Признак, закрытый позой или кадрированием, — это `unknown`, а не «нет».
  Локальные модели это правило нарушают, платные соблюдают.
- Состав ткани по фотографии достоверно не определяется. Оценивается только
  визуальное сходство фактуры; фактический состав берётся из характеристик.
- Mac Mini общий. Полный прогон запускать в тихое время, модели выгружать
  после работы (`keep_alive: 0`), тяжёлые модели — с оглядкой на своп.

## Память на Mac Mini: почему тормозит и что с этим делать

12B-модель занимает около 9 ГБ из 16. После долгого прогона машина уходит в
своп, и страдают соседние службы. Меры, в порядке эффективности.

**1. Кластеры с выгрузкой — основное решение.** `scripts/vision-run.mjs`
обрабатывает карточки пачками (по умолчанию 25), после каждой выгружает
модель (`keep_alive: 0`), ждёт, пока своп опустится ниже порога, и только
потом берёт следующую. Побочная польза — контрольные точки: десятичасовой
прогон можно прервать и продолжить с `--resume`, причём карточки, упавшие
по ошибке, повторяются, а успешные пропускаются.

```
node scripts/vision-run.mjs --stage gate --top 500 --cluster 25
node scripts/vision-run.mjs --stage gate --top 500 --resume
```

Параметры порогов: `--min-free 3` (ГБ свободной памяти), `--max-swap 3072`
(МБ свопа), `--cool 5000` (пауза после выгрузки). Если за две минуты память
не восстановилась, прогон останавливается сам — значит машину занял кто-то
ещё, и продолжать опасно.

**2. Контекст вместо квантования.** `num_ctx` снижен с 4096 до 2048: одна
картинка это 256 токенов, промпт около сотни, ответ до 200 — 2048 хватает с
запасом, а KV-кэш при этом вдвое меньше. Это дешевле по качеству, чем менять
квант.

**3. Квантование — крайняя мера.** Текущий тег `gemma3:12b` это Q4_K_M,
8,1 ГБ. Более низкие кванты (`q3_K_M`, около 6 ГБ) экономят 2 ГБ, но точность
разбора и так пограничная — 62 %, и её падение обесценит всю ступень. Если
памяти совсем не хватает, правильнее уменьшить кластер до 10 карточек, чем
ронять квант.

**4. Приоритет процесса.** Запуск через `nice -n 10 node scripts/vision-run.mjs …`
отдаёт процессорное время живым службам. На память это не влияет, но
отзывчивость планировщика и калькулятора сохраняет.

**5. Разовая уборка после прогона.**

```
ollama stop gemma3:12b
ollama ps
sysctl vm.swapusage
```

Своп сам не сжимается — он освободится по мере того, как система вернёт
страницы. Если `ollama ps` пуст, а машина всё ещё вялая, это остаточный
своп, и он рассосётся за несколько минут.

## Форма запроса влияет сильнее, чем изображение

Замер, который это показал. Один и тот же набор карточек, одна модель,
`temperature 0`, повторный прогон даёт те же цифры до десятых — то есть
результат детерминирован. Меняется только состав полей в схеме:

| Схема разбора | `cuff` (манжета) |
|---|---|
| 8 полей: collar, sleeve, fit, cuff, hem, pocket, fabric, pattern | **6/6** |
| 6 полей: collar, sleeve, cuff, pattern, body_length, shoulder | 1/6 |
| 4 поля: collar, sleeve, cuff, pattern | 1/6 |

Признак, который не трогали, обвалился с 6/6 до 1/6 из-за соседей по схеме.
Значит модель отвечает не независимо по полям: предыдущие решения смещают
последующие, а ограниченное декодирование не даёт передумать.

Отсюда три режима в `scripts/local-vlm-bench.py`, которые надо сравнить
на одном наборе:

| Режим | Флаг | Идея |
|---|---|---|
| Все признаки разом | по умолчанию | как сейчас, база для сравнения |
| По одному признаку | `--one-by-one` | отдельный запрос на каждый признак, прицельный промпт, никаких соседей |
| С полем наблюдения | `--observe` | один запрос, но перед значениями идёт свободное поле `observation` — модель успевает описать увиденное до того, как схема заставит выбрать |

### Результат сравнения

| Режим | Точность | с/карточку |
|---|---|---|
| Все признаки разом | 62 % | 14,6 |
| С полем `observation` | 58 % | 16,8 |
| **По одному признаку** | **75 %** | **17,1** |

**Победил режим «по одному».** Воротник — самый дорогой зрительный признак,
вес 13 — вырос с 4/6 до 6/6. Опасение про время не подтвердилось: 17,1 с
против 14,6, а не 35. Ollama переиспользует уже обработанное изображение
между запросами с одинаковым префиксом, поэтому семь вопросов стоят почти
как один.

Режим `observation` отвергнут: 58 %, и `sleeve_length` стал константой —
свободное поле впереди дало модели «уговорить себя» вместо того, чтобы
смотреть.

**Попытка вернуть выброшенные признаки — проверена и частично отвергнута.**
Гипотеза была: раз признаки больше не мешают друг другу, можно вернуть низ,
длину изделия и линию плеча. Расширение с четырёх вопросов до семи дало 62 %
вместо 75 %, и разбор по признакам показал, почему:

| Признак | Верно | Решение |
|---|---|---|
| `collar` | 6/6 | оставлен |
| `sleeve_length` | 5/6 | оставлен |
| `shoulder` | 5/6 | **добавлен — работает** |
| `pattern` | 5/6 | оставлен |
| `body_length` | 3/6 | выброшен |
| `cuff` | 2/6 | оставлен, но откалиброван |
| `hem` | 1/6 | **выброшен окончательно** |

Четыре прежних признака дали ровно те же 75 % — просадка целиком от трёх
добавленных. Вывод: режим «по одному» убирает взаимное влияние признаков,
но не лечит признак, который модель просто не берёт. Низ остался константой
`straight` при любой формулировке промпта, включая прицельную с явным
описанием рубашечной дуги. Он исключён насовсем; его вес 8 выбывает из
знаменателя по политике `redistribute`.

Итоговый набор — пять вопросов: воротник, длина рукава, манжета, рисунок,
линия плеча.

**Калибровка ненадёжных ответов.** Модель отвечает `cuff='folded'`, когда не
может разобрать манжету: на размеченном наборе это значение встретилось
четыре раза и все четыре раза было неверным, верных `folded` не было ни
одного. В `lib/visualScore.js` такой ответ приводится к `unknown` — иначе
карточка получает штраф за то, что модель не разглядела деталь. Список
таких значений (`UNRELIABLE`) пересматривается при смене модели или промпта.

Остаточная проблема — манжета: модель отвечает `folded` почти всегда.
Отчасти это моя разметка: на муслиновой карточке рукава действительно
подвёрнуты, и `folded` там вернее моего `unknown`. Но систематичность
ответа настораживает, и манжету стоит перепроверить на большем наборе.

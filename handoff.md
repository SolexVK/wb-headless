# Handoff

## Цель
Два направления в одном проекте:
1. **Дашборд динамики остатков** из выгрузки «Остатки по дням» —
   `analytics/inventory-dashboard/build_dashboard.py` (готово).
2. **Сводка по остаткам WB на текущий момент** (FBO/FBS + в пути + возвраты) по
   каждому артикулу продавца — из официального API WB. Сервис (CLI+эндпоинт) +
   Excel. Коммит `d25de0d`.

## Что пробовали и НЕ сработало
- **Пересчёт формул через headless LibreOffice (`xlsx/scripts/recalc.py`) НЕ работает
  в этой среде.** Виснет и отваливается по таймауту даже на файле из 3 ячеек (пробовали
  80/100/280/300 с — всё timeout). Причина: `recalc.py` запускает `soffice` дважды
  (установка макроса в профиль + запуск), и каждый раз медленно бутстрапит свежий
  профиль в песочнице (AF_UNIX под LD_PRELOAD-шимом). Прямой `soffice --convert-to`
  стартует, но полноценный recalc-макрос не доходит. **Обход:** не полагаться на
  headless-recalc; поставить `wb.calculation.fullCalcOnLoad=True`, чтобы Excel/
  LibreOffice сами пересчитали при открытии, а числа независимо сверить через pandas.
  → При возобновлении НЕ тратить время на recalc.py, он тут не поедет.
- **Первая версия грузила ~2000+ живых `SUMIF` на сводных листах** (166+149+14 ключей
  × 7 дней) — книга становилась неподъёмной для любого пересчёта. Отсюда решение
  считать сводные листы значениями в Python, оставив живые формулы только на дашборде.
- **Грабли со смещением столбцов при верификации:** на сводных листах дни начинаются
  с колонки **C** (ключ в B), а не с D. Первый проверочный скрипт читал с D и дал
  ложное «не сходится». Правильно: дни в колонках C..(C+NDAY-1), Изм. и % — следом.
- `openpyxl`/`pandas` в системном python отсутствовали — ставили через `pip install`
  (не в venv, среда эфемерная — при новой сессии поставить заново).

## Открытые вопросы (нужно решение пользователя)
- **Первый живой прогон сводки WB** — токен ищется автоматически
  (`lib/resolveWbToken.js`: env / похоже-названная env-переменная / .env /
  файл / macOS Keychain), вписывать руками не нужно. На маке: `npm run wb-stock`.
  В Actions: секрет репозитория `WB_API_TOKEN` + workflow «Отчёт — остатки WB».
  До живого прогона код не проверен против реального API; на первом запуске
  сверить имена полей ответа WB и при расхождении поправить нормализацию в
  `lib/wbApi.js`. Если токен назван нестандартно и не под паттерн WB…TOKEN —
  резолвер его не найдёт (напечатает список проверенных мест). ЖДУ ПРОГОНА.
- **FBS-баркоды**: полнота остатков FBS зависит от Контент-API (список баркодов).
  Если категории «Контент» нет — список берётся из ответа FBO, товары «только FBS,
  никогда не было на FBO» могут не попасть. Решение — дать токену «Контент».
- **Вкладка с разбивкой по размерам для выбранного артикула** — пользователю предложено,
  ответа пока нет. Сейчас размеры полностью консолидированы; если нужна детализация —
  это отдельный лист/режим. НЕ реализовывать без запроса. (не блокер)
- **Показатель «расход/продажи за период» (снижение остатка)** — предложен как возможное
  улучшение, решение за пользователем. (не блокер)
- **Коммитить ли готовые .xlsx / сырые данные в репозиторий** — сознательно НЕ коммитили
  (коммерческие данные пользователя, и это не код). Если нужно хранить артефакты в репо —
  требуется явное согласие. ЖДУ ОТВЕТА при необходимости.

## Следующий шаг

`WB_API_TOKEN=xxx npm run report:wb-stock`, сверить, что поля ответа WB совпали с
ожиданиями `lib/wbApi.js` (особенно `/api/v1/supplier/stocks`, пагинация карточек,

поправить нормализацию в `lib/wbApi.js` (агрегатор `lib/wbStockSummary.js` трогать не
нужно). Про recalc.py помнить — в этой среде не работает, полагаться на `fullCalcOnLoad`.

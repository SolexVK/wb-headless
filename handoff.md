# Handoff — planner / Этап 3 (остатки, неттинг, план по цветам/размерам/партиям)

Ветка: `claude/production-plan-twv8ki` · репо `solexvk/wb-headless` · приложение в `planner/`.
Билд на конец сессии: **`jit-snapshot-2026-08-25`** (APP_BUILD в `public/app.js`, BACKEND_BUILD в
`server.js` — держим равными; бампаем вместе с каждой правкой).
Деплой у пользователя: Mac mini, порт 8477, supervisor поднимает заново.

## Цель
SPA планирования пошива одежды под Wildberries. Пользователь ведёт сезонный план: прогноз спроса
(«Ранг сезонности», MPStats) → план по цветам/размерам → довозы (партии-поставки со сроком WB) →
вычет реальных остатков (WB FBW/FBS, в пути, склад, производство) → раскладка нетто по цехам →
диаграмма Ганта → выгрузка листов в Excel для цеха. Цель — шить только нужное, вовремя, комфортными
партиями (настил), ничего не теряя.

## Текущее состояние
Всё, сделанное в этой сессии, задеплоено пользователем по ходу (кроме последнего билда — просил
задеплоить). Работает и подтверждено:
- WB-остатки FBW+FBS по nmID; привязка загрузкой таблицы номенклатур; неттинг (живой слой).
- Тумблер «Спрос (брутто) / К производству (нетто)»; Excel = НЕТТО (за вычетом остатков).
- Дробление крупных довозов на равные партии ≥ `batchSize` (floor, не под порог); раскладка по цехам.
- Нумерация произв. партий `prodNo` по (цех×артикул); на Ганте артикул крупно жёлтым + `пN`.
- `sewNotBefore`, `colorAdjust` (±% по цвету), `sizeAdjust` (±% множитель доли размера по цвету) + `sizeTarget` (точный % размера по цвету, для любых вкл. нулевые), `forceSizes`,
  `forceShare` (целевой % размера), `excludedColors` (✕), `forecastBuyoutPct` (заказы→выкупы).
- **Слияние довозов между собой УБРАНО** (было forward→backward→off): нетто[довоз] ≤ спрос[довоз]
  по построению, объём между довозами НЕ переносится. `minBatch` теперь только для СБОРКИ плана
  (объединение соседних МЕСЯЦЕВ в довоз по брутто, ДО вычета остатков).
- **Непокрытый спросом «хвост» размеров** (спрос вне ряда): настройка `tailToExtremePct` (0..100,
  деф. 50) — часть на крайний размер по направлению, остальное пропорционально по ряду.
- **Лог расчёта** (кнопка «⤓ Лог расчёта» на «Плане по размерам»): пошагово прогноз→цвета→размеры→
  примирение→ОСТАТКИ(матрица цвет×размер+источники)→брутто→вычет→нетто→Excel→сверка итогов.
- **Размерный ряд редактируется вручную** (Данные → артикул → «Размерный ряд») — можно добавить свои
  размеры (5XL/6XL) или убрать; `a.sizes` НЕ перезаписывается подтяжкой номенклатуры/карточек.
- **Пошив не раньше — на каждую партию** (План по размерам → поле «Пошив не раньше», `partia.earliestStart`):
  дата, раньше которой конкретную партию не начинать шить. Планировщик берёт ПОЗДНЕЙШУЮ из
  `partia.earliestStart` и `article.sewNotBefore` (`esOf`). Аддитивное поле, поверх пер-артикульного окна.
- **Гант — ручная раскладка блоков (пер-батчевые пины)**: блок можно перетащить ОДНИМ движением и на
  другой ЦЕХ (по вертикали), и на другую ДАТУ (по горизонтали). Пишется пер-батчевый пин
  `state.batchPins["partiaId#batchIndex"] = { ws, cut }` (СТАБИЛЬНЫЙ ключ, не зависит от цеха/порядка).
  Планировщик: пин форсирует цех (перекрывает пер-довозный `workshopId`) и якорит дату кроя; участвует
  в ранжировании (`esOf` учитывает `pinCut`). Осиротевший пин (сменилось число батчей) игнорируется —
  аддитивно/неразрушающе. Эндпойнт `POST /api/pin` ({batchKey,ws,cut} | {batchKey,clear} | {pins} | {clearAll}).
  Кнопки на Ганте: «🧲 Уплотнить» (Вариант A — сохранить раскладку цех+порядок, убрать разрывы в днях:
  блоки встык, первый блок — якорь) и «↺ Сбросить раскладку» (снять все пины). Пиновый блок помечен 📌.
  Пин-цех перекрывает `allowedWorkshops` (перетащенный блок не «исчезает», даже если цех его не шил;
  фикс `gantt-pin-nodrop`). Плюс страховочный варнинг `kind:'unscheduled'`, если задание вообще негде.
- **Авто-синхронизация «Кто шьёт этот артикул»** (`gantt-autoallow`): при переносе блока в цех, который
  раньше не шил артикул, галочка этого цеха ставится сама; когда из цеха ушёл ПОСЛЕДНИЙ блок артикула —
  снимается. Зеркалит `article.allowedWorkshops` на фактическое размещение. Чтобы перетаскивание ОДНОГО
  блока не утащило другие батчи (каскад при расширении списка цехов), прочие батчи артикула
  «замораживаются» цех-пином на их текущий цех. Работает в `POST /api/pin` (ветка одиночного переноса);
  только для артикулов с ЯВНЫМ списком цехов — «любой цех» ([]) оставляем гибким. «Уплотнить» (bulk pins)
  этого не трогает.
- **Версии/резервные копии состояния** (Данные → «🗄 Версии»): именованные снимки в БД (таблица
  `state_snapshots`), восстановление; авто-снимок при старте сервера/перед сбросом/восстановлением
  (ротация 20). Данные и так в БД (`planner/data/planner.db`, gitignored) — обновление кода не трогает.

ЗАКРЫТО: нули в нетто у нишевых цветов (джинса/фисташка/шоколад/бордо) по XS/M/XL — это РЕАЛЬНЫЙ сток
(пользователь подтвердил, что остатки актуальны; джинса 654 при спросе 703 и т.д.). Неттинг верен, не
баг. Если снова всплывёт — вести к разделу ОСТАТКИ лога, вопрос уже решён.

Не тестируется в контейнере: WB/MPStats API (нет сети/токена). Остальное — `node --check` и
изолированные node-тесты (в /tmp scratchpad, зелёные).

## Что изменилось (по сути)
1. **MPStats «0 запросов»**: показываем реальную причину (HTTP 401/403/429) прямо в ошибке + подсказку.
2. **Настройка «Мин. партия»**: живёт на вкладке «Данные» (не в шапке-⚙-токене); деф. поднят до 5000.
3. **Партия ≥5000**: `minBatch` 2000→5000; дробление `floor` (равные части ≥ batchSize, не под порог).
4. **Слияние довозов**: forward давал нетто>спрос и смешивал сезоны/цвета (джинса «возвращалась»);
   backward перекладывал на первый довоз; ИТОГ — merge на уровне нетто **отключён** совсем.
5. **Кириллица в размерах**: «ХL» с кир. Х не маппился на XL (уходил в нормировку) — `latinizeSize`.
6. **Хвост размеров**: `tailToExtremePct`-сплit (деф.50) — XL не раздувается, XS/M поднимаются.
7. **Лог расчёта** + раздел ОСТАТКИ — доказал, что нули = реальный сток (не баг).
8. **Баг «бордовый»→«красный»**: 287 шт остатка бордо игнорировались; теперь отдельный канон «бордо».

## Что пробовали и НЕ сработало (грабли — читать внимательно)
- **Слияние мелких довозов — большие грабли, три итерации:**
  - forward (в следующий по сроку): нетто одного довоза превышал его спрос (8116 vs 6579), осенний
    сток утаскивался в зимнюю поставку (риск дефицита), в довоз подмешивались цвета соседа (джинса,
    выключенная чипом, «возвращалась»). Пользователь справедливо назвал это ошибкой.
  - backward (в предыдущий): раздутие переезжало на ПЕРВЫЙ довоз (та же проблема, просто в начале).
  - ИТОГ: merge на уровне нетто **отключён** (`supplyMerges = []`). Инвариант нетто ≤ спрос важнее
    «партии ≥5000». Комфорт настила даёт только дробление КРУПНЫХ довозов. **Не возвращать merge
    без явной просьбы.**
- **Extreme-routing «весь хвост на XL»**: раздувал XL до ~30%, XS/M тонкие. Заменено на
  `tailToExtremePct`-сплит. Пользователь дважды переформулировал — итог: настройка 0..100, деф.50.
- **«Нули в нетто = баг расчёта»** — НЕ баг. Много кругов ушло на объяснение брутто-vs-нетто.
  Развязка — раздел ОСТАТКИ в логе: сток реален (джинса 654/703). Неттинг вычитает по ячейкам и не
  может выдумать сток. Одинаковый рисунок нулей — потому что у нишевых цветов малый спрос легко
  перекрывается стоком. **Если пользователь снова про нули — сразу вести к разделу ОСТАТКИ лога и к
  записи «В пути 2630».**
- **`sed` бампа билда промахивался**: server.js/app.js меняются «на диске» между шагами (билд-тег уже
  был другим). Всегда сначала `grep APP_BUILD/BACKEND_BUILD`, потом sed от АКТУАЛЬНОГО тега.
- **normColor цветов**: «бордовый»→«красный» (regex /бордов/ висел в группе красного). Аналогично
  возможны другие сюрпризы — при жалобе на «цвет не сопоставлен» проверять `normColor` в консоли.
- **Тест reconcilePlan**: colorRows.name должен быть КАНОН-цветом (`canonColor`), напр. «белый» →
  «белый/молочный», иначе матрица пустая. Кириллица в origin размеров тоже ломала (см. latinizeSize).

## JIT-раскладка (экономная, под оборачиваемость денег) — В РАБОТЕ
Цель собственника: не морозить деньги. Не шить всё рано (товар лежит готовым 3–7 мес), а «точно вовремя»:
финиш пошива к дате готовности = дедлайн ВБ − 1 мес (доставка+форс-мажор). Реперы = `partia.deadline`
(из ранга сезонности → план продаж по месяцам → даты завоза). Летние 005/006/007/014/022/032/033/034 —
весь объём дошить к 15.04, первые партии на ВБ раньше (старт продаж/раскрутка ТОП), зимой цеха заняты
летними. Не-летние: сток под ЗИМНИЕ продажи ДО летнего спринта → пауза → доотшив после 15.04, подушка
≥2 мес. Оборачиваемость: продажи 30–60 дн на ВБ + ткань/пошив/доставка.
- **Часть 1 (СДЕЛАНО, `jit-snapshot`)**: кнопка «⤓ Слепок раскладки» на Ганте → `exportLayoutSnapshotXlsx()`.
  Один лист, строка = артикул×цвет×партия: цех, крой/пошив/готовность, отгрузка/приход/дедлайн ВБ,
  «готово раньше дедлайна ВБ, дн», «пролежит до прихода ВБ, дн», опоздание, метка ЛЕТО. `SUMMER_ARTICLE_IDS`.
  Пользователь отдаёт файл Claude на анализ. Чисто клиентский экспорт (window.XLSX).
- **Часть 2 (task #10, НЕ начато)**: движок «Экономная раскладка (JIT)» — обратный расчёт от реперов,
  конечная ёмкость цехов, летний спринт приоритетом, не-летние с зимним стоком+паузой. Результат — пинами
  (`batchPins`, как «Уплотнить»), превью до/после, откат «Сбросить раскладку». Ждём слепок пользователя +
  подтверждение плана, потом строить. Параметры (подтверждены): буфер доставки 1 мес, летний финиш 15.04,
  подушка не-летних ≥2 мес + гарантия зимнего стока не-летних на время летнего спринта.

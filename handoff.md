## Цель
Раздел **«Ранг сезонности»**: по предмету WB собрать РЕЛЕВАНТНЫХ конкурентов-аналогов
(напр. именно МУСЛИНОВЫЕ женские рубашки, а не все подряд), построить ранг сезонности и
план продаж. Старый подход (плюс/минус-слова + строгий ключ + словарь признаков +
«неопределённые») пользователь признал **провалившимся**: фильтр резал не то и оставлял
нерелевантное. Нужен другой подход.

## Текущее состояние — ИДЁТ ПИВОТ (не закончен)
Старый фильтр (слова/признаки) — тупик, заменяется. Провели серию пробников на живом MPStats
и **нашли рабочий подход + уперлись в квоту**. Live-валидация нового пайплайна НЕ сделана
(MPStats заблокирован до 26.07, см. ниже). Боевой код начат (`wbKeywords.js`), UI ещё не трогали.

### Что выяснили пробниками (planner/tools/probe-search.mjs, (throwaway, в репо))
1. **Публичный поиск WB (`search.wb.ru`) отпал** — режет по HTTP 429 и с сервера, и с Mac mini
   (метит трафик как не-браузерный/не-резидентный). Не закладываться.
2. **`/wb/get/search`, `/wb/get/keyword`, `/wb/get/keywords`, `/wb/get/keywords/expanding|report`**
   в MPStats существуют, но формат недокументирован: search отдаёт 200 с ПУСТЫМ телом при любых
   параметрах (тупик); keywords требует `path`=категория и особый `filterModel` (наугад не подобрать,
   всегда 422 «Не корректные условия фильтра»). Забросили.
3. **РАБОЧИЙ ЭНДПОИНТ:** `GET /wb/get/item/{nmId}/by_keywords?d1=&d2=` → 200, поле `words` —
   ОБЪЕКТ `{ "фраза": { pos:[по дням], traffic_volume:[по дням], ... } }`. Это реальные поисковые
   фразы, по которым покупатели находят товар, с трафиком. **Идеальный дискриминатор:** муслиновая
   рубашка ранжируется по «муслиновая рубашка», льняная — по «льняная». Подтверждено на данных.
4. **Правило релевантности:** не «ранжируется хоть по одной целевой фразе» (даёт мусор: льняная
   рубашка цепляется за муслин-фразу с трафиком 178), а **доля целевого трафика ≥ порога**.
   При пороге ~20% отсекается лён/шёлк, остаётся чистый муслин. Порог — замена всем плюс/минус-словам.
5. **`/wb/get/category`** (POST, `path`, body `{startRow,endRow,sortModel:[{colId:'revenue',sort:'desc'}]}`)
   — до 5000 строк с дневными графиками за 1 запрос. Дешёвый, основной источник товаров и дневных данных.
6. **КРИТИЧНО — суточный лимит MPStats.** by_keywords тратит СУТОЧНУЮ квоту (1 запрос/товар).
   Пробник v7 (~900 запросов) её ВЫЖЕГ → `HTTP 429 "Превышен лимит запросов за 25.07.2026"`,
   после чего заблокированы И by_keywords, И category до след. суток. Скорость by_keywords ~0.12–0.14с/товар.
   Значит «by_keywords по всей категории» НЕ масштабируется — нужен экономный дизайн (см. ниже).

### Новый пайплайн (проектируется, частично написан)
```
1. category (1 запрос) → топ предмета по выручке + дневные графики
2. card.json (БЕСПЛАТНО, WB CDN, вне квоты) → название+описание+характеристики  [lib/season/wbCard.js]
3. ПРЕДФИЛЬТР по целевому слову в тексте карточки → сузить 900 → ~50–150 муслин-кандидатов (бесплатно)
4. by_keywords ТОЛЬКО по кандидатам → доля целевого трафика ≥ порога  [lib/season/wbKeywords.js — НАПИСАН]
5. Кэш by_keywords 30 дней (data/wb-cache/keywords/) → повторные отчёты почти бесплатны
6. Дневные данные из графиков категории → ранг + план (существующий движок seasonPlanReport)
```
UI резко упрощается: **предмет + целевые слова + порог доли + Построить**. Убрать: словарь
признаков, плюс/минус-чипы, «неопределённые», «строгий ключ» (mustHave). Добавить: прогресс % у кнопки.

## Что пробовали и НЕ сработало (важно!)
- **Старый фильтр слов/признаков** — провал по сути: плюс=«любое из» на 40 общих словах пропускает
  почти любую хлопковую рубашку; «муслин» вообще не был в плюсах; воронка по выручке вымывает нишу
  (муслин в длинном хвосте); минус-слово «прозрачная» выкидывало полупрозрачный муслин. Не возвращаться.
- **Публичный поиск WB** — 429 отовсюду (см. выше). Не использовать.
- **MPStats search/keywords по фразе** — формат не даётся (пустое тело / 422). Забросили в пользу by_keywords.
- **by_keywords по всей категории (сотни запросов/отчёт)** — выжигает суточную квоту за один прогон.
  Отсюда правило: предфильтр карточками (бесплатно) → by_keywords только по десяткам кандидатов + кэш 30д.
- **Пробник глотал ошибки как «нет данных»** — из-за этого 52% фейлов в v7 выглядели как «у товаров нет
  ключей», а на деле это был rate-limit/лимит. Мораль: в боевом коде РАЗЛИЧАТЬ 429-лимит / пусто / сбой
  (сделано в wbKeywords.js: DailyLimitError vs null).
- **Grale деплоя (в силе):** после git pull ОБЯЗАТЕЛЬНО `launchctl kickstart -k
  gui/$(id -u)/com.wbheadless.planner`; браузерный кэш — Cmd+Shift+R, сверять `APP_BUILD` в консоли.
  У пользователя `cd planner` часто не нужен (он уже там); heredoc в терминал не вставлять — коммитить
  скрипт в репо и запускать (иначе zsh спотыкается на многострочной вставке).

## Открытые вопросы (нужно решение пользователя)
1. **Суточный лимит MPStats — сколько (ЖДУ ОТВЕТА).** Пользователь смотрит в ЛК MPStats число суточных
   запросов API. Нужно, чтобы выставить потолок `budget` by_keywords на отчёт (по умолчанию заложу ~400

2. **Порог доли целевого трафика** — по умолчанию 20% (ползунок в UI). На данных 20% давал чистый муслин.
   Подтвердить/скорректировать после первого боевого прогона.
3. **Целевые слова** — вводит пользователь (напр. «муслин, марлевк»). Синонимы важны (марлевка=муслин).
4. **Отложено:** расширение через ключи конкурентов (взять by_keywords топ-конкурентов → собрать
   их фразы) — можно как шаг 2 после базового пайплайна; связка «Pб-коридор ↔ сезонность»; экспорт из БД.

## Цель
Веб-инструмент планирования производства рубашек (`planner/`). В этой серии сессий —
раздел **«Ранг сезонности»**: по конкурентам-аналогам из MPStats строит прогноз плана
продаж на сезон (вход с нуля → разгон → сезон/пик → распродажа в ноль), с инженерной
моделью жизненного цикла, поставками на склад WB частями и самопроверкой.

## Текущее состояние
Работает и проверено на реальных данных (план 004 «Рубашка», 026). Всё запушено.
- Графики: единая модель периодов **Разгон/Сезон/Распродажа/Межсезонье** + вехи
  (Вход, Старт сезона, Пик, Начало распродажи, Конец) — и на прогнозе, и на истории.
- Лента благоприятного периода со звёздами — НАД цветными полосами (в верхнем поле).
- На прогнозе: **поставки частями** (пила остатков) — П1 к Входу (объём Разгона +10%),
  П2 за 2–3 дня до Старта (50% Сезона +10%), П3 к середине Сезона (остаток → склад в 0);
  оранжевая пунктирная веха — крайний срок подсорта (≤7 дней до Пика).
- Подписи вех раскладываются в 2 ряда при тесноте (зимний сезон: Пик рядом с распродажей).
- **Переключатель ТОП-3 / ТОП-1** в конструкторе (последняя фича): ТОП-1 = уровень
  сильнейшего аналога по выручке в ценовом сегменте → максимум плана и заказа.
- Анти-кэш статики (server.js) + баннер устаревшего плана с кнопкой «↻ Построить заново».
- Метка сборки UI в консоли: сейчас `season-2026-07-22e`.

## Что изменилось (по сути)
1. История размечается ТЕМИ ЖЕ периодами, что прогноз — по календарным границам сезона
   (seasonCal, день года, повтор по годам). Вехи на истории — линии с тултипом без подписей
   (иначе накладываются за 2 года).
2. Склад на прогнозе = реальная логистика поставок частями (пила), а не монотонный спад.
   Сумма поставок = плану ⇒ склад обнуляется к концу. Подсорт — контингент (только дедлайн).
3. Целевой уровень пика выбирается: среднее ТОП-3 (реалистично) или ТОП-1 по выручке
   (амбициозно). Масштаб плана линеен по targetDaily.
4. Деплой-надёжность: анти-кэш + баннер + метка сборки (решают «обновления не видно»).

## Что пробовали и НЕ сработало (важно!)
- **Главные грабли сессии — «обновления не применяются на Mac mini».** Симптомы у юзера:
  старые названия этапов, лента внутри поля, нет поставок. Оказалось ДВЕ причины:
  1) **Браузер кэшировал app.js/styles.css** (подключались без версии). Лечится: анти-кэш
     `Cache-Control: no-cache` в server.js + `Cmd+Shift+R`. Метка `UI build:` в консоли —
     способ убедиться, что загрузился свежий JS.
  2) **Служба Node НЕ перезапускалась** — Node держит `lib/*.js` в памяти, `git pull` файлы
     обновляет, но процесс считает СТАРЫМ движком. Кнопка «Построить заново» дёргает сервер →
     старый результат (монотонные остатки без пилы, нет цветных полос). Лечится ТОЛЬКО
     перезапуском: `launchctl kickstart -k gui/$(id -u)/com.wbheadless.planner`
     (запасной: `lsof -ti tcp:8477 | xargs kill`, KeepAlive=true поднимет заново).
  3) **Сохранённые планы (`data/plans/*.json`) не пересчитываются при git pull** — хранят
     старый forecastDaily. Нужно нажать пересборку. Признак старого плана: нет
     `seasonCal`/`deliveries` → показывается жёлтый баннер. После корректной пересборки на
     НОВОМ движке баннер ИСЧЕЗАЕТ — это индикатор, что бэкенд свежий.
- **matchAll (строгий AND по словам фильтра)** — приводит к глубокой пагинации и таймауту
  ~2 мин. Оставлен только в движке, в UI НЕ выведен.
- **Фильтр аналогов эвристикой (плюс/минус-слова)** принципиально не отличает, напр., зимнюю
  рубашку от офисной без исчерпывающих слов. Предложена фича «фильтр по фото через LLM» — НЕ
  реализована, ждёт ответа пользователя (см. открытые вопросы).
- **Ликвидация хвоста** раньше спайкала выше пика — исправлено: хвост это спад от уровня
  старта распродажи (не выше). Сезон-детект по спайк-устойчивому тренду (smoothCirc 31),
  мин. длина 140д, масштаб по p90 тела (не по max) — иначе узкий сезон от launch-спайка.
- **Bash `pkill -f "node server.js"`** стабильно даёт "Exit code 144" (артефакт окружения),
  но команду выполняет. `git commit` heredoc иногда падал так же — перезапуск команды помогает.

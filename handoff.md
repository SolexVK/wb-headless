# Handoff — план продаж на сезон (метод Овчинникова)

Ветка: `claude/sales-plan-hzlqew`.

## ⚡ Свежее (эта сессия): ПРОГНОЗ на будущий период + живой прогон

Инструмент стал прогнозным (`lib/forecast.js`): по 2 годам истории (recency-
взвешенный свёрнутый профиль продаж/цены/остатков) строит прогноз на заданный
`--from/--to`; корректирует «дрейфом текущего года» по конкурентам за 60 дней
(priceAdj/volumeAdj, клэмп 0.5–2.0); помечает БЛАГОПРИЯТНЫЕ периоды (спрос выше
среднего при остатках ниже среднего). Фильтр: мягкая релевантность со стем-
словоформами («клетка»→«в клетку»), жёсткие — цена/exclude/живость (продажи/мес
ИЛИ выручка/мес). Выход: xlsx (план по дням запрошенного периода) + HTML
(2 диаграммы: 2 года истории + прогноз).

Живой прогон: рубашки в клетку демисезон оверсайз, 2026-08..2027-03 — 4 запроса,
умеренный ранг, пик авг-сен, март благоприятный. Файлы в reports-output/forecast-*.

Критические фиксы на живых данных: (1) OOS-поправка восстанавливала спрос в
предзапускные дни новинок (в графике категории = нули) → чинил на «только
внутренний простой»; (2) launch-спайки (осенние новинки в августе) раздували
месяц → добавил циклическое сглаживание месячного профиля. Тесты 15/15.

## ⚡ Свежее (эта сессия): 4 правила заказчика внедрены + 2 файла-результата

Правила зафиксированы в `CLAUDE.md` (обязательны):
1. **Новый прогон — только после уточняющих вопросов** (не переиспользовать
   прошлые данные, не додумывать фильтр). В скрипте — режим `--interactive`
   (или запуск без `--group`/`--path`).
2. **Окно = последние 2 года** от текущей даты; недавний год весит больше
   (`recencyWeight`, свёрнутый профиль по одноимённым месяцам).
3. **База `own` = 90% конкуренты + 10% свои** (`competitorWeight`); нет своих →
   100% конкуренты.
4. **Результат — 2 файла:** `.xlsx` (по дням, раскраска по этапам) и `.html`
   (визуальный отчёт: кривая сезона, план шт/цены, фазы). Плюс `.csv`/`.json`.

Ключевое в коде: `computeFoldedMonthlyProfile` (recency-взвешенный профиль),
`detectPhases` переписан на кольцевую логику + проекцию на предстоящий сезон +
`stageOfMonth` (6 этапов). `lib/xlsxWriter.js` — свой генератор .xlsx без
зависимостей (ZIP STORE+CRC32, проверен). `lib/reportExport.js` — xlsx+HTML.
Тесты 12/12. НЕ прогонял живьём (по Правилу 1 следующий прогон — с вопросов).

## ⚡ Свежее (последняя сессия): решена проблема расхода лимитов MPStats

`POST /wb/get/category` отдаёт по каждому товару **дневные графики за весь период**
(`sales_graph`/`stocks_graph`/`price_graph`/`revenue_graph`, длина = число дней,
индекс 0 = d1). Значит дневной ряд ВСЕЙ группы берётся **одним запросом** вместо
N по SKU. Экономия ~60×: было 61 запрос на группу из 60 — стало 1 (широкий
фильтр) или 3–5 (узкий). Реализовано: `extractItemDailyFromGraphs` (mpstats.js) +
`collectFromCategory` (seasonPlanReport.js), с ранней остановкой пагинации.
Режим B прогнан живьём на предмете «Рубашка». Способ и цена — в отчёте
(`method`, `requests`).

## Цель

Построить по линейке товаров (или по предмету WB) **план продаж на сезон** по
методу Данилы Овчинникова: определить **ранг сезонности**, **фазы сезона**
(вход в рынок → разгон → пик → распродажа), **ценовые ориентиры** по фазам и
**плановое число заказов по дням**. Данные — из MPStats (тот же сезон год назад,
дневная детализация продаж/остатков/цены по группе-эталону).

## Текущее состояние

Фича реализована, прогнана на живых данных MPStats и откалибрована. Работает:
- ядро (чистая математика) — покрыто тестами, 5/5 зелёных (`npm test`);
- сбор данных из MPStats (POST /wb/get/category + GET /item/{sku}/sales);
- CLI `season-plan.js` и HTTP `GET /reports/season-plan`;
- корректно отрабатывает дневной лимит MPStats (429) — останавливается, не жжёт.

Проверено на реальных линейках: РУБАШКА (пик июль), МПТ (пик февраль), МС/МПР
(умеренные) — планы осмысленные и правильные по типу товара.

Не сделано (осознанно, см. «Открытые вопросы»): режим B (сборка из предмета)
на живых данных не прогнан из-за лимита; недельный профиль по дням недели;
поправка на out-of-stock в месячных коэффициентах; серверная фильтрация
`filterModel`.

## Что изменилось

1. Полный конвейер «группа-эталон → дневной ряд → сезонный профиль → план».
2. Два источника группы: линейка из `config/groups.json` (режим A) и выдача по
   предмету с детальной фильтрацией (режим B).
3. Ранг сезонности по **амплитуде p90/p50** (пик-к-медиане), пороги strong≥2.0 /
   moderate≥1.3 — откалибровано на реальных линейках.
4. Фазы сезона — по **месячному профилю** продаж (устойчиво к дневным всплескам),
   с проекцией дат на +1 год.
5. Флаги достоверности: `lowConfidence` (мало данных), `peakAtEdge`/`saleTruncated`
   (сезон срезан краем окна).

## Что пробовали и НЕ сработало

**Это главный раздел — грабли, найденные ТОЛЬКО на реальных данных.**

- **Ранг по `p90/p10` — провал.** Изначально амплитуду ранга считали как
  p90/p10 (пик-к-провалу). На реальных линейках метрика зашкаливала: от 2.25 до
  67, а при нулевом низком сезоне (линейка не продаётся часть года) p10=0 →
  амплитуда **Infinity**, и ВСЁ становилось «ярко выраженным». Обошли: перешли на
  **p90/p50** (пик-к-медиане) — устойчива к near-zero провалу. Пороги остались
  2.0/1.3, но теперь применяются к p90/p50. Проверка: МС 1.46, МПР 1.65
  (умеренные) против РУБАШКА 3.35, МПТ 3.80 (ярко выраженные) — делит чисто.

- **Пик по дневному максимуму `kSales` — ложные срабатывания.** Дневной max
  относительно линейного тренда спотыкался на разовых всплесках при наклонном
  тренде. У линейки **МПТ** показывал пик в мае (одиночный дневной всплеск),
  тогда как по объёму продаж пик — **февраль** (зимний товар). Обошли: фазы
  теперь определяются по **месячному профилю** (`computeMonthlyProfile`) — пик-
  месяц по суммарному объёму, точная дата = лучший день внутри пик-месяца.
  Зафиксировано тестом «пик по месячному объёму, а не по дневному всплеску».

- **Ведущие/хвостовые нули искажали тренд.** Линейки, запущенные в середине
  окна (МС с авг’24, МК с мар’25, ЛК с апр’25), тянули «нулевой низкий сезон» из
  пред-запускных дней — линейный тренд задирался, коэффициенты плыли. Обошли:
  `trimToActive` отбрасывает ведущие/хвостовые дни без продаж перед расчётом.

- **Много линеек из `groups.json` — мёртвые.** РМП, РМК-ТВИД, РЖК, РММ, РВП, ПШР
  и др. дают по MPStats **нули за 2 года** (`no_data:1`) — артикулы архивные/
  снятые. Живые линейки с продажами: РУБАШКА, МС, МК, МПР, МПТ, ЛК. Для прогонов
  брать их. (Проверка активности — скрипт-probe по первому SKU каждой группы за
  широкое окно; см. историю сессии.)

- **MPStats wiki и API-доки — JS-рендер, WebFetch их не берёт** (возвращает
  пустой shell). Эндпоинты подтверждали по community-тредам, integration-листам
  и сниппетам поиска. Осталось неподтверждённым: точная схема `filterModel`,
  отдельный REST-путь сезонности (его НЕТ — профиль строим сами), кап окна дат.

- **Дневной лимит MPStats (429) исчерпывается быстро.** За сессию упёрлись в
  лимит («Превышен лимит запросов за <дата>»). `/item/{sku}/sales` = 1 запрос на
  SKU — основной пожиратель лимита. Живые прогоны в конце были заблокированы;
  сбрасывается на следующие сутки. Для офлайн-итераций кэшировали сырые дневные
  ряды в `scratchpad/cache.json` (вне репозитория) и гоняли ядро по кэшу.

## Открытые вопросы (нужно решение пользователя)

- **Прогон режима B на живом предмете.** Нужен реальный `path` предмета WB и
  критерии фильтра (слова/ценовой коридор/мин.продажи). Рекомендация: взять
  предмет одной из живых линеек (напр. рубашки) и собрать группу-аналог.
  ЖДУ ОТВЕТА (и сброса лимита MPStats).
- **Недельный профиль (дни недели) в плане заказов** — добавлять? Методология
  предусматривает, но не реализовано. Рекомендация: добавить как опцию.
- **Поправка на out-of-stock в месячных коэффициентах.** Для дефицитных SKU
  провал по остаткам занижает спрос. Логика восстановления есть в
  `lib/stockReport.js`. Рекомендация: добавить, но у текущих линеек с реальным
  нулевым низким сезоном (МС в июле–августе) это не критично.
- **Пороги ранга и лаги входа** (`rankStrong`/`rankModerate`/`ratingLeadDays`/
  `logisticsLeadDays`) заданы по умолчанию. Если у пользователя есть точные
  значения из курса Овчинникова / свои сроки завоза — подставить. ЖДУ ОТВЕТА.

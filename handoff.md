# Handoff — FBS-аналитика (мульти-тенант веб-сервис для Wildberries)

Ветка: `claude/fbs-fullfilment-branch-cfvgir` · последний коммит: `b593ee5`.

## Цель
Мульти-тенантный веб-сервис аналитики FBS (Fulfillment by Seller) для Wildberries.
Крутится на Mac Mini, публично доступен через Tailscale+Caddy по адресу
`https://mac-mini-vital.tail13d29e.ts.net/fbs/`. Каждый продавец подключает свой
кабинет (WB API-токен), сервис считает отчёты по его FBS-фулфилментам. Весь UI и
ответы — на русском. Код сервиса — в `service/`, пайплайны отчётов — в `scripts/`.

Сейчас в сервисе **5 отчётов**: Подсорт, Остатки, Движение заказов, География,
Логистика (у Логистики 3 вкладки: Сборка / Доставка / Путь возврата).

## Что изменилось (по сути)
- Пайплайны перестали дублировать код: WB-выборки и вся математика отчётов —
  в переиспользуемых модулях, покрытых юнит-тестами с вручную посчитанными числами.
- `views.js` больше не монолит — три модуля + kit; фасад сохраняет прежние импорты.
- Excel-выгрузки собираются через общий kit; % возврата в географии унифицирован
  (везде доля + формат `0.0%`, а не «сырое 33.3 с литеральным %»).
- Архив: у каждого запуска есть HTML-выгрузка; владелец может массово чистить все
  авторские отчёты (кнопка «Очистить все отчёты»), участник — только свои;
  накопительные снимки по расписанию (`user_id IS NULL`) не удаляются нигде.
- Логистика теперь покрывает полный жизненный цикл: сборка → доставка → **путь
  возврата**. Возврат привязывается к исходному ФФ по `srid = rid`; «склад
  возврата WB» = `warehouseName` строки возврата; времена: «отгрузка → выкуп»
  (closedAt → дата продажи) и «у клиента: выкуп → возврат» (дата продажи → дата
  возврата, по общему srid).

## Что пробовали и НЕ сработало (грабли — читать обязательно)
1. **PDF-зависание на ~55с (регресс, который я сам внёс в P2c и потом исправил).**
   В P2c добавил свежий `--user-data-dir` (одноразовый профиль Chrome) ради защиты
   от SingletonLock при параллельных запусках. На macOS свежий профиль заставляет
   Chrome лезть в **Keychain**, а под launchd (без GUI) запрос доступа висит до
   таймаута → первая попытка `--headless=new` висела ровно 55с, потом фолбэк на
   легаси `--headless` срабатывал. Итог: PDF собирался, но пользователь ждал минуту.
   **Как обошли:** откатили к профилю по умолчанию (как до P2c, сборка ~2–3с),
   добавили `--use-mock-keychain` как страховку, оставили только полезную часть
   P2c (пер-попытка timeout 45с + killSignal SIGKILL, 2×45<180с внешнего лимита
   раннера). Вывод: **не задавать свой `--user-data-dir` в headless Chrome на
   macOS/launchd** — это провоцирует Keychain-prompt и зависание.
2. **Windows-прокси блокировал не-443 порты** (более ранняя сессия, но актуально
   для доступа к сервисам). `ERR_TUNNEL_CONNECTION_FAILED` в Chrome = системный
   прокси, а не сервер. Лечится исключением `*.ts.net;100.*` в настройках прокси
   Windows. Сравнивать не только код ответа, но и РАЗМЕР тела (FBS healthz ~71
   байт vs OpenClaw shell ~10КБ — легко перепутать «какой сервис ответил»).
3. **`node --check scripts/fbs-*.mjs` падал с MODULE_NOT_FOUND** — потому что cwd
   оставался в `service/` после `cd service`. Всегда `cd /home/user/wb-headless`
   (или абсолютные пути) перед git add/commit и node --check пайплайнов.
4. **Excel «геро %» ложное равенство:** на листах регионов % хранился как доля
   (0.333 + формат `0.0%`), на FBS-листах — как сырое 33.3 с литеральным `%`.
   Визуально одинаково, но значение в 100× разного масштаба ломало сортировку/
   формулы. Привели всё к доле+`0.0%`. Проверять Excel не глазами по отображению,
   а по фактическому значению ячейки (`cell.value`, `cell.number_format`).
5. **`diff -q` по несуществующему файлу возвращает «отличается»** — при побайтной
   сверке Excel это дало ложную тревогу по `xl/sharedStrings.xml` (openpyxl его не
   создаёт, использует inline strings). Авторитетна рекурсивная `diff -rq` по
   распакованным .xlsx; расхождение только в `docProps/core.xml` = таймстемп
   генерации (не код).
6. **smoke-reports ломался от смены заголовков** — при изменении h1 логистики
   и заголовка дашборда пришлось обновить строковые проверки в smoke-reports
   (`'сроки сборки и доставки'` → `'сроки сборки, доставки и путь возврата'`).
   Смоук проверяет вхождение строк — при правке текстов синхронизировать.
7. **«В какой ФФ вернулся» — ограничение данных WB.** Для FBS возврат физически
   уходит в склад/ПВЗ WB (`warehouseName` строки возврата: «Подольск», «Коледино»
   и т.п.), НЕ в наш фулфилмент. Отдельного времени «возврат оформлен → доехал до
   склада» WB в статистике не отдаёт — поэтому этап возврата меряем как «у клиента»
   (выкуп → оформление возврата). Не обещать пользователю то, чего нет в данных.

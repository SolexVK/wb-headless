# Handoff — FBS / Fulfillment

## Цель
Инструментарий по продажам Wildberries по схеме **FBS** в ветке
`claude/fbs-fullfilment-branch-cfvgir`: тянуть данные по нашим фулфилмент-складам
(остатки, заказы, поставки, статусы, номенклатура) с соблюдением лимитов WB API,
и выдавать **дашборды** (HTML-артефакты) и **PDF-отчёты**. Финальная цель —
операционные отчёты для управления FBS (подсорт, движение товара, SLA и т. д.),
упакованные в скиллы.

## Текущее состояние
Рабочий конвейер на живом WB API (токен в env `Wildberries_API`, лимиты держит
`lib/wbClient.js`). Всё, что построено — **строго FBS** (методы Маркетплейса по
складам продавца). Готово и опубликовано артефактами:
- **Остатки**: `fbs:stock` → снимок; дашборды `fbs:report` (остатки+ретро),
  `fbs:stock:articles` (по артикул+цвету, размеры объединены); PDF `fbs:stock:pdf`.
- **Движение по дням**: `fbs:delivery` → `fbs:delivery:dash` (передано в доставку),
  `fbs:accepted:dash` (принято на фулфилмент + баланс передано−принято).
- **Единый отчёт**: `fbs:report` (HTML) и `fbs:pdf` (PDF A4 альбомная).
- **Подсорт**: `fbs:replenish` → `fbs:replenish:dash` — ГЛАВНЫЙ актуальный отчёт,
  недавно переработан (см. ниже).
- **Скилл** `/fbs-dashboards` собирает три дашборда (delivery/accepted/stock-articles).
- `reports-output/` в `.gitignore` — в git только генераторы `scripts/*.mjs`.

**Подсорт (последнее состояние, согласовано с пользователем):**
- считаем ТОЛЬКО по FF (FBS); FBO не учитываем (парадигма: FBO распродаём);
- расчёт для КАЖДОГО склада отдельно — скорость `perDay` по `warehouseId|nmID`
  (не общая по кабинету); склад без остатка и без продаж — пропускается;
- лид-тайм подсорта 12–18 дн зашит: горизонт заказа = lead(18)+cover(14)=32 дн;
  статус «разрыв до поставки» = закончится раньше min-лида (12 дн);
- сортировка строк: артикул № → цвет → количество;
- новинки (номенклатура, ни разу не на FF) — завоз seed-min (10 шт) на КАЖДЫЙ
  действующий фулфилмент (матрица артикул × склад);
- в шапке дашборда — разбивка статусов по цветам (как пилюли в таблице).
- Последний снимок: подсорт 3333 шт, 103 строки в риске, новинок 166 (×8×10=13280).

## Что изменилось (эта сессия)
- Дашборды «по дням» (delivery/accepted) в стиле стороннего примера «Выберите день»:
  плитки по дням (сегодня=план, прошлые=факт), матрицы фулфилмент×день, баланс
  передано−принято. Заголовок #1 → «Количество переданных в доставку товаров».
- Дашборд остатков по **артикул+цвету** (nmID), размеры суммируются.
- Отчёт **подсорта**: сначала article-level, затем ПЕРЕРАБОТАН под per-warehouse +
  лид-тайм 12–18 дн + сортировка арт→цвет→кол-во + новинки. Новинки — завоз по
  каждому складу (матрица). В шапку добавлена разбивка статусов по цветам.

## Что пробовали и НЕ сработало
- **`statistics/incomes` (приёмка) — 404 по нашему токену** и концептуально это
  FBW-приёмка на склады WB, а не поступления на склад продавца. Вывод: физических
  поступлений на FF WB API не отдаёт. Поэтому «принято на ФФ» = новые сборочные
  задания (создано за день), а не физический завоз.
- **Подсорт на уровне «склад×артикул» с суммарной логикой шумит**: остаток между
  нашими складами перемещается, спрос привязан к складу-исполнителю → ложные
  «нет остатка». Сначала обошли article-level (сумма по сети), но пользователь
  попросил именно per-warehouse; вернули per-warehouse, а строки без остатка И без
  продаж отбрасываем (скорость не выдумываем). Это корректно: скорость пустого
  склада взята из продаж ранее в окне, когда остаток был.
- **Статистика `supplier/orders` для атрибуции FBS по нашему складу — НЕ годится**:
  warehouseName = приёмка/СЦ WB. Наш склад — только в marketplace `/api/v3/orders`
  (поле `warehouseId`).
- **`/api/v3/orders/status/history` — только трансграничные**; тайминги обычного
  FBS берём из `/api/v3/supplies.closedAt`.
- **Метод остатков FBS принимает ШТРИХКОДЫ, не nmID** → карта штрихкод→nmID из
  content cards.
- **Playwright не ставится сам**: `npm i playwright`, Chromium предустановлен
  (`PLAYWRIGHT_BROWSERS_PATH`), запуск с executablePath. Скрипты из scratchpad НЕ
  видят playwright (node_modules только в репо) — временный helper `_shot.mjs`
  клали в корень репо и удаляли. `pdftoppm` в окружении НЕТ — вёрстку проверяем
  скриншотами print-HTML через Playwright.
- **Фетч dev.wildberries.ru** — только через Chromium (антибот+SPA), при HTTPS_PROXY
  опускать TLS до 1.2 (ECH). Каждый фетч 40–90 с; slug'и не брутфорсить.
- **rid↔srid для «выкупа по складу»**: marketplace orders имеют `rid` (не `srid`),
  statistics/sales имеют `srid` — форматы совпадают (`…r<uuid>.0.0`), склейка
  возможна (проверить точное совпадение ключа на пересечении данных). Ещё не сделано.

## Команды для проверки
```bash
for f in scripts/fbs-*.mjs scripts/wb-*.mjs lib/wb*.js; do node --check "$f" && echo "ok $f"; done
npm run token:check            # ожид.: найден ДА, источник env:Wildberries_API

# конвейер подсорта (главное сейчас)
npm run fbs:stock
npm run fbs:replenish -- --velocity-days 28 --lead 18 --lead-min 12 --cover 14 --seed-min 10
npm run fbs:replenish:dash     # → reports-output/fbs-replenishment-dashboard.html (+ .artifact.html)

# дашборды «по дням» и остатки
npm run fbs:dashboards         # stock+delivery+3 дашборда
```
Формальных тестов нет. «Зелёное»: `node --check` по всем скриптам проходит;
`token:check` = найден; конвейер отрабатывает без ошибок и пишет непустые снимки в
`reports-output/`. **Ожидаемое сейчас:** всё зелёное на живом API. Последний снимок:
остаток ~3.4–3.5к шт (данные живые, меняются), подсорт 3333 шт, новинок 166.
Если конвейер падает 401/пусто — проблема с токеном (`Wildberries_API`), а не с кодом.
ВНИМАНИЕ: данные ЖИВЫЕ — остатки/склады меняются между прогонами (появился склад «Екат»,
остаток «переезжал» на «Ред Экспресс») — это не баг.

## Открытые вопросы (нужно решение пользователя)
- **Новинки — на какие склады заводить.** Сейчас на ВСЕ 8 складов (вкл. слабые
  Краснодар/СПб/Екат) → 13280 шт. Рекомендация: заводить только на основные рабочие.
  **ЖДУ список приоритетных складов.**
- **Seed-минимум с учётом размеров.** Сейчас 10 шт на карточку (артикул+цвет). Для
  размерного товара логичнее задавать минимум на размерный ряд. **ЖДУ решение.**
- **Кейс «артикул продаётся на одних складах, но на этом складе его не было».**
  Сейчас такие строки для склада пропускаются. Заводить ли их минимумом на этот
  склад (расширение ассортимента по всем складам)? Чувствительно к деньгам —
  **ЖДУ ответ**: только чистые новинки или тоже new-to-this-warehouse.
- **cover (запас после прихода) = 14 дн** — уточнить реальный цикл между подсортами.

## Отложено «доработаем потом» (по словам пользователя)
- Разрез по РАЗМЕРАМ (артикул→цвет→размер) в подсорте и отчётах.
- Отдельная **FBO-секция** к остаткам (товар на складах WB, метод `statistics/stocks`;
  в заказах/продажах разделять по `warehouseType` = «Склад продавца»/«Склад WB»).
- Отчёт **«выкупы/возвраты по складу»** (join rid↔srid, фильтр FBS) + остальные из
  плана: **SLA/просрочки сборки**, **баклог/завалы**.
- Учёт **товара в пути** (уже заказанный подсорт), чтобы не заказывать повторно.

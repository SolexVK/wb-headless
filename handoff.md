# Handoff

## Цель
Добавить в проект **базу данных** для накопления структурированных данных. Проект (`wb-headless`)
собирает отчёты по товарам Wildberries через MPSTATS и запускается на **GitHub Actions**. Раньше
данные никак не копились: каждый запуск заново дёргал MPSTATS и складывал результат только в
эфемерные файлы `reports-output/` (в `.gitignore`) + artifacts запуска. Нужно было хранилище, чтобы
данные **накапливались между запусками**, к ним можно было обращаться, пересчитывать отчёты задним
числом и снова сохранять — без внешней БД-инфраструктуры.

Выбранный по умолчанию вариант (согласован с пользователем): **SQLite-файл в репозитории** +
**дневные ряды по SKU** как основа накопления. Заложен фундамент под будущий этап — подключение
выгрузок из других инструментов, которые появятся позже.

## Текущее состояние

- `/health` отдаёт статистику БД.

Не проверено на живом окружении (нет доступа к MPSTATS-токену в этой сессии): реальный прогон
`report-stock.js` против настоящего API и шаг коммита БД внутри GitHub Actions (push из раннера).
Логика протестирована через мок `fetch`.

## Что изменилось
- Появилось персистентное хранилище: один файл `data/wb.db` в git. Эфемерный раннер Actions после
  сбора отчёта коммитит обновлённый файл обратно — так данные переживают запуски.
- Схема (`lib/db.js`): `products`, `groups`, `product_groups` (справочник); `sku_daily` — **сырьё**
  по дням (upsert по `(wb, date, source)`, не задваивает); `report_runs`/`report_rows` — снимки
  отчётов; `tool_exports` — **универсальный приёмник** произвольных выгрузок будущих инструментов (JSON).
- Миграции версионные (PRAGMA `user_version`) — новый инструмент добавляет элемент в массив
  `MIGRATIONS`, прогоняются только новые.
- Два пути подключения будущих инструментов: быстрый — `saveToolExport()`; основательный — новая
  типизированная таблица миграцией. Поле `source` в `sku_daily` позволяет разным источникам писать
  ряды бок о бок.

## Что пробовали и НЕ сработало
- **Выбор драйвера SQLite.** Рассматривали `node:sqlite` (встроен в Node 22, локально доступен, но
  помечен экспериментальным и сыплет ExperimentalWarning; в workflow вообще Node 20 — там его нет) и
  `sql.js` (WASM, без нативной сборки, но грузит всю БД в память и требует ручного экспорта в файл).
  Остановились на **`better-sqlite3`**: синхронный, ставится префилд-бинарником (на ubuntu-latest без
  компиляции), без экспериментальных предупреждений, работает на Node 18/20/22. Локальный smoke-тест
  прошёл.
- **FK-падение в `syncGroups` — реальный баг, пойман тестом.** Первая версия `syncGroups` делала
  `INSERT OR IGNORE INTO product_groups(...)` с внешним ключом на `products(wb)`. `OR IGNORE` **не
  подавляет нарушение FOREIGN KEY** — если группа ссылается на WB, которого нет в `products`, вся
  транзакция падала с `FOREIGN KEY constraint failed`, и `runReport` молча уходил в режим «без БД»
  (данные не писались). Всплыло в e2e-тесте, где синхронизировали 2 товара, а `config/groups.json`
  ссылается на весь каталог (206). В бою `runReport` синхронизирует полный каталог первым, поэтому не
  проявлялось — но хрупко. **Обошли:** перед связыванием `syncGroups` вставляет заглушку товара
  (`INSERT OR IGNORE INTO products(wb,'',...)`) для неизвестного WB. После фикса тест зелёный.
- **Журналы SQLite и git.** Чтобы коммитить ровно один файл, отказались от WAL (создаёт `-wal`/`-shm`)
  и оставили `journal_mode = DELETE` (по умолчанию) — после закрытия остаётся только `data/wb.db`.
  Транзиентные `*.db-journal/-wal/-shm` на всякий случай добавлены в `.gitignore`. Масштаб данных
  крошечный (≈75 тыс. строк/год), производительность WAL не нужна.
- **Почему не «поднять БД-сервер на GitHub».** Раннеры Actions эфемерны, диск стирается после job —
  долгоживущий Postgres/MySQL, доступный между запусками, там держать нельзя. Отсюда выбор
  «БД = файл в git».

## Команды для проверки
```bash
# 0. Зависимости (нужен better-sqlite3)
npm ci                     # или: npm install

# 1. Синтаксис ключевых файлов
node --check lib/db.js && node --check db-cli.js && node --check report-stock.js && \
node --check server.js && node --check lib/stockReport.js

# 2. Юнит-прогон слоя БД на временной базе (не трогает data/wb.db)
DB_PATH=/tmp/t.db node --input-type=module -e '
import { openDb, closeDb, syncProducts, syncGroups, saveSkuDaily, saveReport, getSkuDaily, latestReport, saveToolExport, stats } from "./lib/db.js";
const db = openDb();
syncProducts(db,[{wb:111,seller:"A"}]); syncGroups(db,{РМП:[111]});
saveSkuDaily(db,111,[{date:"2026-06-01",balance:5,sales:2,price:1000,revenue:2000}]);
saveReport(db,{period:{d1:"2026-06-01",d2:"2026-06-01"},totals:{lostRevenue:0},rows:[{sku:111,seller:"A"}]});
saveToolExport(db,{tool:"demo",entity:"111",payload:{ok:true}});
console.log(JSON.stringify(stats(db))); console.log(getSkuDaily(db,111).length, latestReport(db).rows.length);
closeDb(db);'; rm -f /tmp/t.db

# 3. CLI против реальной data/wb.db
npm run db:stats
npm run db:sync            # перечитать config/*.json в БД

# 4. Сервер + статистика БД в /health
PORT=8099 node server.js &   # затем: curl -s localhost:8099/health ; потом останови процесс

# 5. Полный отчёт (нужен реальный токен MPSTATS — в этой сессии НЕ проверялось)
MPSTATS_TOKEN=xxxxx npm run report:stock
```
**Ожидаемое состояние (зелёное сейчас):** `node --check` по всем файлам — OK; юнит-прогон п.2 печатает
`products:1 … skuDailyRows:1 … reportRuns:1 … toolExports:1`, затем `1 1`; `npm run db:stats` показывает
`Товаров 206, Групп 22, Дневных строк 0`; `/health` возвращает `ok:true` с блоком `db`. **Красных нет.**
Формальных тест-фреймворков в проекте нет — «зелёным» считается успешный прогон п.1–4. **Не
проверено (не красное, а неизвестное):** реальный `npm run report:stock` против MPSTATS и push БД из
GitHub Actions — требуют секрета `MPSTATS_TOKEN` и запуска workflow.

## Открытые вопросы (нужно решение пользователя)
1. **Подключение будущих инструментов** — пользователь явно отложил на потом («после нужно будет
   подумать, как прикрутить выгрузки из всех инструментов»). Фундамент готов (`tool_exports` +
   миграции). ЖДУ: какой инструмент первый и какой у него формат выгрузки → тогда решим, приёмник
   `tool_exports` или отдельная типизированная таблица.
2. **Стратегия при росте данных.** Сейчас SQLite-в-git. Если объём/частота вырастут или понадобится
   доступ извне GitHub — миграция на serverless (Turso — SQLite-совместимая, почти бесшовно; или
   Neon/Supabase Postgres). Рекомендация: оставаться на SQLite, пока хватает. Не срочно, решения сейчас
   не требует.
3. **Персистит ли HTTP-эндпоинт `/reports/stock-availability`?** Сейчас — нет (оставлен как read-only,
   чтобы ad-hoc запросы не плодили снимки). Накопление идёт через `runReport` (CLI + планировщик +
   workflow). Если нужно, чтобы и HTTP-запросы копили дневное сырьё — скажи, добавлю. Рекомендация:
   оставить как есть.

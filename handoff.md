# Handoff — Визуальный поиск товаров WB по эталону

Ветка: `claude/image-search-5jy2gf`. PR не открывался.

## Цель
Дана эталонная карточка (женская рубашка оверсайз из марлевки/муслина, описана в
`target_womens_shirt_visual_profile.json`) — нужно из выгрузки MPStats по категории
отобрать и отранжировать карточки WB, похожие на неё **визуально и конструктивно**.
Распознавание — локальной моделью на Mac Mini, без платных API.

Принципиальное требование пользователя: **название и описание карточки не имеют права
отсеивать товар** — там бывает недостоверная информация. Отсев только по характеристикам
(структурированные поля WB) и по зрению.

## Текущее состояние
Конвейер собран целиком и один раз прогнан вживую на топ-500 категории «Рубашка».
Всё запушено, рабочее дерево чистое, последний коммит `0d52b66`.

Воронка боевого прогона: 500 → текстовый гейт снял 112 → 29 карточек пропали с WB →
гейт зрением снял 54 → **305 дошли до разбора**. Ошибок модели ноль; 195 минут работы
без роста свопа.

После починки шкалы ткани распределение по корзинам:
очень близкий 32 · близкий 84 · посмотреть глазами 104 · смежный 69 · нерелевантный 8.
В топе — настоящие муслиновые оверсайз-рубашки; шёлковые блузки с гипюром, которые
раньше стояли первыми с баллом 98, ушли.

Незакрытое: у 18 % карточек ткань всё ещё `unknown`, у 47 % — манжета. Лечится
перезапуском разбора (в старых данных нет шестого вопроса про ткань).

**Запланировано на ночь:** пользователь запускает `scripts/night-run.sh` на Mac Mini,
разбор 305 карточек с шестью вопросами, ~2,5 часа. Результата ещё нет.

- `scripts/night-run.sh` — **новое:** отложенный ночной запуск разбора.
- `scripts/score-selftest.mjs` — самопроверка скоринга на шести размеченных карточках.

- `data/top500-shirts.txt`, `data/top500-shirts-meta.csv` — артикулы и метрики из MPStats.

## Что изменилось
1. **Три ступени вместо одной.** Текстовый гейт по характеристикам (бесплатно, снимает 22 %),
   гейт зрением на одном мелком фото (снимает ещё 11 %), затем полный разбор на двух фото.
2. **Один вопрос — один запрос.** Гипотеза пользователя подтвердилась: точность 62 % → 75 %,
   а времени всего +17 %, потому что Ollama переиспользует обработанное изображение
   между запросами с одинаковым префиксом.
3. **Кластеры по 25 с выгрузкой модели.** Тоже идея пользователя. Своп за 195 минут
   не вырос вообще (1760 → 1680 МБ).
4. **Балл считается кодом, не моделью.** Модель отвечает только закрытыми enum'ами;
   проценты и корзины — детерминированная таблица весов.
5. **Починена шкала ткани** (см. следующий раздел).
6. Веса отражают *разделяющую силу внутри категории*, а не важность вообще: в категории
   «Рубашка» отложной воротник есть почти у всех, поэтому делит выборку ткань (вес 20),
   а не воротник (13).

## Что пробовали и НЕ сработало

**Семь жёстких гейтов из исходного профиля → пустая выдача.** Низ изделия и манжета не
видны на большинстве фото, а `unknown` валил карточку. Оставили три гейта
(`garment_type`, `collar`, `front_closure`) и правило «признак не виден ≠ признака нет».

**Главный провал: 45 % карточек в корзине «очень близкий аналог».** Я убрал вопрос
`fabric_texture` из зрения, решив, что состав придёт из характеристик. Но `FROM_TEXT.fabric`
возвращал `null` на обычном «хлопок 100 %» — ткань стала `unknown` у 86 % карточек.
Дальше политика `redistribute` выбросила вес 20 из знаменателя, и «мы не знаем главного»
посчиталось как «идеально совпало по всему остальному». Шёлковая блузка с гипюром
получала 98 баллов. Починено тремя правками: расширенная шкала ткани из текста
(«хлопок + полупрозрачная» → `translucent_cotton`, 0,8 веса), `capBandOnUnknown`
(без ткани балл не выше 89), возврат вопроса про ткань в зрение + `WEAK_TEXT`
(расплывчатый состав уступает конкретному ответу с фото).
**Урок: любой признак с весом ≥ 15 обязан иметь потолок при `unknown`.**

**`gemma3:12b` отдавал HTTP 500** «this model is missing data required for image input» —
локальный тег был без vision-проектора. `--num-ctx 8192` не помогал. Лечится
`ollama pull gemma3:12b` (докачивается слой 8,1 ГБ).

**`fetchCard` без ретраев молча терял карточки** — одна сетевая ошибка = карточка
исчезла из выдачи навсегда, без следа в логе. Добавлены ретраи 400 мс × 2ⁿ.

**Имена полей зрения ≠ имена атрибутов профиля** (`cuff`/`cuffs`, `sleeve_length`/`sleeves`).
Молча превращались в `unknown` — оба признака выпадали из скоринга. Лечится явной
таблицей `VISION_TO_PROFILE`; неявное сопоставление по имени сюда возвращать нельзя.

**`cuff='folded'` — мусорный ответ.** На размеченном наборе встретился четыре раза
и все четыре раза неверно, верных не было. Внесён в `UNRELIABLE`, засчитывается как
`unknown`. Список пересматривать после любой смены модели или промпта.

**Сокращение схемы разбора до четырёх полей не помогло** (точность осталась 75 %),
а добавление `hem` и `body_length` уронило её до 62 %. Оба признака исключены из
вопросов навсегда: низ на фото манекена почти не виден, и модель на нём уверенно врёт.

**Мои прогнозы, которые не сбылись** (не доверять оценкам без замера): «один-по-одному
будет в 2–3 раза медленнее» — оказалось +17 %; «убрать поля поможет манжете» —
точность рухнула 6/6 → 1/6; «гейт зрением отсеивает всего 5 %, может, он не нужен» —
оценка по трети выборки, на полных данных 11 %, ступень окупается.

**MPStats недоступен с Mac Mini** — `~/wb-headless/.env` там просто нет, планировщик
берёт переменные из своего launchd-плиста. Сбор артикулов вынесен в облачную сессию,
список закоммичен в `data/`.

**Грабли окружения:** `| tee` прячет вывод Python (блочная буферизация) — нужен
`python3 -u`. Inline-комментарий `#` внутри команды zsh ломает `cd`. `grep -c` печатает
`0` и выходит с кодом 1, поэтому `|| echo 0` дописывал второй ноль.

**Токен:** в ходе отладки загрузчика `.env` я вывел в консоль реальное значение
`MPSTATS_TOKEN`. Пользователю сообщено, ротацию рекомендовал — **не подтверждено, что сделана.**

**Ожидаемое состояние:** `node --check` и `bash -n` — молча, без вывода. Самопроверка
скоринга — «Все 6 карточек попали в ожидаемые корзины». Формальных unit-тестов в проекте
нет, самопроверка их заменяет. `report-visual.mjs` в облачной сессии упадёт с «Нет данных» —
это нормально, `out/*.jsonl` лежат только на Mac Mini и в git не коммитятся.

## Открытые вопросы (нужно решение пользователя)
1. **Веса и порог отсечки после ночного прогона.** Сейчас `cutoff: 80`, границы корзин
   90/80/70/50. Пользователь собирался посмотреть новую выдачу глазами и сказать, устраивает
   ли раскладка. Рекомендация: ничего не трогать, пока не пришли данные с шестым вопросом —
   ткань закроется у 82 % → 100 %, и распределение поедет само. **ЖДУ ОТВЕТА.**
2. **`hem` и `body_length` — вес 11 на двух признаках, которые не наблюдаются никогда.**
   Варианты: (а) оставить как есть — вес честно выбывает у всех одинаково, на ранжирование
   не влияет; (б) обнулить веса и перераспределить на ткань и силуэт. Рекомендую (а):
   если однажды появится модель, которая видит низ, признаки заработают без правок.
   **ЖДУ ОТВЕТА, не срочно.**
3. **Ротация `MPSTATS_TOKEN`** — см. выше. **ЖДУ ПОДТВЕРЖДЕНИЯ.**
4. **Порт-реестр в `MACMINI-DEPLOY.md` устарел на 19 портов**, Tailscale Funnel выключен
   (все маршруты «tailnet only»). Предлагал обновить реестр — ответа не было. К этой задаче
   отношения не имеет, но всплыло при аудите. **ЖДУ ОТВЕТА.**

## Следующий шаг
Утром: `tail -40 out/night-run.log` на Mac Mini — убедиться, что ночной прогон дошёл до
конца (ищем строку «разбор завершён, код 0») и модель выгружена. Затем
`node scripts/report-visual.mjs --top 20` и сравнить долю `fabric=unknown` с нынешними 18 %.
Если ноль ошибок и ткань закрылась — конвейер можно считать готовым и переходить к
масштабированию с 500 карточек на всю категорию (~15 700 при выручке ≥ 100 000 ₽).

## Цель
Финмодель показала кассовый разрыв. Задача: **сократить план продаж с ~342k до ~200k шт (Эпоха 1)**,
убирая в первую очередь **слабо продающиеся расцветки** (по фактическим данным ВБ за 6 мес), затем —
количествами под финмодель (Эпоха 2). Строим фичу «✂️ Сокращение плана» поэтапно. Метрика реза —
на выбор (выкупы / выручка / смешанная); применять сразу, НО с откатом; «убрать расцветку» = обнулить
в матрице всех партий + перевести цвет в архив (archivedColors) → пересчёт Ганта/ткани/финансов.

## Что изменилось
- **Штуки плана = СУММА по этапам** (не МАКС). Этап = волна продаж, штуки складываются. Формула теперь
  как demand в дашборде (app.js:3009 `Σ matrixSum(planMatrix)` по plan-партиям, не historical). Это дало
  правильные ~342k вместо 129k.
- **Метрика реза — смешанная**: normalize(выкупы) и normalize(выручка) к долям от максимума, бленд 50/50.
  Плюс режимы «только выкупы» и «только выручка».
- **Защита новинок** `a.cutProtected`: артикул исключён и из авто-, и из ручного реза. Нормализуется
  в model.js. 036 (новинка без продаж) — пример, обязательно защищать.
- **Применение реза**: снапшот «перед резом Эпоха 1» → обнулить planMatrix во всех партиях + archivedColors
  → recalc(true) (PUT state + POST /api/schedule → Гант/ткань/финансы). Журнал в state.planCut
  {snapshotId, items, cutUnits}. Откат = restore снапшота (реюз /api/state/snapshots/:id/restore).
- **state.planCut** уцелевает при нормализации: normalizeState = `{...base, ...input}`, unknown-ключи верхнего
  уровня сохраняются (проверено).

- **План 129 969 вместо ~311k (реально 342k):** planUnitsByArticleColor брал МАКС по этапам (ошибочно
  думал «одна вещь проходит все этапы»). На деле `p.stageId` = ВОЛНА продаж, `p.status`
  (plan/cutting/…) = произв. стадия. Правильно — СУММА по всем plan-партиям (как app.js:3009). Фикс: MAX→SUM.
- **404 на /api/plancut/sales/collect после git pull:** backend НЕ перезапускался — node держал старый
  server.js в памяти (frontend/app.js статикой обновлялся, а роут collect в старом бэкенде отсутствовал).
  Диагностика: `curl /api/health` показывал старый билд. Фикс: перезапуск launchd-ярлыка
  `com.wbheadless.planner` (`launchctl kickstart -k gui/$(id -u)/com.wbheadless.planner`). **ВСЕГДА после
  git pull перезапускать бэкенд и сверять билд в /api/health.**
- **Exit code 144 в Bash** при `kill`/`pkill` в составной команде (сигнал уходит шеллу) — коммиты/тесты
  проходят, но код 144. Обход: kill отдельной командой; для проверки «жив ли сервер» — `pgrep -af`
  (учти, что оно ловит и саму строку команды).
- **GET /api/state отдаёт state НЕ обёрнутым** в `{state}` (в отличие от PUT/restore). В E2E-тесте
  ловил `undefined.articles` — фикс: `const st = g.state || g`.
- Прошлые грабли (в силе): строгая группировка артикул→ВБ по первым цифрам vendorCode (без смешивания);
  cookie сессии по ХОСТУ не порту (архив без входа); подписка Claude только через `claude` CLI; Mac mini
  без прокси нет интернета; launchd урезает PATH (CLAUDE_CLI_PATH в data/.env); БД в WAL — архив через

Формальных unit-тестов нет; «зелёное» = node --check OK + ручной прогон эндпоинтов.

# Handoff — Этап 3: Ранг сезонности → План по размерам (этапы → поставки)

Ветка: `claude/production-plan-twv8ki`. Приложение: `planner/` (Node + Express + SQLite, SPA на ванильном JS-модуле). Работает на Mac mini у пользователя (`openclaw@Mac-mini-Vital`), публично через Tailscale Funnel. **Планировщик запущен на порту 8477** (не 8090 — 8090 занят посторонним Python-приложением).

## Цель
Связать «Ранг сезонности» (прогноз спроса) с производственным «Планом по размерам». Прогноз → матрица цвет×размер → **серия партий-поставок** (приход на WB частями), с заменой устаревших «4 этапов» на динамические поставки, распределением по цехам по мощностям, и реалистичным стартом плана продаж с учётом времени на запуск. Архитектура сопоставления цветов — «C+».

## Текущее состояние
**Всё работает, основной поток закрыт.** «Применить» создаёт партии-поставки, они видны на «Плане по размерам» и планируются. Последний коммит `787d6b6`, ветка синхронизирована (`0 0`, запушено).

Готово и запушено (Этап 3):
- Движок reconcile + colorNorm; модель партий-поставок (`deadline`/`deliveryTag`/`origin`); планировщик по сроку партии; блок 🎨 (сортировка/выравнивание/ВСЕГО); блок 🧩 (гибкое сопоставление, «создать цвет», архивные цвета, серия поставок); «План по размерам» на поставках (без этапов); распределение по цехам по мощностям; фильтр по цеху; «Удалить все партии»; нейминг для года («Довоз окт 26»); **«Старт плана продаж»** (авто/вручную, срок запуска, вместо «Целевого года»).
- Диагностика рассинхрона: `/api/health` отдаёт `backendBuild`, фронт показывает красный баннер, если backend старый.

**Три правки по листу «Ранг сезонности» (последняя итерация) — ГОТОВО и запушено:**
1. **🧩 == 🎨** (коммит `c331dc0`): пер-цветовое кол-во в блоке «План по размерам из прогноза» теперь точно совпадает с блоком 🎨. Баг был в размерах: доля размера спроса, которого нет в ряду карточки (напр. «38-40/XS» при ряде S..5XL), молча терялась в «не размещено». Починка в `reconcile.js`: непокрытые размерные доли **перераспределяются** на существующие размеры (нормировка весов к 1), полное кол-во цвета попадает в матрицу.
2. **Планы продаж по цветам** (коммит `787d6b6`): раньше был отдельный блок «📊 Планы продаж по цветам» — пользователь его отверг. Теперь per-color планы **внутри блока «План продаж по дням»**: под сводной таблицей — секция «Планы продаж по цветам» с **чипами-фильтром** (только выбранные цвета артикула) и **сворачиваемым `<details>`** на каждый цвет; таблица цвета (выкупы/заказы/цена/благопр.) в той же гранулярности (дни/недели/месяцы), объёмы масштабированы долей цвета (лидер=1), итог = qty цвета из ассортимента = объёмы в партиях.
3. **Слияние мелких партий года** (коммит `c331dc0`): для круглогодичного плана при дроблении на довозы, если партия < `MIN_PROD_BATCH=2000` шт, соседние месяцы **сливаются** (сен 1189 + окт 1567 = 2756), дата = ранний месяц, тег «Довоз сен–окт 26». **План продаж остаётся помесячным** — сливаются только производственные партии. `mergeDeliveriesForProduction()` в `app.js`, применяется и в предпросмотре, и в `applyReconcile`.

**НЕ сделано (следующее):** шаг 5 — лист «Данные»: скрытие архивных цветов (`article.archivedColors`) на прочих листах (Факт/Заказ ткани/экспорт/расчёты) + бейдж «заведи ткань» для новых цветов без fabricInfo. Модель `archivedColors` уже есть, но листы её пока не скрывают.

## Что изменилось (суть)
Партия перестала быть `(артикул × этап)` — теперь `(артикул × поставка)` со своим сроком WB. «Применить» в Ранге создаёт серию партий-поставок (доли по времени × полный цветной тираж, Хэмилтон — каждый цвет×размер в каждой партии). «План по размерам» показывает их без оси этапов, распределяет по цехам по мощностям (свой первый, 2-3-й только под срок). Прогноз строится не от «сегодня», а от реалистичного старта продаж (сегодня + срок запуска), с автосдвигом сезона, если не успеваем.

Плюс движок: `planner/lib/season/forecast.js` — 14-дневный разгон годового плана (`RAMP_DAYS=14`, `rampF`), чтобы продажи стартовали «от малого к большему», а не сразу с пика (коммит `3ceb5a1`).

## Что пробовали и НЕ сработало / грабли (важно!)
- **Отдельный блок «Планы продаж по цветам» — отвергнут пользователем.** Сначала сделал per-color планы отдельным блоком (помесячные выкупы + таблица поставок). Пользователь хотел иначе: не отдельно, а **внутри «Плана продаж по дням»**, с фильтром по цвету и сворачиванием, в той же гранулярности. Переделано (см. `seasonColorPlansSection`). Урок: per-color план = масштаб сводной кривой долей цвета (лидер=1), НЕ пересчёт с нуля — иначе разойдётся с производством.
- **Слияние партий — только производство, НЕ продажи.** Важно: `mergeDeliveriesForProduction` трогает только производственные партии-довозы; помесячный план продаж остаётся как есть. Не путать.
- **Двойные слушатели при перерисовке #se-table.** Старый `bindSeasonView` на смене гранулярности вызывал сам себя и заново вешал слушатели на внешние контролы (%выкупа/пороги) и тултипы графиков. С добавлением фильтра цвета это стало плодить дубли. Разделил: `bindSeasonTableLocal` (только #se-table, реентерабельно) + `bindSeasonView` (внешние контролы один раз); `attachSeasonTip` защищён флагом `dataset.tipBound`.
- **ГЛАВНАЯ ловушка сессии: старый backend в памяти.** Пользователь `git pull` + hard-reload → браузер брал новый `app.js` (статика с диска), но **работающий Node-процесс держал старый `model.js` в памяти** (Node не перечитывает модули). Старый фильтр удалял партии-поставки без этапа → «Применить» молча создавал 0 партий (Гант «0 циклов», «нет партий»). Ушло МНОГО времени на отладку (сервер/модель/HTTP/RBAC/даты — всё чисто в изоляции). **Диагностика-победитель:** `console.log('[apply] после сохранения: партий = N')` показал «создано 3, выжило 0». **Причина:** процесс не перезапущен. **Лечение:** обязательно рестарт Node-процесса после pull. Добавлен `backendBuild` в `/api/health` + красный баннер во фронте, чтобы рассинхрон был виден сразу.
- **Порты на Mac mini:** планировщик на **8477** (env `PLANNER_PORT=8477`), а `npm start` по умолчанию лезет на 8090 (занят посторонним Python → `EADDRINUSE`). Рестарт: `lsof -ti tcp:8477 | xargs kill -9`, затем `PLANNER_PORT=8477 nohup node --experimental-sqlite server.js > ~/planner.log 2>&1 &`.
- **Даты ISO со временем:** ранний фильтр `model.js` валидировал `deadline` строгим `^\d{4}-\d{2}-\d{2}$` — не проходили даты вида `2027-04-15T00:00:00Z`. Починено: `validDeadline` режет строку до 10 символов. (В реальном плане даты были чистые, но защита нужна.)
- **`df()` — локальная в другой функции**, не глобальная → ReferenceError при повторном использовании. В каждой функции свой форматтер даты.
- **`git push` иногда молча «Everything up-to-date»** после commit в той же compound-команде. Всегда проверять `git rev-list --left-right --count origin/<branch>...HEAD` → `0 0`.
- **Планы в SQLite (не в файлах):** перезапись `data/plans/004.json` НЕ меняет то, что отдаёт сервер. Для теста плана — `savePlan()` через node пишет в БД. Старые планы (004/026) без `colorAnalysis` → блок 🧩 для них «недоступно».
- **Playwright:** `/opt/node22/lib/node_modules/playwright`, CommonJS: `import pkg from '.../index.js'; const {chromium}=pkg;`, `chromium.launch({executablePath:'/opt/pw-browsers/chromium'})`. Кнопки внутри свёрнутого `<details>` кликать через `pg.evaluate(()=>document.getElementById(id).click())` (иначе «element not visible»). Готовые скрипты в scratchpad.
- **Распределение по цветам уже работает:** `splitMatrixByShares` (per-cell Хэмилтон) кладёт КАЖДЫЙ цвет×размер в КАЖДУЮ партию (проверено: 11 цветов × 8 размеров = 88 ячеек в каждой из 3 партий, даже в П1 на 5%). Пересобирать не нужно.

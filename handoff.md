# Handoff — Этап 3: Ранг сезонности → План по размерам (этапы → поставки)

Ветка: `claude/production-plan-twv8ki`. Приложение: `planner/` (Node + Express + SQLite, SPA на ванильном JS-модуле). Работает на Mac mini у пользователя, публично через Tailscale Funnel.

## Цель
Связать «Ранг сезонности» (прогноз спроса по цветам/размерам) с производственным «Планом по размерам». Прогноз выдаёт кол-во по канон-цветам × доли размеров-диапазонов; надо свести это в матрицу партии по цветам/ряду карточки и **распределить на серию поставок** (приход на WB частями), заменив устаревшую систему «4 фиксированных этапа» на динамические поставки. Архитектура сопоставления — «C+» (авто-матч + ручные решения + обучение + ноль потерь).

Большой план на 3 листа (Ранг сезонности, План по размерам, Данные) согласован с пользователем. Развилки закрыты: **Разв.1 = вариант A** (из поставок берём только пропорции по времени, раскладываем полный цветной тираж), **Разв.2** = этапы не вырезаем, переводим в legacy, **Разв.3** = проактивный предраздел по цехам делаем опциональным тумблером на шаге 4, **Разв.4** = «Заказ ткани» откладываем (#38).

## Что изменилось
Партия перестала быть жёстко `(артикул × этап)` — теперь может жить по собственному `deadline` (дата прихода на WB) с меткой поставки. Этапы сохранены как legacy: если у партии нет `deadline`, планировщик берёт `stage.deadline` (старое поведение). Reconcile сводит прогноз в матрицу и (пока) создаёт ОДНУ партию на выбранный этап — это будет заменено на серию поставок в шаге 3. Блок 🎨 приведён в порядок по просьбе пользователя.

## Что пробовали и НЕ сработало / грабли
- **Дублирование логики фронт/движок** — ранее фронт-функции сезонности расходились с серверными и ловили ReferenceError. Урок применён: `normColor`/`canonColor` вынесены в ЕДИНЫЙ `public/colorNorm.js`, который импортят обе стороны. Сервер импортит фронтовый файл по относительному пути `../../public/colorNorm.js` — работает (сервер стартует, проверено).
- **Playwright путь**: модуль в `/opt/node22/lib/node_modules/playwright` (НЕ `/usr/lib/...`), и это CommonJS — импорт так: `import pkg from '/opt/node22/lib/node_modules/playwright/index.js'; const { chromium } = pkg;`. Запуск браузера: `chromium.launch({executablePath:'/opt/pw-browsers/chromium'})`. Готовый smoke-скрипт лежит в `scratchpad/smoke.mjs`.
- **`git push` иногда молча говорит «Everything up-to-date»** сразу после `git commit` в той же compound-команде, хотя коммит создан и HEAD впереди origin. Лечится повторным `git push` ОТДЕЛЬНОЙ командой. Всегда проверять `git rev-list --left-right --count origin/<branch>...HEAD` → должно быть `0 0`.
- **Фильтр партий в `ensurePartias`** раньше удалял любую партию с невалидным `stageId`. Если бы оставили — партии-поставки без этапа молча пропадали бы. Исправлено: партия валидна если есть артикул И (валидный этап ИЛИ свой deadline-дата).
- **`aggregateFabric` группирует по `stageIdx`** — для партий без этапа даёт `?? 99` (поздний bucket). Не роняет расчёт, но группировка ткани для поставок пока некорректна — осознанно отложено (Разв.4, #38).
- **Паритет цветов 9 vs 11** (замечание пользователя): в 🧩 меньше цветов, чем в 🎓, потому что (а) `reconcileInputs` берёт только `cq.core` (теряет `weak`), и (б) «создать новый цвет» пока не пишет цвет → нет строки в матрице. Оба чинятся в шаге 3.
- **`p.deliveries` подтверждённо доходит до фронта** (используется в графике поставок, app.js:2605/2715): элемент `{date, qty, tag, title}`, плюс `p.restockDeadline`. Серию поставок строить из этого.

# Handoff — planner / Этап 3 (остатки, неттинг, план по цветам/партиям)

Ветка: `claude/production-plan-twv8ki` · репо `solexvk/wb-headless` · приложение в `planner/`.
Билд на конец сессии: **`sizeadj-2026-08-24p`** (APP_BUILD в `public/app.js`, BACKEND_BUILD в `server.js` — держим равными).
Деплой у пользователя: Mac mini, порт 8477, supervisor поднимает заново.

## Цель
SPA планирования пошива одежды под Wildberries. Пользователь ведёт сезонный план: прогноз спроса
(«Ранг сезонности») → план по цветам/размерам → довозы (партии-поставки) → вычет реальных остатков
(WB FBW/FBS, в пути, склад, производство) → раскладка нетто по цехам → диаграмма Ганта. Цель — шить
только нужное, вовремя, комфортными партиями (дробление крупных довозов), ничего не теряя.

## Текущее состояние
Всё, сделанное в этой и прошлых сессиях, задеплоено пользователем и подтверждено. Работает:
- WB-остатки FBW+FBS по nmID; привязка загрузкой таблицы номенклатур; неттинг (живой слой);
  выгрузка «План по размерам → Excel» на НЕТТО; тумблер «Спрос / К производству».
- Объединение мелких довозов после вычета остатков (нетто < `settings.minBatch`=2000 → вперёд).
- Дробление крупных довозов на партии ≤ `settings.batchSize`=5000, раскладка по цехам.
- «Пошив не раньше» по артикулу (`article.sewNotBefore`); коэффициент ±% по рыночному цвету
  (`article.colorAdjust`); исключение цвета ✕ (`excludedColors`) — вырезается везде и из
  производства; авто-подбор цветов НЕ теряет объём (удаление — только вручную ✕).
- **Нумерация произв. партий `prodNo`** — сквозная по (ЦЕХ × АРТИКУЛ), по порядку кроя.
- **«План по размерам»: таблица произв. партий под матрицей** (Партия `id·пN`, Довоз, Цех, Шт,
  Крой→Готовность). Довоз остаётся ЕДИНЫМ редактируемым блоком спроса — пользователь это подтвердил,
  материализовать батчи в отдельные строки-довозы НЕ надо.
- **Гант**: на полосе номер артикула — первым, крупно (16px) жёлтым; номер партии `prodNo` — вторым.
- Excel-выгрузка: лист на произв. партию, имя/шапка по `prodNo`+цеху.
- **Процент выкупа для прогноза** (`article.forecastBuyoutPct`, деф. 100): MPStats даёт ЗАКАЗЫ,
  не выкупы; умножаем прогноз на %выкупа → реальные выкупы для производства (opt-in).
- **Принудительное включение размера** (`article.forceSizes`): размер ряда, не покрытый ни одним
  диапазоном спроса (напр. XL при рядах 52-56/50-52/54-56), раньше получал 0 — непокрытая доля
  размазывалась по всем размерам. Теперь чекбоксы в панели «Размеры»; отмеченный размер получает
  непокрытую спросом долю поровну (до нормировки весов). Ноль потерь сохраняется.
- **Целевой % размера** (`article.forceShare` {размер:%}): рядом с чекбоксом форс-размера — поле %;
  размеру гарантируется ровно этот вес тиража цвета, остаток делится между прочими пропорционально.
- **Доли размера по цвету** (`article.sizeAdjust` {цвет:{размер:%}}): размерная кривая одна на все
  цвета (MPStats-конкуренты); блок «⚙ Доли размера по цвету (±%)» под матрицей в «Плане по размерам»
  даёт множитель к доле размера ВНУТРИ цвета (100=как есть). Тираж цвета сохраняется (перенормировка).
  Множитель к нулю = 0 (поле заблокировано). Применяется в план по кнопке «Применить».
- **Партия ≥5000 (кроме последней)**: `settings.minBatch` по умолчанию 2000→**5000** (мелкие довозы
  сливаются вперёд цепочкой до ≥5000, хвост как есть); дробление крупного довоза `ceil→floor` в
  `scheduler.js` (равные части всегда ≥ `batchSize`, а не под ним: 21045→4×5261, было 5×4209).
  ⚠️ У пользователя в сохранённом state minBatch=2000 — надо вручную выставить 5000 в ⚙.

Не тестируется в контейнере: WB API (нет токена/сети). Остальное — изолированными node-тестами и
`node --check`.

ВНЕ ОБЛАСТИ: пользователь вставил лог из ДРУГОГО проекта `~/wb-headless-imgsearch` (vision-пайплайн
Ollama/gemma3: 305 рубашек, attrs-ступень отработала 0 ошибок). Это не наш репозиторий, задачи по

## Что изменилось (по сути)
1. Произв. партии нумеруются `prodNo` по (цех × артикул) по порядку кроя (артикул в цеху: 1,2,3…;
   другой артикул — снова с 1). Пересчёт на каждом расчёте (финал — после раскладки всех артикулов).
2. Дробление довоза видно в «Плане по размерам» таблицей; в Excel — лист на партию; на Ганте — крупно
   артикул.
3. Довоз НЕ материализуется в отдельные партии — остаётся редактируемым блоком спроса (решение
   пользователя), дробление/номера считаются живьём.

## Что пробовали и НЕ сработало (грабли — читать внимательно)
- **Дробление сначала жило только в планировщике (Гант)** — в «Плане по размерам»/Excel оставались
  3 довоза. Исправлено: у цикла `batchMatrix`, Excel — лист на батч, в «Плане» — таблица партий.
- **Материализовать батчи как отдельные партии-довозы — отвергнуто**: конфликтует с живым неттингом
  (батчи gross vs net) и мешает редактированию спроса. Пользователь ПОДТВЕРДИЛ: довоз = единый
  редактируемый блок, дробление живьём. НЕ пере-решать.
- **Расхождение план продаж vs план по размерам** (прошлая сессия): авто-подбор «просто убирал»
  слабые цвета (объём выпадал). Вернули: авто НЕ теряет объём, удаление цвета — только ✕ вручную.
- **Исключённый ✕ цвет показывался нулевой колонкой**: чинили в 4 местах (colsForMatrix, чипы,
  init-loop матрицы, computeSupplyNetting — вырезание из net).
- **FBW=0**: join по размеру карточки (techSize часто пуст, размер в wbSize) — индексируем по nmId,
  размер из строки отчёта. **FBS=0**: `wb_cards` терял skus при кэше — колонка `payload`.
- **302 при curl /api/health сразу после kill** — не ошибка, supervisor ещё поднимается; ждать ~5с.
- Флип-флоп по слабым цветам (дропать/не дропать) — оба раза по явной просьбе; итог: авто не дропает,
  ✕ дропает вручную.

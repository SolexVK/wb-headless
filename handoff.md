# Handoff — Производственный план (Этап 3)

## Цель
Инструмент планирования производства одежды. Связка: **Ранг сезонности (прогноз спроса)
→ План по размерам (матрицы цвет×размер по довозам) → Диаграмма Ганта (расписание по цехам)**.
Ключевая идея Этапа 3: динамические довозы (партии-поставки по датам прихода на WB) вместо
фиксированных этапов, и чтобы объёмы/тайминг производства вытекали из кривой сезонности.

Приложение: vanilla-JS ES-module SPA (`planner/public/app.js`) + Node/Express бэкенд
(`--experimental-sqlite`). Крутится на Mac mini пользователя, порт **8477** (`PLANNER_PORT=8477`),
наружу через Tailscale Funnel. Ветка разработки: `claude/production-plan-twv8ki`.

## Текущее состояние
Всё работает и задеплоено на Mac mini. Два последних крупных фичи этой сессии:

1. **Сезонные цвета по довозам** (commit `1fb8209`) — на «Плане по размерам» у каждого довоза
   чипы цветов (вкл/выкл). Тираж цвета делится только между отмеченными довозами. Готово, проверено
   пользователем ранее не отдельно, но математика подтверждена тестом. Фронтенд-онли.

2. **Ритм производства: окно → пауза → рестарт** (commit `1af428e`) — на «Ранге сезонности» блок
   предпросмотра: когда шить каждый довоз, пауза в межсезонье, дата рестарта. Кнопка «Применить»
   пишет `partia.earliestStart` и пересчитывает Гант. Планировщик теперь уважает «не начинать раньше».
   **Задеплоено, бэкенд подтверждён** (`/api/health` → `prod-rhythm-pause-earlieststart-2026-08-19a`).

## Что изменилось (по сути)
- **Сезонные цвета:** источник истины «цвет едет в этом довозе?» — массив `partia.colorOff` (имена
  выключенных цветов). Вес довоза для деления — `partia.deliveryShare` (лениво = объём партии при
  первом использовании, дальше не пересчитывается — иначе вес «плыл» бы). Раскладка Хэмилтоном
  (`apportionByWeights`), суммы сохраняются (ноль потерь). Нельзя выключить цвет во всех довозах.
  Оба поля — фронтенд-онли, переживают `normalizeState` (партия-луп не стрипает неизвестные поля).
- **Ритм производства:** скорость пошива = сумма `capacities.sew` цехов, доступных артикулу
  (`allowedWorkshops` или все). Для каждого plan-довоза с дедлайном: `sewStart = deadline − транзит
  − производство − риск-буфер`. Пауза = от готовности последнего довоза до рестарта. Рестарт: сезонный
  (нет `p.miniSeasons`) → следующий сезон через год; круглогодичный → ближайший мини-сезон после
  окончания пошива. «Применить» → `earliestStart` в каждый довоз → `recalc(true)`.
- **Планировщик:** был жадный форвард от `seasonStart` без пер-задачного пола (шил всё сразу, за
  месяцы вперёд). Теперь `earliestStart` создаёт реальную паузу: простой цеха возникает только когда
  нет готового задания. Обратная совместимость сохранена (без `earliestStart` расписание идентично).

## Что пробовали и НЕ сработало (грабли — читать перед работой!)
- **«Живучесть» сервера на 8477 при деплое (ГЛАВНЫЕ грабли).** На Mac mini сервер под супервизором
  (launchd/pm2/nodemon — что-то автоперезапускающее). Симптом: `git pull` + попытка вручную запустить
  `node server.js` → `EADDRINUSE`, при этом `/api/health` показывает СТАРЫЙ `backendBuild`, потому что
  порт держит старый процесс. **Диагностировать ТОЛЬКО по `backendBuild` в `/api/health`, не по
  тексту ошибки.** Рабочий рецепт деплоя бэкенда: `git pull` → `lsof -ti tcp:8477 | xargs kill -9`
  → супервизор сам поднимет НОВЫЙ код за пару секунд → `curl /api/health` для проверки. Ручной
  `node server.js` запускать НЕ нужно (он словит EADDRINUSE — это норма, супервизор уже занял порт).
- **Циркулярный вес при сезонных цветах.** Нельзя брать вес довоза из текущего объёма партии на лету:
  выключил цвет → объём партии упал → вес поменялся → восстановить цвет нечем. Решение — стабильный
  `deliveryShare`, зафиксированный один раз (лениво из объёма ДО правок цветов, когда объём ещё
  пропорционален времени).
- **zsh и многострочная вставка с кавычками/эмодзи** (`dquote>`): давать пользователю ОДНОСТРОЧНЫЕ
  команды без двойных кавычек и эмодзи.
- Раньше по проекту: community-SheetJS не пишет стили (перешли на `xlsx-js-style`); SERP-кэш травился
  пустыми выборками (не кэшируем пустое + пустой кэш = miss); `runForecast` бросает явную ошибку при
  `itemsWithData==0`. (Это уже исправлено, здесь для контекста.)

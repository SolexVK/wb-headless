# Handoff

## Цель
Инструмент планирования производства одежды под план продаж WB (папка `planner/`):
Гант, партии по цехам, заказ ткани, юнит-экономика, RBAC, контроль сроков. Идёт
большая линия «Производство 2.0» — непрерывный конвейер + «тихий контроль» + спасатель
сроков + правила настила, с прицелом на живую сеть ввода данных (Telegram) и стресс-
устойчивый авто-план. Ветка `claude/production-plan-twv8ki`, деплой на Mac mini (служба
launchd `com.wbheadless.planner`).

## Ранг сезонности (serp-v2) — ЗАКРЫТО
Раздел «Ранг сезонности»: по целевым фразам строит прогноз продаж на будущий сезон +
двухлетнюю сезонную кривую, копит планы (Часть 2). Полностью на MPStats **serp-v2**.

**Архитектура (экономия лимита — всего 150 запросов/день):**
- Источник — `POST /api/seo/keywords/<фраза>/serp-v2` (`planner/lib/season/wbSerp.js`): 1
  запрос на фразу отдаёт до 200 товаров, что РЕАЛЬНО ранжируются по фразе (поведенческая
  релевантность), у каждого — дневные графики продаж/выручки за 2 года. Сортировка по
  выручке. Итого **1–3 запроса на полный прогон** (было ~60). Кэш в БД (`wb_serp`), окна
  режутся в памяти из одной выдачи (`_serpAll` в `buildSeasonPlanReport`).
- Жёсткий контроль лимита: `mpstatsBudgetToday/Add`, статус в `/api/season/status`.
  **НИКОГДА не жечь лимит тест-скриптами** — валидировать офлайн через `SERP_FIXTURE_FILE`
  (фикстура реальной выдачи: `scratchpad/srt.json`).

**Отбор аналогов (`seasonPlanReport.js`):** нишевый ключ по 4-символьному корню (все
словоформы: муслин→«мусл» ловит «муслина»); поле «нишевое слово» (`nicheWords`); минус-слова
по стему; фильтр по МЕДИАННОЙ цене за год (устойчив к распродажам); фильтр по полу из карточки
(CDN); «Предв. выбор» — визуальный чек-бокс-отбор ТОП-30 без ключа в названии (`approvedIds`).
Витрина ТОП-15 конкурентов с фото, метрики за последний год, оборачиваемость = остаток ÷
среднесуточные продажи за год.

**Прогноз «Выкупов» (итог этой сессии — 4 правки):**
1. Синтетическая кривая (`forecast.js`) задаёт только ФОРМУ сезона (разгон/пик/распродажа),
   с ролловером года вперёд от «сегодня».
2. Уровень ТОП-3/ТОП-1 = скорость лидеров по выручке за ПОСЛЕДНИЙ ГОД ÷ активные дни
   (`activeDaysLY`) — не ÷ всё окно (распроданные/новые не занижают).
3. ОБЪЁМ прибит к реальности: `Выкупы` = фактические продажи ТОП-1 (или среднего ТОП-3)
   финальной выборки за ТОТ ЖЕ сезон в последнем полном году (`seasonTargets`, множитель
   формы на дневной план+остатки+поставки, склад→0 к концу).
4. Проекция РОСТА рынка: год-к-году на одинаковом сезонном куске двух свежих лет,
   компаундируется на число лет до прогноза. `plan.growthMode`: 'market' (по умолчанию,
   выбор пользователя) | 'none'; годовой рост зажат [0.5, 2.0]. Видно в карточке «Выкупы».

**Файлы:** `wbSerp.js` (НОВЫЙ, serp-v2 клиент), `seasonPlanReport.js` (движок сбора+плана),
`forecast.js` (кривая сезона), `seasonApi.js` (runForecast/runCandidates), `db.js` (wb_serp,
season_searches, budget), `server.js` (`/api/season/{build,candidates,status}`), `app.js`
(конструктор + накопитель; `APP_BUILD='season-serp-2026-07-28p'`).

**Грабли:** ценовой фильтр 0 трактуется как «нет ограничения» (в тесте не передавай 0 как
min/max — режет всё); serp endRow ≤ 200 (иначе HTTP 422); скорость лидеров считать только по
крупным ПО ВЫРУЧКЕ (не «быстрым за активный день» — товар, живший 2 мес, ложно попадал в ТОП);
рост рынка ≠ рост карточки (рынок ×1.79 раздут новичками, когорта/лидеры ×1.25–1.37).

## Что пробовали и НЕ сработало (грабли — читать!)
- **Пооперационный ручной журнал (первый заход 3a) — тупик.** Ввод дат крой/пошив/утюжка/
  ОТК на каждую партию — мёртвая система, никто вручную вести не будет (слова пользователя).
  Развернули на «тихий контроль» (статус+даты авто). Пооперационный ввод остался опциональным
  «разбором» в окне Ганта. МОРАЛЬ: минимизируй ручной ввод, опирайся на уже делаемое (статус)
  и события.
- **Спасатель: «перетасовка» с разморозкой авто-назначений давала «затронуто 16 партий»** —
  по сути полный перепланинг, а не точечное спасение (артефакт: авто-партии при повторном
  прогоне назначаются иначе). Убрали. Оставили ТОЛЬКО чистое переназначение с заморозкой
  (двигаются лишь даты у помощника) + настил-дробление + эскалацию. МОРАЛЬ: «минимум
  возмущения» важнее «оптимальности»; замораживай план перед пробным переносом.
- **Спасатель редко находит whole-reassign на тесном Aug-1 дедлайне** — это НЕ баг: все
  конкурируют за срок, любой перенос двигает чужую stage1-партию за дедлайн → честная
  эскалация. На дедлайнах с запасом (окт/дек/фев) переназначение находится легко. Ветку
  настил-дробления трудно спровоцировать — whole-reassign покрывает почти всё (свойство домена).
- **Детерминизм движка**: `new Date()` в ядре для «сегодня» — ок, но в тестах передавай
  planningDate явно (иначе недетерминизм).
- (прошлые сессии, актуально) «бесконечные» партии = мощность пошива цеха задана 1
  (нормализация Math.max(1,...)); при странных датах сперва проверь мощности. `fmt` в gantt.js
  не показывает год. Новые top-level поля state — не забывать в permissions.js applyWritePolicy.

# Handoff — сервер netcup, planner и доступы

Дата: 04.09.2026. Ветки: **`claude/server-setup-fmrhlf`** (инфраструктура, скрипты, документация)
и **`claude/production-plan-twv8ki`** (код planner — с неё развёрнуты боевой и демо-экземпляры).
Пуш в обе разрешён пользователем.

## Цель

Перевезти рабочие инструменты с общего Mac Mini на собственный VPS (netcup), чтобы сервисы жили
на управляемом сервере с доменом, HTTPS и бэкапами. Схема как на Mac Mini, но без Tailscale Funnel:
наружу смотрит только Caddy, сервисы слушают `127.0.0.1:<порт>`. Первый переехавший сервис —
planner («производственный план»), к нему нужен разграниченный доступ для сотрудников и публичная
демо-витрина.

## Текущее состояние

Работает:

- **Сервер**: Debian 13, вход только по ssh-ключу, ufw (22/80/443), fail2ban, автообновления,
  swap, Node 22, Caddy с Let's Encrypt.
- **wb-headless** — `https://tools.aidemiko.ru/wb/`, порт 8080, systemd `wb-headless.service`.
- **planner (боевой)** — `https://planner.aidemiko.ru/`, порт 9100, `planner.service`,
  база с Mac Mini перенесена целиком (`planner.db` ~117 МБ, `samples/`, `plans/`, `wb-cache/`),
  launchd-агент на Mac Mini выключен (plist переименован в `.off`).
- **planner ДЕМО** — `https://demo.aidemiko.ru/`, порт 9101, `planner-demo.service`,
  данные вымышленные (сид репозитория), вход без входа: открыл адрес — смотришь.
- **Доступ**: только через Telegram-бота `@aidemiko_planner_bot`. Владелец — по
  `OWNER_TELEGRAM_ID`. Сотрудники — по членству в рабочей группе (`STAFF_CHAT_ID`,
  проверка `getChatMember` при входе + фоновая раз в час). Посторонним отказ.
  Проверено: лог показывает «сотрудники — по членству в группе …», `getChatMember`
  возвращает `status: creator` для владельца.
- **Бэкапы** — скрипт написан и запушен (`50-install-backups.sh`), но **на сервере ещё не
  установлен** (см. «Следующий шаг»).

Не сделано:

- свежий снапшот в панели netcup (существующий `base-debian13-node-wbheadless` сделан ещё до
  Caddy, домена и planner);
- PR #14 не влит, сервер продолжает жить на ветке `claude/server-setup-fmrhlf`;
- вход сотрудника из группы вживую ещё не проверялся (проверял только владелец);
- выгрузка бэкапов наружу (на Mac Mini) — только рекомендация в документации.

## Что изменилось

**Переезд planner.** Код в `/opt/planner` (ветка planner), systemd вместо launchd, порт
`127.0.0.1:9100` вместо `0.0.0.0:8090`, наружу — через Caddy на отдельном поддомене
(поддомен, а не путь: во фронтенде 68 абсолютных `/api/…` и `/admin`).

**Модель доступа.** Было: автоприём любого Telegram-аккаунта. Стало: единственное условие —
членство в рабочей группе. Ушли ссылки-приглашения с кодами (пользователь прямо сказал, что
раздавать хвосты под каждого человека он не будет); коды остались отключённым запасным путём.
Демо открывается без всякой ссылки (`GUEST_AUTO=1`).

**Права.** Роль `staff`: просмотр Ганта, плана по размерам, сезонности и отчётов + выгрузки;
юнит-экономика — личный черновик в браузере (localStorage), в общую базу не пишется.
Закрыты дыры: три вкладки вообще отсутствовали в модели прав; архив отчётов и «Сокращение»
висели на праве «Данные»; `google/export` и `google/disconnect` требовали лишь право просмотра.

**Демо-данные.** Генерируются сидом репозитория (вымышленная фабрика), копирование боевой
базы удалено из кода полностью.

**Бэкапы.** Ежедневный снимок базы и конфигов с ротацией.

## Что пробовали и НЕ сработало

1. **Демо как обезличенная копия боевой базы** (первая версия, `anonymize-db.mjs`). Заменял
   названия и искажал цены. Пользователь справедливо забраковал: копия остаётся настоящим
   производственным планом — те же сроки, партии, размерные раскладки, число моделей. Плюс
   каждая правка обезличивателя — шанс что-то забыть. **Заменено** генерацией данных с нуля;
   анонимизатор удалён, чтобы им не воспользовались по инерции.

2. **`cp` живой базы SQLite** — копия оказалась неполной: часть данных лежала в WAL-журнале,
   в скопированном файле не было даже таблицы состояния. **Правильно:** `VACUUM INTO` (используется
   и в бэкапах, и в демо-стенде).

3. **Снимок базы под пользователем `planner` прямо в каталог демо** — `unable to open database file`:
   каталог принадлежит `plannerdemo`. **Обход:** снимок во временный каталог владельца базы,
   дальше root переносит файл.

4. **`npm install` в каталоге развёртывания ломал обновление кода.** Он создаёт
   `package-lock.json`; как неотслеживаемый файл тот блокировал `git checkout` («would be
   overwritten by checkout»), скрипт обрывался, и на стенд не приезжал ни генератор данных,
   ни исправление кнопок — при этом снаружи всё выглядело обновлённым. Это причина, по которой
   демо несколько итераций показывало реальные данные. **Исправлено:** `checkout -f`,
   `npm --no-package-lock`, файл в `.gitignore`, плюс контроль содержимого демо-базы после сидинга.

5. **Проверка «сервис защищён» по `/api/health`** — этот адрес публичный по замыслу, при
   Telegram-авторизации отдаёт 200, и скрипт печатал ложное «авторизация ВЫКЛЮЧЕНА».
   **Исправлено:** проверяется корень сайта (302 — Telegram, 401 — пароль, 200 — открыто).

6. **Режим «только просмотр» блокировал все кнопки без пометки** — наблюдатель не мог ни
   построить отчёт (он считается в браузере!), ни скачать Excel/PDF, хотя выгрузки ему положены.
   **Исправлено:** атрибут `data-ro-ok` на действиях, которые ничего не меняют.

7. **Баннер песочницы удалялся сразу после добавления** — существующий код снимал элемент по
   селектору `.ro-banner`, под который попал и мой баннер. **Исправлено:** `:not(.sandbox)`.

8. **Обращение к `GUEST_AUTO` до объявления** (temporal dead zone) — сервис упал бы при старте.
   Поймано до отправки пользователю запуском реального сервера.

9. **`sudo sh -c 'source …'`** — dash не знает `source`, нужен `bash -c` или `.`.

10. **`git pull` в `/opt/planner*` под `deploy`** — «dubious ownership» (каталоги принадлежат
    системным пользователям). Обновлять от root с `safe.directory`, затем возвращать владельца.

11. **`pkill -f "planner/server.js"` в этой среде убивает и собственную оболочку** (шаблон
    совпадает с командной строкой самого процесса) — гасить по конкретному PID.

12. **Секреты в чате.** Пользователь дважды присылал сгенерированные коды (в т.ч. дающий вход
    владельцем). Оба заменены. Правило: коды и токены в переписку не копировать.

## Команды для проверки

Формальных тестов в репозитории нет. Проверяется так:

```bash
# синтаксис (в корне репозитория)
bash -n deploy/vps/*.sh
node --check server.js

# planner (ветка claude/production-plan-twv8ki)
node --check planner/server.js
node --check planner/lib/authMiddleware.js
node --check planner/public/app.js

# живой прогон planner локально (создаёт planner/data — потом удалить)
cd planner && npm install --omit=dev --ignore-scripts --no-audit --no-fund --no-package-lock && cd ..
PLANNER_PORT=9310 PLANNER_HOST=127.0.0.1 SESSION_SECRET=t \
  node --experimental-sqlite planner/server.js
curl -s localhost:9310/api/health          # {"ok":true,...}

# сервер снаружи
curl -s -o /dev/null -w '%{http_code}\n' https://planner.aidemiko.ru/   # 302 → /login
curl -s https://planner.aidemiko.ru/api/me                              # authEnabled: true
curl -s -o /dev/null -w '%{http_code}\n' https://demo.aidemiko.ru/      # 302, дальше гость
curl -s https://tools.aidemiko.ru/wb/health                             # {"ok":true,...}

# на сервере
sudo journalctl -u planner -n 12 --no-pager | grep 'planner\]'
sudo systemctl status planner planner-demo wb-headless caddy --no-pager
```

**Ожидаемое состояние:** все `bash -n` и `node --check` — зелёные. Снаружи `planner.aidemiko.ru`
отдаёт 302 на `/login`, `demo.aidemiko.ru` пускает гостя, `tools.aidemiko.ru/wb/health` — `{"ok":true}`.
В логе planner три строки: авторизация включена, «сотрудники — по членству в группе -1003319802430»,
«слушает 127.0.0.1:9100». Красных проверок быть не должно. Единственное известное отклонение —
`planner-backup.timer` на сервере ещё не установлен (скрипт не запускали).

## Следующий шаг

Установить бэкапы на сервере — это единственное незакрытое место, где данные существуют
в одном экземпляре:

```bash
sudo git -C /opt/wb-headless pull && sudo chown -R wbheadless:wbheadless /opt/wb-headless
sudo bash /opt/wb-headless/deploy/vps/50-install-backups.sh 2>&1 | tail -15
```

Ожидаем: таймер включён, первая копия создана, в `/var/backups/planner` лежит архив.
Затем — снапшот в панели netcup (Media → Snapshots → Create, тип Offline).

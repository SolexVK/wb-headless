# Handoff — planner / Этап 3 (остатки, неттинг, план по цветам/партиям)

Ветка: `claude/production-plan-twv8ki` · репо `solexvk/wb-headless` · приложение в `planner/`.
Билд на конец сессии: **`batch-sheets-2026-08-22j`** (APP_BUILD в `public/app.js`, BACKEND_BUILD в `server.js` — держим равными).
Деплой у пользователя: Mac mini, порт 8477, supervisor поднимает заново.

## Цель
SPA планирования пошива одежды под Wildberries. Пользователь ведёт сезонный план: прогноз спроса
(«Ранг сезонности») → план по цветам/размерам → довозы (партии-поставки) → вычет реальных остатков
(WB FBW/FBS, в пути, склад, производство) → раскладка нетто по цехам → диаграмма Ганта. Цель — шить
только нужное, вовремя, комфортными партиями, ничего не теряя.

## Текущее состояние
Всё, сделанное в этой сессии, задеплоено пользователем и подтверждено. Работает:
- WB-остатки FBW+FBS по nmID; привязка загрузкой таблицы номенклатур; неттинг (живой слой);
  выгрузка «План по размерам → Excel» на НЕТТО; тумблер «Спрос / К производству» на листе.
- Объединение мелких довозов после вычета остатков (нетто < мин.партии → в следующий довоз).
- «Пошив не раньше» — сезонное окно старта по артикулу (`article.sewNotBefore`).
- Слабые цвета (<3%) больше НЕ удаляются авто-подбором (только распределяются по сезону); удалять
  цвет — вручную кнопкой ✕ в «Ранге» (`excludedColors`, с пересчётом объёма).
- Ручной коэффициент ±% к «Кол-ву к пошиву» по рыночным цветам (`article.colorAdjust`).
- Исключённые цвета (✕) убраны из матрицы/чипов/Ганта/производства (фикс в 4 местах).
- **Дробление крупных довозов на партии ≤ `settings.batchSize` (5000)** — по цехам; видно на Ганте,
  в «Плане по размерам» (строка разбивки) и в Excel (лист на каждую произв. партию, «Довоз N ·
  партия K из M · цех»).

Не тестируется в контейнере: WB API (нет токена/сети). Всё остальное — изолированными node-тестами
и `node --check` (см. ниже).

- `planner/public/gantt.js` — подпись «п.K/M» на баре батча + в тултипе.

## Что изменилось (по сути)
1. Остатки WB (FBW+FBS) → неттинг → нетто в цех/Гант/Excel. План по размерам на экране — эталон
   спроса (живой слой), но есть тумблер «К производству (нетто)».
2. Мелкие довозы после вычета остатков сливаются вперёд; крупные — дробятся на партии ≤5000 по цехам.
3. Слабые/исключённые цвета: авто-подбор не теряет объём; удаление — ручное (✕), с пересчётом;
   исключённые нигде не показываются и не шьются.
4. Ручной коэффициент ±% по цвету + «Пошив не раньше» по артикулу.

## Что пробовали и НЕ сработало (грабли — читать внимательно)
- **FBW-остатки = 0**: join шёл по «nmId|размер-карточки», а у карточек Content API `techSize` часто
  ПУСТОЙ (размер в `wbSize`). Индексируем остатки по nmId, размер берём из строки отчёта.
- **FBS всегда 0 при «штрихкодов 0»**: таблица `wb_cards` в SQLite сохраняла только габариты и молча
  теряла skus/sizes/color при кэш-раунд-трипе. Лечится колонкой `wb_cards.payload`. Диагностика
  «штрихкодов запрошено 0» = верный индикатор этой болезни.
- **Старый `/api/v1/supplier/stocks` → 404 deprecated** — не воскрешать; FBW только через
  Seller Analytics `warehouse_remains` (асинхронный отчёт ~до 2 мин, кэш 1ч).
- **Расхождение план продаж 110к vs план по размерам 70к**: это был НЕ баг переноса (перенос кладёт
  полные 111к). Причина — авто-подбор «просто убирал» слабые цвета (объём выпадал). По просьбе
  пользователя вернул: авто-подбор объём не теряет, удаление цвета — вручную ✕.
- **Дробление сначала сделал только в планировщике (Гант)** — в «Плане по размерам» и Excel
  оставались 3 довоза. Пользователь заметил. Исправлено: у цикла есть `batchMatrix`, Excel — лист
  на батч, в «Плане по размерам» — строка разбивки. Довозы НЕ материализуются как отдельные партии
  (остаются одним редактируемым блоком спроса; дробление считается живьём).
- **Исключённый ✕ цвет всё равно показывался** колонкой с нулями: `colsForMatrix` отдавала все
  активные цвета, матрица инициализировала их нулями, чипы брали `activeColors`, планировщик видел
  их в planMatrix. Пришлось чинить в 4 местах (colsForMatrix, чипы, init-loop, computeSupplyNetting).
- **302 при curl /api/health сразу после kill** — не ошибка: supervisor ещё не поднял сервер; ждать
  ~5 сек и повторить.
- Флип-флоп по слабым цветам (сначала «дропать», потом «вернуть выбор пользователю») — оба раза по
  явной просьбе; итог: авто НЕ дропает, ✕ дропает вручную. Не пере-решать без пользователя.

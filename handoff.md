### «Ранг сезонности» (serp-v2) — как устроено
- **Источник** — `POST /api/seo/keywords/<фраза>/serp-v2` (`planner/lib/season/wbSerp.js`):
  1 запрос на фразу → до 200 товаров, что РЕАЛЬНО ранжируются по фразе (включая те, где в
  названии нет ключа), у каждого дневные графики продаж/выручки за 2 года. Сортировка по
  выручке. Кэш в БД (`wb_serp`), окна режутся в памяти из одной выдачи (`_serpAll`).
- **Лимит MPStats — жёстко 150/день.** `mpstatsBudgetToday/Add`, статус в `/api/season/status`.
  Валидация — ТОЛЬКО офлайн через `SERP_FIXTURE_FILE` (фикстура: `scratchpad/srt.json`).
- **Отбор аналогов** (`seasonPlanReport.js`): нишевый ключ по 4-символьному корню (ловит все
  словоформы: «мусл»→«муслина»); поле «нишевое слово» (`nicheWords`); минус-слова по стему;
  фильтр по МЕДИАННОЙ цене за год (устойчив к распродажам); фильтр по полу из карточки (CDN);
  «Предв. выбор» — чек-бокс-отбор ТОП-30 без ключа в названии (`approvedIds`). Витрина ТОП-15
  с фото; метрики за последний год; оборачиваемость = остаток ÷ среднесут. продажи за год.
- **Прогноз «Выкупов»** (4 правки этой сессии, по порядку):
  1. Кривая (`forecast.js`) задаёт только ФОРМУ сезона (разгон/пик/распродажа), год катится
     вперёд от «сегодня».
  2. Уровень ТОП-3/ТОП-1 = скорость лидеров по выручке ÷ активные дни за год (`activeDaysLY`),
     не ÷ всё окно.
  3. ОБЪЁМ прибит к факту: `Выкупы` = реальные продажи ТОП-1 (или среднего ТОП-3) финальной
     выборки за ТОТ ЖЕ сезон в последнем полном году; множитель формы на план+остатки+поставки.
  4. Проекция РОСТА рынка: год-к-году на одинаковом сезонном куске двух свежих лет,
     компаундируется на число лет до прогноза. `plan.growthMode`: `'market'` (по умолчанию —
     выбор пользователя) | `'none'`; годовой рост зажат [0.5, 2.0].

## Что изменилось (смысл)
- Раньше «Выкупы» = сумма синтетической кривой, отмасштабированной по ПИКУ (скорость лидера ×
  сезонный индекс). Это давало ~2× переоценку и не учитывало ни распроданность лидеров, ни рост.
- Теперь: форма — синтетическая, а ОБЪЁМ — реальный (сколько лидер(ы) продали за аналогичный
  сезон) × измеренный рост рынка на годы вперёд. Точнее и «амбициознее» через выбор ТОП-1/рынок.
- Оборачиваемость в ТОП-15 починена (serp даёт только текущий остаток → остаток ÷ продажи/год).

## Что пробовали и НЕ сработало (грабли — читать!)
- **Жгли суточный лимит MPStats тест-скриптами** — пользователь дважды злился. Тест-скрипты в
  обход бюджета приложения = сожжённый общий лимит (150/день). МОРАЛЬ: **никаких живых запросов
  к MPStats при разработке.** Только офлайн через `SERP_FIXTURE_FILE=scratchpad/srt.json`.
- **Ценовой фильтр 0 в тесте резал всё.** В движке `priceMin/priceMax=0` трактуется как «нет
  ограничения», но если в тест передать `priceMax:0` буквально — отфильтрует всё (>0 режется).
  В тестах передавай `null`, не `0`.
- **Скорость «за активный день» пускала мусор в ТОП-3.** Если брать 3 самых быстрых по
  unitsSold/activeDays — наверх лезет товар, живший на витрине 2 месяца (продавал бойко, но
  всего ~4300 шт/год против 21800 у лидера). Исправлено: ТОП-3/ТОП-1 = самые КРУПНЫЕ ПО ВЫРУЧКЕ,
  и уже ИХ скорость в сезон. Тогда ТОП-1 ≥ среднего ТОП-3 (интуитивно верно).
- **Рост рынка ≠ рост карточки.** Весь рынок вырос ×1.79 г/г, но это раздуто НОВЫМИ продавцами;
  когорта (те же товары оба года) и лидеры — ×1.25–1.37. Пользователь сознательно выбрал «весь
  рынок ×1.79» (агрессивно, ×3.2 за 2 года). Переключатель `growthMode` оставлен на будущее.
- **serp endRow > 200 → HTTP 422** («Некорректный диапазон страницы»). Максимум 200 строк/запрос.
- **404 на Mac mini давал пустой toast** (HTTP/2, пустой statusText) — чинили показом `HTTP <code>`;
  первопричина — не рестартнули службу после деплоя. После `git pull` ВСЕГДА `launchctl kickstart`.
- (Производство 2.0, прошлые сессии, всё ещё актуально) пооперационный ручной журнал — мёртвая
  система (ушли на «тихий контроль» по статусу); спасатель с разморозкой авто-назначений давал
  «затронуто 16 партий» (полный перепланинг) — оставили только заморозку+точечный перенос;
  «бесконечные» партии = мощность пошива 1; новые top-level поля state — не забывать в
  `permissions.js applyWritePolicy`.

# Handoff — Этап 3: Ранг сезонности → План по размерам (этапы → поставки)

Ветка: `claude/production-plan-twv8ki`. Приложение: `planner/` (Node + Express + SQLite, SPA на ванильном JS-модуле). Работает на Mac mini у пользователя (`openclaw@Mac-mini-Vital`), публично через Tailscale Funnel. **Планировщик запущен на порту 8477** (не 8090 — 8090 занят посторонним Python-приложением).

## Цель
Связать «Ранг сезонности» (прогноз спроса) с производственным «Планом по размерам». Прогноз → матрица цвет×размер → **серия партий-поставок** (приход на WB частями), с заменой устаревших «4 этапов» на динамические поставки, распределением по цехам по мощностям, и реалистичным стартом плана продаж с учётом времени на запуск. Архитектура сопоставления цветов — «C+».

**Три правки по листу «Ранг сезонности» (последняя итерация) — ГОТОВО и запушено:**
1. **🧩 == 🎨** (коммит `c331dc0`): пер-цветовое кол-во в блоке «План по размерам из прогноза» теперь точно совпадает с блоком 🎨. Починка в `reconcile.js`: непокрытые размерные доли **перераспределяются** на существующие размеры (нормировка весов к 1), полное кол-во цвета попадает в матрицу.
2. **Планы продаж по цветам** (коммит `787d6b6`): раньше был отдельный блок «📊 Планы продаж по цветам» — пользователь его отверг. 3. **Слияние мелких партий года** (коммит `c331dc0`): для круглогодичного плана при дроблении на довозы, если партия < `MIN_PROD_BATCH=2000` шт, соседние месяцы **сливаются** (сен 1189 + окт 1567 = 2756), дата = ранний месяц, тег «Довоз сен–окт 26». **План продаж остаётся помесячным** — сливаются только производственные партии. `mergeDeliveriesForProduction()` в `app.js`, применяется и в предпросмотре, и в `applyReconcile`.

## Что изменилось (суть)
Партия перестала быть `(артикул × этап)` — теперь `(артикул × поставка)` со своим сроком WB. «Применить» в Ранге создаёт серию партий-поставок (доли по времени × полный цветной тираж, Хэмилтон — каждый цвет×размер в каждой партии). «План по размерам» показывает их без оси этапов, распределяет по цехам по мощностям (свой первый, 2-3-й только под срок). Прогноз строится не от «сегодня», а от реалистичного старта продаж (сегодня + срок запуска), с автосдвигом сезона, если не успеваем.

Плюс движок: `planner/lib/season/forecast.js` — 14-дневный разгон годового плана (`RAMP_DAYS=14`, `rampF`), чтобы продажи стартовали «от малого к большему», а не сразу с пика (коммит `3ceb5a1`).

Ловушка при проверке в NODE: браузерный bundle при виде `module`/`require` пытается `require("./cpexcel.js")` (его нет) → падает; в БРАУЗЕРЕ этого пути нет, использует UTF-8 фолбэк. Проверял стили в node через `require(...)` с предопределённым `global.cptable`-стабом + `XLSX.write(...,{type:"buffer"})` → в `xl/styles.xml` появляются `fgColor rgb="FF..."`, кириллица в worksheet целая. API совместим (aoa_to_sheet/sheet_to_json/read/writeFile) — шаблон-экспорт/импорт не сломались.
- **Скрытие пустых размеров ломало вставку из буфера.** Если прятать нулевые строки/архивные столбцы в РЕДАКТИРУЕМОЙ сетке, `onMatrixPaste` (маппил по `a.sizes`/`a.colors`) съезжал на скрытые ячейки. Починка: вставка раскладывается по ВИДИМЫМ `visSizes`/`visCols`. Плюс тумблер «показать все размеры» (`mxAllSizes`), чтобы можно было ввести объём в пустой размер. `rowsForMatrix` при ПОЛНОСТЬЮ пустой матрице возвращает весь ряд (иначе в новую партию некуда вводить).
- **Архив цветов/артикулов — «спрятать, но не потерять».** Цвета: `colsForMatrix` показывает архивный цвет, если в нём ЕСТЬ данные (иначе архивация молча съела бы количества). Артикулы: `article.archived` — данные и партии сохраняются; фильтрация через единый `articlesSorted()` (отдаёт только активные) каскадит на все селекторы; backend `scheduler` пропускает партии архивных (нужен был рестарт — менялся `BACKEND_BUILD`).

## Цель
Раздел **«Ранг сезонности»**: по предмету WB собрать РЕЛЕВАНТНЫХ конкурентов-аналоги
(напр. именно МУСЛИНОВЫЕ женские рубашки, а не все подряд), построить ранг сезонности и
план продаж. Старый подход (плюс/минус-слова + строгий ключ + словарь признаков +
«неопределённые») пользователь признал **провалившимся**: фильтр резал не то и оставлял
нерелевантное. Нужен другой подход — это и есть текущий незавершённый блок.

Рабочий новый пайплайн (проектируется):
```
1. category (1 запрос) → топ предмета по выручке + дневные графики
2. card.json (БЕСПЛАТНО, WB CDN, вне квоты) → название+описание+характеристики
3. ПРЕДФИЛЬТР по целевому слову в тексте карточки → 900 → ~50–150 муслин-кандидатов (бесплатно)
4. by_keywords ТОЛЬКО по кандидатам → доля целевого трафика ≥ порога (~20%)
5. Кэш by_keywords 30 дней → повторные отчёты почти бесплатны
6. Дневные данные из графиков категории → ранг + план (движок seasonPlanReport)
```
UI упростится до: **предмет + целевые слова + порог доли + Построить** (+ прогресс %).
Убрать: словарь признаков, плюс/минус-чипы, «неопределённые», строгий ключ (mustHave).

## Что изменилось
1. **Стратегический разворот.** Отказ от определения релевантности «нашими словами»
   (плюс/минус/признаки) в пользу **реальных поисковых фраз товара** из MPStats `by_keywords`:
   товар релевантен, если ДОЛЯ его трафика по целевым словам ≥ порога.
2. **Найден и подтверждён рабочий эндпоинт** `GET /wb/get/item/{nmId}/by_keywords` и его формат
   (`words: { фраза: { traffic_volume:[…], pos:[…] } }`).
3. **Вскрыт суточный лимит MPStats** как главное ограничение дизайна → пайплайн переведён на
   экономию запросов (бесплатный предфильтр карточками + by_keywords только по кандидатам + кэш 30д).
4. Добавлен инфраструктурный клиент `wbKeywords.js` с честной обработкой лимита (не молчаливые нули).

## Что пробовали и НЕ сработало (важно!)
- **Старый фильтр слов/признаков** — провал по сути: плюс=«любое из» на ~40 общих словах пропускает
  почти любую хлопковую рубашку; «муслин» вообще не попадал в плюсы; воронка по выручке вымывает нишу
  (муслин в длинном хвосте); минус «прозрачная» выкидывало полупрозрачный муслин. НЕ возвращаться.
- **Публичный поиск WB (`search.wb.ru`, v4/v9, ru/sng)** — HTTP 429 и с сервера, и с Mac mini
  (метит не-браузерный/не-резидентный трафик, срабатывает после первых же запросов). Мёртв, не закладываться.
- **MPStats `/wb/get/search`** — при любых теле/параметрах отдаёт `200` с ПУСТЫМ телом (тупик).
  **`/wb/get/keyword(s)`** — требует `path`=категория и особый `filterModel`; наугад не подобрать
  (всегда `422 «Не корректные условия фильтра»`). **`/keywords/expanding|report`** — фейковые роуты
  («Method not allowed: OPTIONS»). Всё заброшено в пользу `by_keywords`.
- **by_keywords по ВСЕЙ категории (сотни–тысячи запросов/отчёт)** — выжигает суточную квоту за один
  прогон: пробник v7 (~900 запросов) → `429 «Превышен лимит запросов за 25.07.2026»`, после чего
  заблокированы И by_keywords, И category до след. суток. Отсюда обязательный предфильтр карточками
  (бесплатно) + кэш + потолок `budget`. Скорость by_keywords ~0.12–0.14с/товар (сам по себе быстрый).
- **Пробник глотал ошибки как «нет данных»** — 52% «фейлов» в v7 выглядели как «у товаров нет ключей»,
  а по факту это был лимит. Мораль (учтено в wbKeywords.js): РАЗЛИЧАТЬ 429-лимит / пусто / сетевой сбой.
- **Правило «ранжируется хоть по одной целевой фразе»** — слишком слабое: льняная рубашка цеплялась
  за муслин-фразу с трафиком 178 (доля 0%). Заменено на **порог ДОЛИ целевого трафика (~20%)**.
- **Grale деплоя (в силе):** после git pull ОБЯЗАТЕЛЬНО `launchctl kickstart -k
  gui/$(id -u)/com.wbheadless.planner`; браузер — Cmd+Shift+R, сверять `APP_BUILD` в консоли.
  У пользователя `cd planner` часто лишний (он уже там). Многострочный heredoc в терминал НЕ вставлять
  (zsh спотыкается) — коммитить скрипт в репо и запускать оттуда.

## Открытые вопросы (нужно решение пользователя)
1. **Суточный лимит MPStats — сколько запросов (ЖДУ ОТВЕТА).** Пользователь смотрит число в ЛК
   MPStats (раздел тарифа/API). Нужно для потолка `budget` by_keywords на отчёт. Рекомендация без
   числа — консервативно ~400 + предфильтр карточками.
2. **Порог доли целевого трафика** — по умолчанию 20% (ползунок в UI). На данных 20% давал чистый
   муслин. Рекомендация: 20%, скорректировать после первого боевого прогона. ЖДУ подтверждения.
3. **Целевые слова** — вводит пользователь (напр. «муслин, марлевк»). Синонимы важны (марлевка=муслин).
4. **Отложено (не начинать без старта):** расширение через ключи топ-конкурентов (их by_keywords →
   сбор фраз); связка «Pб-коридор ↔ сезонность»; экспорт/отчёты из БД.

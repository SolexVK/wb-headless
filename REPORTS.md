# Регулярный отчёт: наличие товара и упущенная выручка

Отчёт показывает по каждому SKU:

- сколько дней за период товар **реально был в наличии** (остаток > 0);
- сколько дней он **простоял в нуле** (out-of-stock);
- **упущенную выручку** — сколько бы продали в дни простоя, будь товар на складе.

Данные берутся из MPSTATS (отчёт «по дням» по товару, `wb_item_sales`).

## Методология упущенной выручки

Прозрачная и воспроизводимая (см. `lib/stockReport.js`):

1. По дневному ряду считаем дни с остатком > 0 (в наличии) и дни с остатком = 0 (простой).
2. Средние продажи в день считаем **только по дням в наличии** — иначе нули из дней простоя занизили бы спрос:
   `avgDailyUnits = проданные штуки / дни_в_наличии`
3. Средняя цена = `выручка / проданные штуки` (если API не отдал выручку — среднее по дням с продажами).
4. `Упущено штук = avgDailyUnits × дни_простоя`
   `Упущенная выручка = упущено штук × средняя цена`

## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `MPSTATS_TOKEN` | да | — | Токен MPSTATS (заголовок `X-Mpstats-TOKEN`) |
| `API_KEY` | да (для HTTP) | `supersecret` | Ключ доступа к эндпоинтам сервиса (заголовок `x-api-key`) |
| `REPORT_DAYS` | нет | `30` | Длина периода по умолчанию (в днях) |
| `REPORT_CONCURRENCY` | нет | `5` | Число параллельных запросов к MPSTATS |
| `MPSTATS_BASE_URL` | нет | `https://mpstats.io/api` | База API |
| `MPSTATS_ITEM_SALES_PATH` | нет | `/wb/get/item/{sku}/sales` | Шаблон пути к отчёту по товару |
| `REPORT_SCHEDULE_ENABLED` | нет | `0` | `1` — включить встроенный ежедневный планировщик |
| `REPORT_SCHEDULE_HOUR` | нет | `6` | Час запуска планировщика (UTC) |

Список товаров лежит в `config/skus.json` — связка **WB-артикула (SKU)** и
**артикула продавца**:

```json
{
  "items": [
    { "wb": 535397255, "seller": "001 РМК-твид бордовый" }
  ]
}
```

### Выбор подмножества товаров (экономия лимита)

Чтобы не опрашивать все 206 товаров (и не жечь суточный лимит MPSTATS),
можно собрать отчёт только по нужным. Два способа:

**A. Группа (линейка) — выпадающий список.** Самый удобный: в форме
«Run workflow» поле **group** — выбираешь линейку из списка (РМП, МС,
Муслin, «Все»…), печатать ничего не нужно. Группы описаны в
`config/groups.json` (метка → список WB-артикулов). Источники:
`REPORT_GROUP` (CLI/сервис), `&group=` (HTTP).

**B. Точечный фильтр — текстом.** Для выбора конкретных товаров или
комбинаций: поле **filter** / `REPORT_FILTER` / `&filter=`. Если задан,
**перебивает** выбор группы.

Правила фильтра (токены через запятую, регистр не важен):

| Пример фильтра | Что выберет |
|---|---|
| *(пусто)* | все товары |
| `РМП` | все, где в артикуле продавца встречается «РМП» |
| `002_РМП_белый, 016 МС голубой` | два конкретных товара |
| `535397255` | по числовому WB-артикулу (SKU) |

Товар попадает в выборку, если **любой** токен совпал: числовой токен
сверяется с WB-артикулом, текстовый — ищется внутри артикула продавца.

## Запуск

### 1. Разово из командной строки

```bash
# период = последние REPORT_DAYS дней
MPSTATS_TOKEN=xxxxx npm run report:stock

# явный период
MPSTATS_TOKEN=xxxxx node report-stock.js 2026-06-01 2026-06-30

# только выбранные товары (период по умолчанию)
MPSTATS_TOKEN=xxxxx REPORT_FILTER="РМП" npm run report:stock
MPSTATS_TOKEN=xxxxx node report-stock.js "" "" "002_РМП_белый, 016 МС голубой"
```

Результат — файлы `reports-output/stock-<d1>_<d2>.csv` и `.json` плюс сводка в консоль.
CSV в кодировке UTF-8 с BOM и разделителем `;` — открывается в Excel без плясок.

### 2. По HTTP (сервис запущен)

```bash
# JSON
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/stock-availability?d1=2026-06-01&d2=2026-06-30"

# CSV-файл
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/stock-availability?format=csv" -o stock.csv

# только выбранные товары
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/stock-availability?format=csv&filter=РМП" -o stock.csv
```

Без `d1`/`d2` берётся период = последние `REPORT_DAYS` дней.

### 3. Регулярно (по расписанию)

**Вариант A — встроенный планировщик.** Запустите сервис с:

```bash
REPORT_SCHEDULE_ENABLED=1 REPORT_SCHEDULE_HOUR=6 MPSTATS_TOKEN=xxxxx npm start
```

Каждый день в 06:00 UTC отчёт соберётся сам и ляжет в `reports-output/`.

**Вариант B — системный cron:**

```cron
0 6 * * *  cd /path/to/wb-headless && MPSTATS_TOKEN=xxxxx node report-stock.js >> report.log 2>&1
```

# Отчёт: ABC(-XYZ) анализ товарной матрицы

Классический инструмент управления ассортиментом. Отвечает на два вопроса
одновременно: **сколько денег приносит товар** (ABC) и **насколько его спрос
прогнозируем** (XYZ). Пересечение даёт матрицу 3×3.

Данные — тот же дневной ряд MPSTATS, что и в отчёте по наличию
(см. `lib/abcReport.js`).

## Методология

**ABC** — вклад в результат. Товары ранжируются по убыванию показателя
(по умолчанию — выручка) и раскладываются по **накопленной доле**:

- **A** — «локомотивы»: верхние товары, дающие до `ABC_A_PCT` % (80 %) результата;
- **B** — «середняки»: следующие до `ABC_B_PCT` % (95 %);
- **C** — «хвост»: всё остальное. Товары без продаж всегда попадают в C.

Класс присваивается по накопленной доле **включительно** с самим товаром.

**XYZ** — стабильность спроса. По дневному ряду продаж считаем коэффициент
вариации `CV = σ / среднее` (нули простоя тоже учитываются — это тоже
нестабильность):

- **X** — ровный спрос            (`CV ≤ ABC_X_CV` %, 10 %);
- **Y** — колеблющийся спрос      (`ABC_X_CV` % < `CV ≤ ABC_Y_CV` %, 25 %);
- **Z** — рваный/разовый спрос    (`CV > ABC_Y_CV` %).

**Как читать матрицу.** `AX` — товар-опора (высокий стабильный спрос, держать
всегда, не допускать out-of-stock). `CZ` — мало денег + непредсказуемый спрос:
кандидат на вывод из матрицы. Промежуточные классы — по ситуации.

## Переменные окружения (в дополнение к общим выше)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ABC_METRIC` | `revenue` | Показатель ранжирования ABC: `revenue` или `units` |
| `ABC_A_PCT` | `80` | Граница класса A (накопл. доля, %) |
| `ABC_B_PCT` | `95` | Граница класса B (A+B, %) |
| `ABC_X_CV` | `10` | Граница X (коэффициент вариации, %) |
| `ABC_Y_CV` | `25` | Граница Y (X+Y, %) |

Выбор подмножества товаров (`filter` / `group` / `REPORT_FILTER` /
`REPORT_GROUP`) работает **точно так же**, как в отчёте по наличию.

## Запуск

```bash
# CLI: период = последние REPORT_DAYS дней, ABC по выручке
MPSTATS_TOKEN=xxxxx npm run report:abc

# явный период + только линейка РМП
MPSTATS_TOKEN=xxxxx node report-abc.js 2026-06-01 2026-06-30 "РМП"

# ранжировать ABC по штукам
MPSTATS_TOKEN=xxxxx ABC_METRIC=units npm run report:abc
```

Результат — `reports-output/abc-<d1>_<d2>.csv` и `.json` + матрица в консоль.

```bash
# HTTP: JSON
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/abc?d1=2026-06-01&d2=2026-06-30"

# HTTP: CSV, только РМП, ABC по штукам
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/abc?format=csv&filter=РМП&metric=units" -o abc.csv
```

## Колонки отчёта (CSV) / поля строки (JSON)

| Поле | Описание |
|---|---|
| `class` | Совмещённый класс матрицы (`AX`, `BY`, `CZ`, …) |
| `abc` | Класс ABC (`A`/`B`/`C`) |
| `xyz` | Класс XYZ (`X`/`Y`/`Z`) |
| `seller` | Артикул продавца |
| `sku` | Артикул WB (nmId) |
| `units` | Продано штук |
| `revenue` | Выручка, ₽ |
| `avgPrice` | Средняя цена, ₽ |
| `sharePct` | Доля товара в выбранном показателе, % |
| `cumSharePct` | Накопленная доля (для границ ABC), % |
| `cvPct` | Коэффициент вариации спроса, % |
| `daysWithSales` | Дней с ненулевыми продажами |

JSON дополнительно содержит `matrix` (сводка 3×3: SKU, выручка, штуки и доля
выручки по каждой ячейке), `classTotals` (одномерные срезы по ABC и по XYZ) и
`thresholds` (применённые пороги). Строки отсортированы по убыванию показателя;
SKU без данных идут в конце и попадают в `totals.skusNoData`.

# Отчёт: история остатков WB (поправка ABC на наличие)

**Зачем.** ABC-анализ врёт, если не знать наличие. Товар попадает в класс C не
всегда потому, что «плохой», — часто потому, что его **не было на складе WB** и
продавать было нечего. Чтобы не выводить хорошие товары по ошибке, нужна история
остатков: сколько дней в периоде товар реально был в наличии.

## Источник данных и лимиты (важно!)

Эндпоинты и форматы **проверены на живом API** (июль 2026):

| Что | Метод | История | Лимит |
|---|---|---|---|
| Текущий снимок остатков | Statistics `GET /api/v1/supplier/stocks` | **нет** (только «сейчас», обновление раз в 30 мин) | ~**1 запрос/мин** |
| **Дневная история остатков** | Analytics `POST /api/v2/nm-report/downloads`, тип `STOCK_HISTORY_DAILY_CSV` | **до 3 месяцев** (остаток на 23:59 каждого дня), **без Jam** | асинхронный отчёт, ~**3 запроса/мин** |
| История до года | тот же эндпоинт, тип `DETAIL_HISTORY_REPORT` | до 12 мес | требует подписки **Jam** |

Асинхронный отчёт: `POST /api/v2/nm-report/downloads` (создать) →
`GET /api/v2/nm-report/downloads?filter[downloadIds]=<id>` (статус `SUCCESS`) →
`GET /api/v2/nm-report/downloads/file/<id>` (**ZIP с CSV**). CSV в «широком»
формате: колонки — даты `DD.MM.YYYY`, строка — `nmID × размер × склад`;
`lib/wbStocks.js` распаковывает ZIP (через `zlib`, без внешних зависимостей) и
суммирует остаток по складам/размерам на каждый день.

**Защита от бана.** Все запросы к WB в `lib/wbApi.js` строго
**сериализованы и разнесены по времени** (по умолчанию: статистика ≥ 61 с,
аналитика ≥ 21 с между запросами), на `429` честно ждём `Retry-After`.
Дневная история — **один отчёт на весь кабинет**, поэтому запросов немного.
Не запускайте чаще раза в сутки — история обновляется раз в день.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `WB_TOKEN` | да | Токен WB (категории «Аналитика» и «Статистика») |
| `WB_STATS_MIN_INTERVAL_MS` | нет (61000) | Мин. интервал между запросами статистики, мс |
| `WB_ANALYTICS_MIN_INTERVAL_MS` | нет (21000) | Мин. интервал между запросами аналитики, мс |
| `WB_DOWNLOADS_PATH` | нет | Путь отчётов (по умолчанию `/api/v2/nm-report/downloads`) |
| `WB_STOCK_REPORT_TYPE` | нет | Тип отчёта (`STOCK_HISTORY_DAILY_CSV` / `DETAIL_HISTORY_REPORT`) |
| `WB_STOCK_TYPE` | нет | Тип остатка: пусто = склады WB, `mp` = маркетплейс/FBS |

## Запуск

```bash
# дневная история за последние 90 дней (макс. для дневного отчёта)
WB_TOKEN=xxx npm run report:wb-stocks

# явный период
WB_TOKEN=xxx node report-wb-stocks.js 2026-04-01 2026-06-30

# быстрый текущий снимок остатков (Statistics API)
WB_TOKEN=xxx node report-wb-stocks.js --current
```

Результат — `reports-output/wb-stocks-<d1>_<d2>.csv` и `.json`. Джойн к артикулам
продавца — через `config/skus.json` (nmId ↔ артикул).

## Колонки и метки

| Поле | Описание |
|---|---|
| `seller` / `wb` | Артикул продавца / SKU (nmId) |
| `daysInStock` / `daysOutOfStock` | Дней в наличии / без остатка |
| `inStockRatePct` | Доля дней в наличии, % |
| `flag` | `ДЕФИЦИТ` (< 50% дней), `частичный дефицит` (< 85%), `в наличии` |

**Как это правит ABC.** Товар с меткой `ДЕФИЦИТ` и низкими продажами **нельзя**
списывать в C — низкие продажи объясняются отсутствием остатка, а не спросом.
Такие позиции выделяются как «дать шанс / обеспечить наличие», а не «выводить».

# Регулярный отчёт: наличие товара и упущенная выручка

Отчёт показывает по каждому SKU:

- сколько дней за период товар **реально был в наличии** (остаток > 0);
- сколько дней он **простоял в нуле** (out-of-stock);
- **упущенную выручку** — сколько бы продали в дни простоя, будь товар на складе.

Данные берутся из одного из двух источников (переключатель `REPORT_SOURCE`):

- **`REPORT_SOURCE=wb`** — **WB API** (рекомендуется): спрос по дням из заказов
  (`statistics-api` `/api/v1/supplier/orders`), история остатков по дням из
  Analytics CSV (`STOCK_HISTORY_DAILY_CSV`, без подписки «Джем», до 3 мес).
  Первичные данные, бесплатно, без чужой суточной квоты. Соблюдение лимитов —
  через `lib/wbClient.js` (token-bucket, `X-Ratelimit-*`, 429). См.
  [`docs/wb-api/`](docs/wb-api/).
- **`REPORT_SOURCE=mpstats`** (по умолчанию) — MPSTATS (отчёт «по дням» по
  товару, `wb_item_sales`).

> ⚠ WB-ветку нужно один раз проверить живым токеном: точная схема параметров и
> колонок CSV-отчёта остатков в публичной доке видна не полностью, поэтому
> парсинг колонок сделан терпимым к именам. Логика расчёта проверена на моке.

## Методология упущенной выручки

Прозрачная и воспроизводимая (см. `lib/stockReport.js`):

1. По дневному ряду считаем дни с остатком > 0 (в наличии) и дни с остатком = 0 (простой).
2. Средние продажи в день считаем **только по дням в наличии** — иначе нули из дней простоя занизили бы спрос:
   `avgDailyUnits = проданные штуки / дни_в_наличии`
3. Средняя цена = `выручка / проданные штуки` (если API не отдал выручку — среднее по дням с продажами).
4. `Упущено штук = avgDailyUnits × дни_простоя`
   `Упущенная выручка = упущено штук × средняя цена`

## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `REPORT_SOURCE` | нет | `mpstats` | Источник данных: `wb` (WB API) или `mpstats` |
| `WB_API_TOKEN` | да для `wb` | — | Токен WB API (заголовок `Authorization`); нужны категории **Статистика** и **Аналитика** |
| `WB_TOKEN_TYPE` | нет | `base` | Тип токена WB: `personal`/`service`/`base`/`test` (влияет на лимиты) |
| `MPSTATS_TOKEN` | да для `mpstats` | — | Токен MPSTATS (заголовок `X-Mpstats-TOKEN`) |
| `API_KEY` | да (для HTTP) | `supersecret` | Ключ доступа к эндпоинтам сервиса (заголовок `x-api-key`) |
| `REPORT_DAYS` | нет | `30` | Длина периода по умолчанию (в днях) |
| `REPORT_CONCURRENCY` | нет | `5` | Число параллельных запросов к MPSTATS |
| `MPSTATS_BASE_URL` | нет | `https://mpstats.io/api` | База API |
| `MPSTATS_ITEM_SALES_PATH` | нет | `/wb/get/item/{sku}/sales` | Шаблон пути к отчёту по товару |
| `REPORT_SCHEDULE_ENABLED` | нет | `0` | `1` — включить встроенный ежедневный планировщик |
| `REPORT_SCHEDULE_HOUR` | нет | `6` | Час запуска планировщика (UTC) |

Список товаров лежит в `config/skus.json` — связка **WB-артикула (SKU)** и
**артикула продавца**:

```json
{
  "items": [
    { "wb": 535397255, "seller": "001 РМК-твид бордовый" }
  ]
}
```

### Выбор подмножества товаров (экономия лимита)

Чтобы не опрашивать все 206 товаров (и не жечь суточный лимит MPSTATS),
можно собрать отчёт только по нужным. Два способа:

**A. Группа (линейка) — выпадающий список.** Самый удобный: в форме
«Run workflow» поле **group** — выбираешь линейку из списка (РМП, МС,
Муслin, «Все»…), печатать ничего не нужно. Группы описаны в
`config/groups.json` (метка → список WB-артикулов). Источники:
`REPORT_GROUP` (CLI/сервис), `&group=` (HTTP).

**B. Точечный фильтр — текстом.** Для выбора конкретных товаров или
комбинаций: поле **filter** / `REPORT_FILTER` / `&filter=`. Если задан,
**перебивает** выбор группы.

Правила фильтра (токены через запятую, регистр не важен):

| Пример фильтра | Что выберет |
|---|---|
| *(пусто)* | все товары |
| `РМП` | все, где в артикуле продавца встречается «РМП» |
| `002_РМП_белый, 016 МС голубой` | два конкретных товара |
| `535397255` | по числовому WB-артикулу (SKU) |

Товар попадает в выборку, если **любой** токен совпал: числовой токен
сверяется с WB-артикулом, текстовый — ищется внутри артикула продавца.

## Запуск

### 1. Разово из командной строки

```bash
# период = последние REPORT_DAYS дней
MPSTATS_TOKEN=xxxxx npm run report:stock

# явный период
MPSTATS_TOKEN=xxxxx node report-stock.js 2026-06-01 2026-06-30

# только выбранные товары (период по умолчанию)
MPSTATS_TOKEN=xxxxx REPORT_FILTER="РМП" npm run report:stock
MPSTATS_TOKEN=xxxxx node report-stock.js "" "" "002_РМП_белый, 016 МС голубой"
```

Результат — файлы `reports-output/stock-<d1>_<d2>.csv` и `.json` плюс сводка в консоль.
CSV в кодировке UTF-8 с BOM и разделителем `;` — открывается в Excel без плясок.

### 2. По HTTP (сервис запущен)

```bash
# JSON
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/stock-availability?d1=2026-06-01&d2=2026-06-30"

# CSV-файл
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/stock-availability?format=csv" -o stock.csv

# только выбранные товары
curl -H "x-api-key: $API_KEY" \
  "http://localhost:8080/reports/stock-availability?format=csv&filter=РМП" -o stock.csv
```

Без `d1`/`d2` берётся период = последние `REPORT_DAYS` дней.

### 3. Регулярно (по расписанию)

**Вариант A — встроенный планировщик.** Запустите сервис с:

```bash
REPORT_SCHEDULE_ENABLED=1 REPORT_SCHEDULE_HOUR=6 MPSTATS_TOKEN=xxxxx npm start
```

Каждый день в 06:00 UTC отчёт соберётся сам и ляжет в `reports-output/`.

**Вариант B — системный cron:**

```cron
0 6 * * *  cd /path/to/wb-headless && MPSTATS_TOKEN=xxxxx node report-stock.js >> report.log 2>&1
```

## Колонки отчёта (CSV/JSON)

| Поле | Описание |
|---|---|
| `seller` | Артикул продавца (человекочитаемый) |
| `sku` | Артикул WB (nmId) |
| `daysTotal` | Дней в периоде с данными |
| `daysInStock` | Дней в наличии (остаток > 0) |
| `daysOutOfStock` | Дней без остатка |
| `inStockRatePct` | Доля дней в наличии, % |
| `unitsSold` | Продано штук |
| `revenue` | Выручка, ₽ |
| `avgPrice` | Средняя цена продажи, ₽ |
| `avgDailyUnitsInStock` | Средние продажи в день (только дни в наличии) |
| `lostUnits` | Упущено штук |
| `lostRevenue` | Упущенная выручка, ₽ |

Строки отсортированы по убыванию упущенной выручки — сверху самые «дорогие» простои.
SKU без данных за период идут в конце и попадают в `totals.skusNoData`.

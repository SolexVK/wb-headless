# Контракт инструментов

Обязателен к прочтению перед созданием любого нового агента.

**Главный принцип: агент не пишет код доступа к данным.** Всё, что умеет доставать и считать
код в этом репозитории, агент вызывает, а не реализует заново. Агент отвечает за суждение —
что означают цифры и что с этим делать. Код отвечает за то, чтобы цифры были верными.

Нарушение этого принципа — источник почти всех конфликтов: две реализации одной метрики
расходятся, и никто не знает, какая правильная.

---

## 1. Что уже реализовано и переиспользуется как есть

### Отчёт по наличию и упущенной выручке

`report-stock.js` + `lib/stockReport.js`. Считает по каждому SKU за период: дни в наличии,
дни простоя, продажи, среднюю цену, **упущенные штуки и упущенную выручку**.

```bash
MPSTATS_TOKEN=xxx npm run report:stock                       # период = REPORT_DAYS (30)
MPSTATS_TOKEN=xxx node report-stock.js 2026-06-01 2026-06-30 # явный период
MPSTATS_TOKEN=xxx REPORT_GROUP=РМП npm run report:stock      # только линейка
MPSTATS_TOKEN=xxx REPORT_FILTER="002_РМП_белый" npm run report:stock
```

HTTP: `GET /reports/stock-availability?d1=&d2=&format=csv|json&group=&filter=`
(заголовок `x-api-key`). Результат — `reports-output/stock-<d1>_<d2>.{csv,json}`.

Колонки: `seller, sku, daysTotal, daysInStock, daysOutOfStock, inStockRatePct, unitsSold,
revenue, avgPrice, avgDailyUnitsInStock, lostUnits, lostRevenue`. Сортировка — по убыванию
упущенной выручки.

Методология упущенной выручки: средние продажи в день считаются **только по дням в наличии**,
иначе нули простоя занизили бы спрос. Это уже сделано правильно — не пересчитывать по-своему.

> **Связь с реестром процессов.** Процесс РОП-20 «учёт упущенных продаж» помечен как
> отсутствующий. Это неточность: инструмент есть, но его результат не заводится в план-факт.
> Задача агента — не считать упущенную выручку, а **встроить готовую цифру в отчётность**.

### Анализ ниши

`report-niche.js` + `lib/nicheAnalysis.js`, `lib/nicheReport.js`, `lib/nicheReportHtml.js`.
Скоринг ниши 0–100 по пяти измерениям, вердикт, экономика, реализация остатка по месяцам,
ценовые сегменты, топ-продавцы, PDF. Управляется навыком `/wb-niche-analysis`.

```bash
node scripts/wb-category.mjs мужская рубашка         # резолв пути категории WB
NICHE_ORACLE=oracle.xlsx NICHE_PLUS="..." NICHE_MINUS="..." NICHE_COST=700 \
  node report-niche.js "Мужчинам/Рубашки" 2025-08-01 2026-03-31
```

HTTP: `GET /reports/niche`. Пороги скоринга — `config/niche-thresholds.json`
(ключи: `capacity, trend, seasonality, competition, saturation, queryDemand`).

**Агентам сюда не лезть.** Это отдельное направление со своим владельцем, своим `handoff.md`
и открытым PR. Агент может использовать *результат* анализа ниши, но не менять его логику.

### Доступ к MPStats

`lib/mpstats.js` — единственная точка входа к API. Экспортирует:

| Функция | Что даёт |
| --- | --- |
| `fetchItemDailySales(sku, d1, d2)` | дневной ряд по товару: продажи, остаток, выручка |
| `fetchCategory(...)` | выгрузка товаров категории |
| `fetchCategories()` | дерево категорий WB |
| `fetchCategoryTrends(path, d1, d2)` | тренд по категории |
| `fetchCategorySellers(path, d1, d2)` | продавцы категории |
| `fetchCategoryBrands(path, d1, d2)` | бренды категории |
| `fetchPriceSegmentation(path, d1, d2)` | ценовые сегменты |
| `fetchSearchResults(query, opts)` | поисковая выдача |

Новые обращения к MPStats добавляются **сюда**, а не в код агента и не отдельным скриптом.

### Вспомогательное

- `lib/oraclePhrases.js` — разбор выгрузки «Оракул запросов» (Wildbox), фильтрация фраз
  плюс/минус-ключами. `scripts/oracle-phrases.mjs` — предпросмотр без сети.
- `lib/renderPdf.js` — `findChromium()`, `htmlToPdf(html, path)`. Любой PDF собирается этим.

## 2. Справочник товаров: он есть, но неполный

`config/skus.json` — **206 позиций**, связка WB-артикул (`nmId`) ↔ артикул продавца.
`config/groups.json` — 22 линейки (РЖК 24, РЖП 21, РЖМ 20, МС 18, РМП 18, РММ 16 …),
все 206 позиций распределены.

Это и есть основа справочника из находки 09. Не создавать второй — **расширять этот**.

Чего в нём нет и что нужно добавить, чтобы закрыть находку:

- себестоимость производства на единицу — **блокер, см. `CLAUDE.md`**
- текущая цена и цена безубыточности
- бренд (AIDEMIKO / AIZEK), модель, цвет, размер отдельными полями
- сезонность: летний / демисезонный / зимний
- статус: активный / распродажа / выведен

> **Расхождение, требующее вашего ответа.** В `skus.json` 206 позиций, а по интервью (B2)
> уникальных баркодов 550–600. Либо файл покрывает не все размеры, либо устарел. Пока не
> выяснено, любой отчёт «по всем SKU» будет неполным и об этом надо говорить вслух.

## 3. Чего в инструментах НЕТ

Границу надо знать, чтобы агент не делал вид, что данные есть.

| Чего нет | Следствие для агента |
| --- | --- |
| Доступа к рекламному кабинету WB | ДРР, ставки, кампании — только из ручных выгрузок в `data/ads/` |
| Остатков в разрезе фулфилментов | MPStats даёт остаток на WB целиком. Разрез по 7 складам живёт в таблице логиста → `data/stock/` |
| Возвратов по складам | Находка 02 (перекос в Москву) пока не считается автоматически |
| Отзывов и вопросов | Только ручная выгрузка в `data/reviews/` |
| Цен конкурентов с историей | `fetchCategory` даёт срез на момент запроса; история не накапливается |
| Себестоимости | Ни в одном файле репозитория |
| Данных Ozon | Инструментов нет вообще |

Правило: если данных нет — агент говорит «нет данных», а не подставляет правдоподобное число.
Это уже записано в `CLAUDE.md` и здесь повторяется намеренно.

## 4. Границы владения файлами

Главный механизм защиты от конфликтов. Кто что имеет право менять:

| Область | Владелец | Агентам |
| --- | --- | --- |
| `lib/`, `server.js`, `report-*.js`, `scripts/` | направление «анализ ниши» и разработка | **только чтение и вызов.** Изменения — через `code-reviewer` и PR |
| `config/niche-thresholds.json` | анализ ниши | не трогать |
| `config/skus.json`, `config/groups.json` | общий справочник | менять можно, но **только дополняя**; удаление позиций — через человека |
| `.claude/agents/` | команда агентов | зона агентов, менять свободно |
| `.claude/skills/wb-niche-analysis/` | анализ ниши | не трогать |
| `data/` | входные данные | **только чтение** |
| `reports/`, `documents/`, `content/` | результаты агентов | писать сюда |
| `reports-output/` | результаты инструментов | не писать руками, только через скрипты |
| `handoff.md` | анализ ниши | не трогать |
| `docs/handoff/agent-team.md` | команда агентов | обновлять здесь |

**Не путать `reports/` и `reports-output/`.** Первое — выводы агентов. Второе — машинный вывод
скриптов. Смешение делает непонятным, что откуда взялось.

## 5. Как избежать конфликтов между агентами

1. **Одна метрика — один источник.** Упущенная выручка считается `stockReport.js` и больше
   нигде. Данные MPStats берутся через `lib/mpstats.js` и больше никак. Если агенту нужна
   метрика, которой нет, — сначала решаем, где ей место в коде, потом агент её вызывает.
2. **Перед созданием агента — проверка пересечений.** Позвать `agent-builder`: он обязан
   пройти по существующим `.claude/agents/*.md` и по этому файлу. Пересечение более чем
   наполовину — дорабатываем существующего, а не плодим нового.
3. **Имена уникальны.** Проверка: `grep -h '^name:' .claude/agents/*.md | sort | uniq -d`
   должно быть пусто.
4. **Одна ветка — одно направление.** `claude/agent-team` для команды агентов,
   `claude/niche-analysis-*` для анализа ниши. Не смешивать в одном PR.
5. **Права по минимуму.** Аналитику не нужен `Write` в `lib/`. Читающему агенту не нужен
   `Bash`. Это и безопасность, и защита от того, что агент «поправит» чужой код.

## 6. Карта: агент ↔ инструмент

Как существующие агенты должны быть связаны с кодом. Там, где стоит «переработать», агент
сейчас описан абстрактно и будет дублировать готовое.

| Агент | Использует | Состояние |
| --- | --- | --- |
| `sales-analyst` | `report-stock.js` (продажи, упущенная выручка), `data/sales/` | переработать: сейчас не знает про `lostRevenue` |
| `inventory-planner` | `report-stock.js` (наличие, скорость продаж), `data/stock/` для разреза по FF | **переработать: прямое дублирование расчёта наличия** |
| `pricing-analyst` | `lib/mpstats.js` → `fetchCategory`, `fetchPriceSegmentation` | переработать: сейчас ходит в веб напрямую |
| `ads-analyst` | только `data/ads/` — доступа к кабинету нет | уточнить границу |
| `review-triage` | только `data/reviews/` | без изменений |
| `listing-writer` | `lib/mpstats.js` → `fetchSearchResults` для запросов | переработать |
| `content-planner` | `data/stock/`, `reports/sales/` | без изменений |
| `doc-drafter` | `templates/`, `data/company/` | без изменений |
| `code-reviewer` | `git diff`, запуск `node --check` | связать с реальными командами проверки |
| `bug-fixer` | `node --check`, smoke-наборы | связать с реальными командами проверки |
| `agent-builder` | этот файл + `.claude/agents/` | **обязан читать этот файл перед созданием агента** |

## 7. Проверка перед коммитом нового агента

```bash
cd /workspace/wb-headless

# фронтматтер на месте у всех агентов
for f in .claude/agents/*.md; do
  [ "$(basename "$f")" = "README.md" ] && continue
  head -1 "$f" | grep -q '^---$' || echo "НЕТ фронтматтера: $f"
  grep -q '^name:' "$f" || echo "НЕТ name: $f"
  grep -q '^description:' "$f" || echo "НЕТ description: $f"
done

# имена уникальны
grep -h '^name:' .claude/agents/*.md | sort | uniq -d      # ждём пусто

# агент не лезет в чужую зону
grep -l 'lib/\|server\.js\|niche-thresholds' .claude/agents/*.md   # проверить каждое совпадение
```

FBS-сервис: архитектура и план

Мульти-тенант веб-сервис вокруг готовых движков подсорта и дашбордов: регистрация, организации и кабинеты со своими WB-токенами, выбор отчётов, обновление по кнопке. Хостинг — Mac Mini (Tailscale), затем VPS.

Согласованные решения

БД: SQLite → Postgres (позже) Восстановление: админ-сброс, email — Фаза 4 Код: папка service/ в этом репо Обновление данных: по кнопке Доступ: Организация / Кабинет (ниже)

Модель доступа — как заходят сотрудники

Решает твой нюанс: несколько менеджеров работают с одним кабинетом, токен вводится один раз, параллельные сессии не мешают друг другу.

кэш на кабинет
Токен — один раз. Admin организации подключает кабинет и вводит WB-токен. Все участники видят кабинеты организации без повторного ввода токена.
Параллельная работа — без накладок. У каждого свой аккаунт и сессия, поэтому «общий аккаунт» не нужен. Снимок кэшируется на кабинет; одновременный «Обновить» схлопывается одним расчётом (single-flight-замок), отчёты — только чтение.

Модель данных (SQLite → Postgres, тонкий слой доступа)

users пользователь

  • id, email (уникальный), password_hash (bcrypt)
  • name, created_at, last_login

organizations организация

  • id, name, owner_user_id, created_at

memberships участие

  • user_id × org_id, role: owner / admin / member
  • роль решает: управлять кабинетами/участниками или только смотреть отчёты

cabinets кабинет WB

  • id, org_id, name
  • wb_token_enc (AES-256-GCM), token_meta (категории/срок), is_active

invitations приглашения

  • org_id, email/код, role, expires_at — admin зовёт менеджеров в организацию

snapshot_cache кэш отчётов

  • cabinet_id × report × params_hash → json, refreshed_at
  • общий на кабинет; чистится при «Обновить»

Архитектура

Бэкенд

Node + Express (уже в репо). Сессии в httpOnly-cookie, bcrypt. Логи — pino (ротация + отдельный лог ошибок).

Движки как бэкенд

Готовые scripts/fbs-*.mjs отдают JSON (--json). Сервис запускает их с токеном кабинета и рендерит.

Данные по кнопке

«Обновить» → расчёт → кэш снимка per (кабинет, отчёт, параметры). Повторный заход — из кэша.

Безопасность

  • ✓WB-токены шифруются в БД (AES-256-GCM, ключ в env/Keychain), никогда не в логах и не на фронте.
  • ✓Пароли — bcrypt. Сессии — httpOnly + Secure cookie, CSRF-защита, rate-limit на логин/регистрацию.
  • ✓Правильный тип WB-токена. Пользователь даёт Базовый, «Только чтение» с категориями Контент + Статистика + Маркетплейс (персональный в облаке WB запрещает).
  • ✓Проверка прав до запроса. Токен — JWT; читаем битовую маску s (Контент=1, Аналитика=2, Маркетплейс=4, Статистика=5, read-only=30) и /ping — форма подключения сразу скажет, чего не хватает.
  • ✓Изоляция. Каждый запрос к данным строго по (user → org → cabinet); чужой кабинет недоступен.

Отчёты в сервисе

Реестр «имя → движок → рендер». Новый отчёт = одна строка. Готовые подключаем первыми, невстроенные — позже, тем же способом.

Деплой на Mac Mini — правила безопасности

По памятке docs/china-fbs/deploy/MAC-MINI-RULES.md (соседняя ветка, PR #13). Читаем её ПЕРЕД любым шагом деплоя — сервис не должен ломать соседей.

🚫 Нельзя

  • tailscale serve reset / голый funnel <порт>
  • Трогать 443 руками (занят Caddy), включать com.tandem.funnel
  • Занимать порты 8477/8787/8899/7837/8090/9000/8443/10000/2019
  • Править/рестартить чужие launchd, коммитить секреты

✅ Можно / как надо

  • Свой сервис на свободном loopback: 127.0.0.1:91xx
  • Свой LaunchAgent с уникальным label
  • Публикация только через Caddy (path-маршрут на 443 + caddy reload), Funnel не трогать
  • Тест локально, вкл. «внешний» кейс через Host-заголовок

Дизайн-следствие: сервис слушает настраиваемый 127.0.0.1:91xx (env PORT), никаких привязок к 443/Funnel в коде — публикацию делаем на этапе деплоя через Caddy.

Опорный документ. Готовые движки (scripts/fbs-*.mjs, config/replenishment.json) переиспользуются как бэкенд через --json. Следующий шаг — Фаза 0.

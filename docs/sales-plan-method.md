# Метод построения плана продаж на сезон (по Овчинникову) — рабочая методология

> Документ фиксирует согласованные решения и методологию для фичи «план продаж
> на сезон» на данных MPStats. Ветка: `claude/sales-plan-hzlqew`.

## Суть подхода

План строится не линейно «от прошлого месяца», а через декомпозицию спроса на
**базу (тренд)** и **сезонную надбавку**. План любого дня/месяца =
`База × сезонный коэффициент периода`. По амплитуде коэффициентов предмету
присваивается **ранг сезонности**, который переключает режим планирования
(буфер, сроки завоза, тайминг рекламы, ценовая стратегия).

## Зафиксированные решения (ответы заказчика)

1. **Пороги ранга.** Не берём фиксированные пороги из общих статей. Ранг —
   **умеренной** грануляции, но рассчитывается **на основе ежедневной статистики
   по продажам и ценам** за требуемый период **год назад** (тот же календарный
   период прошлого года, дневная детализация).

2. **Уровень планирования — по линейкам из `config/groups.json`.**
   Предварительно собираем группу артикулов: берём выдачу по **предмету**, затем
   применяем **детальную фильтрацию**, чтобы в выборке остались только
   релевантные артикулы (аналоги нашего товара, а не «весь предмет подряд»).

3. **Источник сезонности — собранная группа** артикулов, данные из **MPStats**
   (а не только собственные продажи и не «категория целиком»).

4. **Горизонт истории.** Стартуем с **категорийной сезонности + артикулов
   собранной группы**. По группе получаем **общие (агрегированные) дневные
   данные**: продажи, остатки, цены — **за каждый день требуемого прошлого
   периода**.

## Входные метрики (что собираем)

По каждому артикулу группы, по дням, за целевой период прошлого года:

- **Продажи, шт** (и/или заказы) — основной сигнал спроса;
- **Остатки, шт** — для поправки на out-of-stock и оценки давления запаса;
- **Цена** — для ценового профиля сезона;
- (производные) **выручка**, **средний чек**.

Затем всё агрегируется в **дневной ряд по группе**.

## Пошаговая методология

### Шаг 0. Сбор группы артикулов по предмету + фильтрация

Цель — получить множество **релевантных** SKU (аналогов нашего товара), а не
весь предмет.

1. Берём выдачу по **предмету/категории** из MPStats (отчёт «Категории» —
   список товаров предмета за период). Возвращает по каждому nmId: продажи,
   выручку, остаток, цену, бренд, продавца, рейтинг.
2. Применяем **детальную фильтрацию**, чтобы отсеять нерелевантное:
   - ценовой коридор (наш ценовой сегмент ± дельта);
   - по ключевым словам в названии/характеристиках (наш тип товара);
   - отсечь «шум»: товары почти без продаж, брошенные карточки, товары не из
     нашего сегмента (детское/опт/другой размерный ряд и т.п.);
   - при необходимости — по бренду/продавцу (исключить/включить).
3. Результат — список nmId группы. Сохраняем связку с линейкой из
   `config/groups.json` (метка линейки → список WB-артикулов группы-эталона).

### Шаг 1. Сбор дневных данных по группе за целевой период (год назад)

Целевой период — тот же календарный интервал прошлого года, что мы планируем
(например, планируем осень 2026 → тянем осень 2025), при возможности с запасом
по краям, чтобы видеть вход в сезон и распродажу.

Для каждого nmId группы запрашиваем дневной ряд:
- **продажи/заказы, шт** за день;
- **остаток, шт** на день;
- **цена** дня;
- (выручка — если отдаётся, иначе реконструируем из штук×цена).

Эндпоинт по товару — тот же, что уже используется в `lib/mpstats.js`:
`/wb/get/item/{sku}/sales?d1=YYYY-MM-DD&d2=YYYY-MM-DD`.

### Шаг 2. Агрегация в дневной ряд по группе и чистка

1. **Суммируем по группе** по каждому календарному дню:
   - `salesGroup[d] = Σ sales_i[d]` — суммарные продажи группы за день;
   - `stockGroup[d] = Σ stock_i[d]` — суммарный остаток группы на день;
   - `priceGroup[d]` — **средневзвешенная по продажам** цена группы за день
     (`Σ price_i·sales_i / Σ sales_i`); если продаж в день нет — простое среднее
     по активным карточкам. Взвешивание по продажам даёт «цену реального спроса».
2. **Поправка на out-of-stock.** Дни, когда значимая доля группы стояла в нуле,
   искусственно занижают спрос. Восстанавливаем ожидаемые продажи такого дня по
   продажам в наличии (логика уже есть в `lib/stockReport.js`:
   `avgDailyUnitsInStock`). Флажим такие дни как «дефицитные».
3. **Чистка выбросов.** Разовые всплески (акции WB, вирусный товар) гасим
   медианным/скользящим сглаживанием, чтобы они не ломали профиль сезона.

### Шаг 3. Нормализация коэффициентов (продажи, остатки, цена)

Для каждого из трёх рядов строим **дневной коэффициент** — отношение к своей
базе за период, предварительно сгладив и сняв тренд.

1. **Сглаживание.** Скользящее среднее окном 7 дней (убирает недельную «пилу» и
   шум): `smoothed[d] = MA7(series[d])`.
2. **База периода.** `base = mean(smoothed[*])` за весь целевой период
   (среднедневной уровень).
3. **Снятие тренда.** Оцениваем линейный/скользящий тренд `trend[d]` (растущий
   или падающий рынок) и делим на него, чтобы сезонность не «съела» тренд:
   `deTrended[d] = smoothed[d] / trend[d] · base`.
4. **Коэффициенты** (безразмерные, 1.0 = средний уровень):
   - **продажи:** `kSales[d] = deTrended_sales[d] / base_sales`;
   - **остатки:** `kStock[d] = smoothed_stock[d] / mean_stock` — показывает, где
     запас группы был выше/ниже среднего (низкий `kStock` в пик = дефицит рынка,
     окно возможности);
   - **цена:** `kPrice[d] = smoothed_price[d] / mean_price` — как двигалась цена
     реального спроса по ходу сезона (растёт к пику, падает в распродажу).

Интерпретация: `kSales=1.20` → +20% к среднему спросу; `kSales=0.80` → −20%.

### Шаг 4. Ранг сезонности предмета

Ранг = сила выраженности сезона, считается по **амплитуде** сглаженного
коэффициента продаж за год-назад-период:

```
amplitude = max(kSales) / min(kSales)      (или percentile95/percentile5 — устойчивее к краям)
```

Классификация (умеренной грануляции, пороги калибруются по факт. данным группы):

| Ранг | Ориентир по амплитуде | Режим планирования |
|---|---|---|
| Ярко выраженный | пик ≫ базы (`max(kSales)` ~>2, глубокий провал) | ранний завоз, большой буфер, весь маркетинг в пик |
| Умеренный | заметные волны, спрос круглый год | гибкое пополнение, усиление к пику |
| Слабый / всесезонный | коэффициенты в узком коридоре | планирование по скользящей средней, буфер минимум |

### Шаг 5. Определение фаз сезона (вход → разгон → пик → распродажа)

Работаем по сглаженной кривой `kSales[d]` и её производной (наклону):

- **Пик** — максимум `kSales` (дата `Dpeak`). Вокруг — «горячий сезон»
  (дни с `kSales ≥ ~1.3`).
- **Разгон** — участок устойчивого роста наклона до пика; начинается, когда
  `kSales` уверенно пробивает вверх ~1.0.
- **Вход в рынок (когда выгодно заходить)** — **раньше** начала разгона, с
  упреждением на подготовку:
  `Dentry = Dstart_ramp − (лаг на рейтинг/SEO ~2–6 нед) − (лаг на завоз ~2–4 нед)`.
  Практика рынка: партию закупают за **60–90 дней** до пика, карточку выводят за
  **1–2 месяца** до сезона — чтобы к пику иметь отзывы, рейтинг и топ выдачи.
- **Распродажа** — участок спада после пика: когда `kSales` уверенно уходит вниз
  через ~1.0 и наклон отрицательный. Остатки нужно распродать до «смерти» спроса.

Итог фазы отдаём как календарные интервалы + ключевые даты (`Dentry`,
`Dramp`, `Dpeak`, `Dsale`).

### Шаг 6. Ценовая динамика по фазам

Из `kPrice[d]` восстанавливаем, как рынок вёл цену, и накладываем стратегию:

- **Вход/разгон** — цена на уровне рынка или чуть ниже (набор скорости, рейтинга);
  ориентир — `kPrice` начала сезона.
- **Пик** — цена максимальная (`max kPrice`); закладываем наценку «под скидку».
- **Распродажа** — цена минимальная (`min kPrice`); сброс остатков, до −N% от пика.

Отдаём рекомендованную цену по фазам = `mean_price_группы × kPrice_фазы`,
скорректированную на нашу unit-экономику (минимальная цена = себестоимость +
расходы + реклама + подушка возвратов + плановая прибыль).

### Шаг 7. Плановое ежедневное количество заказов

Переводим сезонный профиль в дневной план:

1. **База под план.** `BaseDaily = целевой объём периода / число дней`
   (с учётом тренда рынка и нашей цели роста — коэффициент амбиции).
2. **Дневной план:** `planOrders[d] = BaseDaily × kSales[d]` — столько заказов в
   день нужно держать, чтобы идти по сезону.
3. **Недельный профиль** (опционально): накладываем коэффициенты дней недели
   (в какие дни недели заказов больше) — MPStats даёт недельную сезонность.
4. **Проверка обеспеченностью:** сверяем `planOrders[d]` с запасом и сроком
   поставки на склады WB — план по заказам должен быть подкреплён планом завоза
   (буфер по рангу: ярко выраженный ~40–45 дней, всесезонный ~20–30 дней).

### Выход (что отдаёт модуль)

По линейке/группе:
- ранг сезонности + амплитуда;
- дневные ряды коэффициентов `kSales`, `kStock`, `kPrice`;
- фазы сезона с датами (`Dentry`, `Dramp`, `Dpeak`, `Dsale`);
- рекомендованная цена по фазам;
- плановое число заказов по дням `planOrders[d]`;
- план завоза/буфера под пик.

## Привязка к API MPStats (по итогам ресёрча)

База: `https://mpstats.io/api/`, авторизация — заголовок `X-Mpstats-TOKEN`
(уже реализована в `lib/mpstats.js`). Данные MPStats копит с 25.01.2020 —
значит, дневной ряд «год назад» доступен. Коды: `200` ок, `202`
«ещё не готово, повторить», `429` + `Retry-After` — лимит.

### Шаг 0 — список товаров предмета: `POST /wb/get/category` (подтверждено)

- Query: `d1`, `d2` (YYYY-MM-DD), `path` — путь предмета, URL-энкоденный
  (напр. `Женщинам/Одежда`, предмет — последний узел пути).
- Тело (ag-grid-стиль, серверные пагинация/фильтр/сортировка):
  ```json
  { "startRow": 0, "endRow": 5000,
    "filterModel": { },
    "sortModel": [ { "colId": "revenue", "sort": "desc" } ] }
  ```
  - `startRow/endRow` — окно пагинации, до **~5000 строк** за запрос;
  - `filterModel` — **серверная фильтрация** (по слову/цене/бренду) — главный
    рычаг сократить число запросов и сразу отсеять нерелевантное на Шаге 0;
    точная схема полей `filterModel` — **уточнить по авторизованным докам**;
  - `sortModel` — сортировка.
- Ответ: `{ total, data: [ … ] }`. Поля товара в `data[]`: `id` (это WB nmId —
  имя поля `id`, не `nmId`), `name`, `brand`, `seller`, `balance`, `rating`,
  `comments`, `sales`, `final_price`, `revenue`, `graph` (спарклайн).

Так набираем группу-эталон и точечно фильтруем до релевантных аналогов.

### Шаг 1 — дневной ряд по товару: `GET /wb/get/item/{sku}/sales` (подтверждено)

- Метод **GET** (POST/иные отдают 405/500), query: `d1`, `d2`; опц. `fbs=1`.
- Поля дня: `data` (дата — именно `data`, не `date`), `balance`, `sales`,
  `price`, `final_price`, `rating`, `comments`, `is_new`.
- Это основной потребитель лимита (1 SKU = 1 запрос) — размер группы держим
  разумным и/или пагинируем по датам, если упрёмся в кап окна.

### Тренд категории: `GET /wb/get/category/trends` (подтверждено)

- Query: `d1`, `d2`, `path`. Даёт трендовый ряд категории — используем для
  снятия тренда (Шаг 3) и как второй, более устойчивый источник для ранга.

### Что осталось уточнить (по авторизованным докам / реальным запросам)

- Точная схема `filterModel` для серверной фильтрации по цене/слову/бренду.
- Есть ли кап на ширину окна `d1–d2` у `/item/{sku}/sales` (если да — пагинируем).
- Конкретные числовые лимиты тарифа (429 драится из пула «Внешняя аналитика»).
- **Готового API сезонности не подтверждено** — отдельного `/seasonality`
  эндпоинта нет; сезонный профиль **строим сами** из дневного ряда группы
  (как и заложено в методике). Отчёт сезонности в UI существует (% к тренду по
  дням/неделям/месяцам в разрезах выручка/заказы/товары-с-заказами) — это лишь
  подтверждает корректность нашего подхода.
- Отдельный REST-путь «Сводный отчёт по предмету» не подтверждён — работаем
  через `path` предмета в `/wb/get/category`.

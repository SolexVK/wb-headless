Главная проблема

Одна точка входа к MPStats существует в четырёх версиях

Контракт инструментов требует: одна метрика — один источник. По факту базовый модуль доступа к данным разошёлся на четыре независимые ветви, и main не знает про три из них.

Что уже построено

Три роли архитектуры закрыты кодом, а не агентами

claude/fbs-fullfilment — работающий сервис, а не заготовка

Мультитенантный веб-сервис аналитики FBS, развёрнутый на Mac Mini под launchd, с шифрованием токена AES-256-GCM. Пять отчётов, все smoke-тесты зелёные:

  • Подсорт — рекомендации к дозаказу по складам и размерам. Это ровно роль replenishment из архитектуры.
  • Остатки — FBS по складам, ежесуточный автоснимок, архив 90 дней. Это те данные, которые я просил логиста выгружать в CSV вручную.
  • География — возвраты привязаны к складу отгрузки через srid = rid.
  • Движение заказов и Логистика — сроки сборки и доставки по фулфилментам, среднее, медиана, p90.
Моя находка 02 уже решена в коде

Я писал, что возвраты стекаются в московский фулфилмент и перекос надо ловить поправкой в формуле подсорта. В этой ветке привязка возврата к исходному складу отгрузки уже реализована. Данные для правильного расчёта есть — вопрос лишь в том, что этот сервис не связан ни с чем остальным.

claude/wildberries-tools — каскад из трёх инструментов

ТОП по фразе → сравнение карточек → конкурентный анализ, сцепленные общим JSON-контрактом по nmId, плюс оркестратор scripts/wb-pipeline.mjs. Движок конкурентного анализа — Python на ~1 950 строк, отдаёт markdown, HTML, PDF и JSON.

Здесь же живёт база доступа к WB: lib/wbClient.js, lib/wbToken.js, lib/wbCabinet.js через headless-браузер, снимки документации API. Токены берутся из тех же переменных окружения, что я нашёл: MPSTATS_TOKEN, Wildberries_API, WB_COOKIES, WB_LOCALSTORAGE.

Пересечение с моим модулем

В отчёте конкурентного анализа есть блок «C. Юнит-экономика»: коридор маржи и ДРР, безубыточность с рекламой, сегменты по цене. Там зашита константа выкуп 36 %. Мой lib/ownEconomics.js считает то же самое, но по нашей себестоимости и из config/economics.json. Две реализации маржи — ровно то, против чего написан контракт. Решать, какая эталонная, нужно до того, как обе разойдутся дальше.

claude/sales-plan — прогноз плана продаж, обкатан живьём

Навык seasonality-sales-plan: сезонный профиль за два года с recency-взвешиванием, ранг, фазы с датами входа, разгона, пика и распродажи, дневной план заказов, рекомендованная цена по фазам. Четыре запроса MPStats на весь прогноз. Отдаёт xlsx, html, csv, json. Прогонялся на рубашках в клетку.

Это роль season-plan, и она в рабочем состоянии. Не сделано: отбор своих товаров через WB Seller API — база перенесена, ждёт способа отбора.

claude/database — хранилище, которого не хватало

SQLite в репозитории, lib/db.js со схемой и миграциями, CLI, накопление дневных рядов по SKU, статистика в /health, коммит базы обратно в ветку после запуска GitHub Actions. Засеян каталогом: 206 товаров, 22 группы, ноль дневных строк.

Не проверено на живом окружении: в той сессии не было токена MPStats. Сейчас он есть — это первое, что стоит прогнать.

Следствие

Архитектуру надо поправить

Я проектировал двадцать ролей исходя из того, что инструментов нет и coder будет писать коннекторы. Это оказалось неверно. Уточнённая картина:

Что это меняет по сути

Дефицит у компании не в инструментах, а в связности. Пять отчётов FBS, каскад конкурентного анализа, прогноз сезонности и база данных существуют — но не знают друг о друге, живут в разных ветках, и ни один не попадает в ежедневное решение. Именно это и должна закрывать команда агентов: не считать заново, а связывать и интерпретировать.

План

Как сводить

Порядок от нулевого риска к спорному. Каждый шаг проверяется qa-auditor до перехода к следующему.

  1. Прогнать базу на живых токенах

    Ветка database не проверялась на реальном MPStats — токена не было. Сейчас есть. Это самый дешёвый шаг и он показывает, годится ли SQLite как хранилище под накопление.

    Риск нулевой · ничего не сливаем

  2. Внести непересекающееся

    Каталог service/ FBS-сервиса, docs/wb-api/*, навыки из всех четырёх веток. Эти пути не встречаются в main, конфликтов нет.

    Риск низкий · сразу даёт пять отчётов и четыре навыка

  3. Выбрать эталон для lib/mpstats.js

    Четыре версии, ни одна не надмножество. Нужно решение человека: скорее всего основой берётся версия main как самая полная, а функции сезонности и каскада доносятся из двух других. Механически слить нельзя.

    Требует вашего решения · блокирует всё дальнейшее

  4. Перенести доступ к WB

    lib/wbClient.js, lib/wbToken.js, lib/wbCabinet.js из wildberries-tools как более новой версии. После этого мой lib/wbContent.js надо будет либо встроить в wbClient, либо оставить как отдельный узкий модуль — решать после чтения кода.

    Риск средний · две версии wbClient расходятся на 326 байт

  5. Развести юнит-экономику

    Блок C конкурентного анализа считает маржу по рынку и медианной цене, мой модуль — по нашей себестоимости. Скорее всего они дополняют друг друга, но константу выкупа 36 % надо вынести в config/economics.json, чтобы источник был один.

    Требует чтения кода Python-движка

  6. Собрать server.js и package.json вручную

    Пять версий каждого. Это единственная часть, где придётся именно собирать, а не выбирать: эндпоинты и зависимости в ветках непересекающиеся.

    Самый спорный шаг · делать последним

Правило, без которого всё повторится

После сведения — работать в main через короткоживущие ветки с обязательным merge. Тридцать семь параллельных веток появились не случайно: каждая сессия начинала своё направление и не возвращала его назад. Пока это правило не введено, любая ревизия устареет за месяц.

Данные о версиях получены через git cat-file -s и git rev-parse по каждой ветке. Описания состояния — из handoff.md каждой ветки, разделы «Цель» и «Текущее состояние». Код модулей не читался, кроме docs/sales-plan-method.md; выводы о пересечениях сделаны по объявленному составу файлов и описаниям авторов.

# Потери на «сгоревших» складах Wildberries — как получить данные через API

Практическая заметка: где в WB API отражаются **потери товара на складах FBW**
(утрата/повреждение по вине WB, в т.ч. после пожаров) и **компенсации ущерба**,
и как их выгрузить, **не поймав бан по лимитам**.

Официальный снимок метода — [`finance-reports.md`](./finance-reports.md)
(страница `financial-reports-and-accounting`, подтверждена живым фетчем 2026-08-16).

---

## 1. Два разных сценария потерь

- **Аварии/пожары, где WB признаёт ответственность** (напр. пожар в Шушарах,
  январь 2024) → WB **компенсирует** ущерб. Компенсация приходит строками
  «Компенсация ущерба» в детализации к отчёту о реализации (метод ниже).
- **Атаки БПЛА, июль–август 2026** → WB объявил это **форс-мажором**
  (оферта №98 от 07.07.2026) и ущерб **не компенсирует**. Значит, строк
  компенсации в отчёте **не будет**, и потери нужно **оценивать самостоятельно**
  — по остаткам, лежавшим на этих складах:

  ```bash
  WB_API_TOKEN=xxx npm run report:fire        # склады и себестоимость — в config/fire-warehouses.json
  ```

  Раннер тянет `warehouse_remains`, суммирует остатки на сгоревших складах с
  детализацией по артикулам и умножает на среднюю себестоимость. **Оговорка:**
  `warehouse_remains` — снимок «на сейчас»; после списания сгоревшего товара WB
  цифра занижается, поэтому корректнее иметь снимок ДО пожара.

Дальше — про **первый сценарий** (компенсируемые потери).

## 2. Метод: детализация к отчёту о реализации за период

- **Метод:** `POST /api/finance/v1/sales-reports/detailed`
- **Хост:** `https://finance-api.wildberries.ru`
- **Данные доступны с 29 января 2024** (т.е. пожар в Шушарах покрывается).
- **Что искать в строках:** операции/обоснования с типом **«Компенсация ущерба»**
  (утрата или порча товара на складе/при обработке WB).

> Это актуальная замена старого `GET /api/v5/supplier/reportDetailByPeriod`
> (statistics-api). Новый метод — на `finance-api`, POST с телом, курсор `rrdId`.

Компенсация приходит отдельными строками: тип операции `sellerOperName` и/или
обоснование `bonusTypeName` содержат «**компенсац**»/«**ущерб**», а сумма к
перечислению продавцу — в `forPay`.

## 3. Лимиты запросов — чтобы не словить бан

Лимит у метода **самый жёсткий**:

| Тип токена            | Период | Лимит      | Всплеск |
|-----------------------|--------|------------|---------|
| Персональный          | 1 мин  | 1 запрос   | 1       |
| Сервисный             | 1 мин  | 1 запрос   | 1       |
| Базовый **с секретом**| 1 мин  | 1 запрос   | 1       |
| Базовый (без секрета) | 24 ч   | 2 запроса  | 1       |

- **Не чаще 1 запроса в минуту.** Для базового токена без секрета — 2 запроса в
  сутки, планируйте выгрузку заранее.
- **429 → не долбить.** Ждать по заголовку `X-Ratelimit-Retry`.
- **4xx не повторять.**
- Отчёт большой → листать курсором **`rrdId`**, пока не придёт **204 (нет данных)**.

Полная теория лимитов — [`limits.md`](./limits.md). Всё это соблюдает клиент
[`lib/wbClient.js`](../../lib/wbClient.js) — обязательно передавайте `methodLimit`.

## 4. Как выгрузить (с соблюдением лимита)

```js
import { WbClient } from '../lib/wbClient.js';

const wb = new WbClient({ token: process.env.WB_API_TOKEN, tokenType: 'base' });

// Детализация реализации листается курсором rrdId: в каждый следующий запрос
// кладём rrdId последней строки предыдущего ответа, пока не придёт 204/пусто.
async function fetchRealizationDetail({ dateFrom, dateTo }) {
  const rows = [];
  let rrdId = 0;
  for (;;) {
    const { status, data } = await wb.request('statistics', '/api/finance/v1/sales-reports/detailed', {
      method: 'POST',
      baseUrl: 'https://finance-api.wildberries.ru', // метод на finance-api, не на statistics-api
      body: { dateFrom, dateTo, limit: 100000, rrdId, period: 'weekly' },
      // ← лимит именно этого метода: 1 запрос в минуту, всплеск 1
      methodLimit: { limit: 1, periodSec: 60, burst: 1 },
    });
    if (status === 204 || !Array.isArray(data) || data.length === 0) break;
    rows.push(...data);
    rrdId = data[data.length - 1].rrdId; // курсор на следующую страницу
  }
  return rows;
}

// Оставляем только строки про потери/компенсацию ущерба.
function onlyDamageCompensation(rows) {
  const re = /(компенсац|ущерб|утрат|порч|недостач)/i;
  return rows.filter((r) =>
    re.test(r.sellerOperName || '') || re.test(r.bonusTypeName || '')
  );
}
```

### Полезные поля строки отчёта (новый finance-api, camelCase)

| Поле             | Значение |
|------------------|----------|
| `sellerOperName` | Тип операции (искать «Компенсация ущерба» и т.п.) |
| `bonusTypeName`  | Обоснование для оплаты/удержания |
| `forPay`         | Сумма к перечислению продавцу (компенсация — со знаком «+») |
| `docTypeName`    | Тип документа (Продажа / Возврат) |
| `officeName`     | Склад |
| `nmId`, `vendorCode`, `subjectName`, `brandName` | Идентификация товара |
| `quantity`       | Количество |
| `rrdId`          | ID строки — курсор для листания |
| `orderDt`, `saleDt`, `rrDate` | Даты |

> Точные названия типов операций/обоснований WB может менять. Фильтруйте по
> подстроке («компенсац»/«ущерб»), а не по точному совпадению, и при первой
> выгрузке сверьтесь с уникальными значениями `sellerOperName` за период инцидента.

## 5. Смежные источники (для сверки, не сами потери)

- **Остатки на складах** — `GET /api/v1/warehouse_remains` (`seller-analytics-api`):
  что *сейчас* на складах; исчезновение позиции после инцидента видно здесь.
  Это основа раннера `report:fire` для форс-мажорного сценария.
- **Платное хранение** — `GET /api/v1/paid_storage`: плата за хранение, не потери.
- **Баланс** — `GET /api/v1/account/balance` (`finance-api`): текущий баланс счёта.

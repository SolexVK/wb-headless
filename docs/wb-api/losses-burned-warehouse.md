# Потери на «сгоревших» складах Wildberries — как получить данные через API

Практическая заметка: где в WB API отражаются **потери товара на складах FBW**
(утрата/повреждение по вине WB, в т.ч. после пожара на складе — напр. Шушары,
январь 2024) и **компенсации ущерба**, и как их выгрузить, **не поймав бан по
лимитам**.

> ⚠️ Это авторская аналитическая заметка, а не дословный снимок официальной
> страницы. Официальный снимок метода `reportDetailByPeriod` в этот репозиторий
> ещё **не** втянут: портал `dev.wildberries.ru` в текущем окружении отдаёт
> антибот-заглушку (HTTP 498, «Подозрительная активность»). Страница добавлена в
> `pages.json` — снимок подтянется еженедельным workflow или ручным
> `npm run docs:fetch` из окружения без блокировки. См. раздел «Что осталось».

---

## 1. Короткий ответ

Отдельного метода «покажи мои сгоревшие товары» у WB **нет**. Потери и
компенсации по ним проходят деньгами в **детализации к отчёту о реализации**:

- **Метод:** `GET /api/v5/supplier/reportDetailByPeriod`
- **Хост (категория `statistics`):** `https://statistics-api.wildberries.ru`
- **Что искать в строках:** операции/обоснования с типом
  **«Компенсация ущерба»** (утрата или порча товара на складе/при обработке WB).

Компенсация приходит отдельными строками отчёта: тип операции
`supplier_oper_name` и/или обоснование `bonus_type_name` содержат
«**компенсац**»/«**ущерб**», а сумма к перечислению продавцу лежит в
`ppvz_for_pay`.

Смежные источники (для сверки, но это **не** сами потери):
- **Остатки на складах** — `GET /api/v1/warehouse_remains` (категория
  `analytics`): показывает, что *сейчас* на складах; резкое исчезновение позиции
  после инцидента видно здесь.
- **Платное хранение** — `GET /api/v1/paid_storage` (категория `analytics`): это
  плата за хранение, к потерям отношения не имеет.
- **Отчёты об удержаниях** (`/api/v1/analytics/*`) — штрафы/удержания, тоже не
  про утрату товара.

## 2. Лимиты запросов — чтобы не словить бан

`reportDetailByPeriod` относится к **старому Statistics API** с самым жёстким
лимитом во всём WB API. По данным `reports-statistics.md` (методы `orders` /
`sales` / детализация реализации делят один лимит на аккаунт):

| Тип токена            | Период | Лимит      | Восстановление | Всплеск (burst) |
|-----------------------|--------|------------|----------------|-----------------|
| Персональный          | 1 мин  | 1 запрос   | 1 мин          | 10              |
| Сервисный             | 1 мин  | 1 запрос   | 1 мин          | 10              |
| Базовый **с секретом**| 1 мин  | 1 запрос   | 1 мин          | 10              |
| Базовый (без секрета) | 3 часа | 1 запрос   | 3 часа         | 1               |

Практические правила (полная теория — в [`limits.md`](./limits.md) и
[`README.md`](./README.md)):

- **Не чаще 1 запроса в минуту.** Для базового токена без секрета — вообще
  1 запрос в 3 часа, планируйте выгрузку заранее.
- **429 → не долбить.** Ждать ровно столько, сколько в заголовке
  `X-Ratelimit-Retry`; остаток всплеска смотреть в `X-Ratelimit-Remaining`.
- **4xx не повторять** — ошибочные запросы жгут лимит быстрее (в категории
  «Маркетплейс» один 4xx = 10 запросов).
- Отчёт большой → листать через курсор **`rrdid`** (см. ниже), а не слать
  параллельные запросы.

Всё это уже соблюдает клиент [`lib/wbClient.js`](../../lib/wbClient.js)
(token-bucket на категорию, чтение `X-Ratelimit-*`, ожидание по
`X-Ratelimit-Retry`, запрет ретраев на 4xx). **Обязательно** передавайте методу
его точный лимит через `methodLimit`.

## 3. Как выгрузить (с соблюдением лимита)

```js
import { WbClient } from '../lib/wbClient.js';

const wb = new WbClient({
  token: process.env.WB_API_TOKEN,
  tokenType: 'base', // или 'personal'/'service'
});

// Детализация реализации листается курсором rrdid: в каждый следующий запрос
// кладём rrd_id последней строки предыдущего ответа, пока не придёт пустой массив.
async function fetchRealizationDetail({ dateFrom, dateTo }) {
  const rows = [];
  let rrdid = 0;
  for (;;) {
    const { data } = await wb.get('statistics', '/api/v5/supplier/reportDetailByPeriod', {
      query: { dateFrom, dateTo, limit: 100000, rrdid },
      // ← лимит именно этого метода: 1 запрос в минуту, всплеск 10
      methodLimit: { limit: 1, periodSec: 60, burst: 10 },
    });
    if (!data || data.length === 0) break;
    rows.push(...data);
    rrdid = data[data.length - 1].rrd_id; // курсор на следующую страницу
  }
  return rows;
}

// Оставляем только строки про потери/компенсацию ущерба.
function onlyDamageCompensation(rows) {
  const re = /(компенсац|ущерб|утрат|порч|недостач)/i;
  return rows.filter(r =>
    re.test(r.supplier_oper_name || '') || re.test(r.bonus_type_name || '')
  );
}
```

### Полезные поля строки отчёта

| Поле                | Значение |
|---------------------|----------|
| `supplier_oper_name`| Тип операции (искать «Компенсация ущерба» и т.п.) |
| `bonus_type_name`   | Обоснование для оплаты/удержания |
| `ppvz_for_pay`      | Сумма к перечислению продавцу (компенсация — со знаком «+») |
| `doc_type_name`     | Тип документа (Продажа / Возврат) |
| `nm_id`, `sa_name`, `barcode`, `ts_name` | Идентификация товара |
| `quantity`          | Количество |
| `rrd_id`            | ID строки — используется как курсор `rrdid` для листания |
| `rr_dt`, `order_dt`, `sale_dt` | Даты |

> Точные названия типов операций/обоснований WB может менять. Правильнее
> фильтровать по подстроке («компенсац»/«ущерб»), а не по точному совпадению, и
> при первой выгрузке глазами свериться с уникальными значениями
> `supplier_oper_name` за период инцидента.

## 4. Что осталось (обновление документации)

1. **Втянуть официальный снимок метода.** Страница финансовых отчётов
   (раздел «Документы и бухгалтерия» → детализация к отчёту о реализации)
   добавлена в [`pages.json`](./pages.json). Из окружения без антибот-блокировки:
   ```bash
   node scripts/refresh-wb-docs.mjs         # обновит все страницы из pages.json
   # либо точечно:
   node scripts/fetch-wb-docs.mjs https://dev.wildberries.ru/docs/openapi/financial-reports docs/wb-api/finance-reports.md
   ```
   Слаг `financial-reports` — наиболее вероятный, но **требует проверки** живым
   фетчем (в этой сессии портал был под антиботом). Если он вернёт заглушку —
   открыть раздел «Документы и бухгалтерия» в браузере и взять реальный слаг.
2. После успешного снимка — сверить в нём точный лимит `reportDetailByPeriod`,
   список значений `supplier_oper_name`/`bonus_type_name` и обновить эту заметку.

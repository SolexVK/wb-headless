## Часть 1. Правила работы с WB API (жёсткие)

### 1.1. Как WB считает лимиты

Алгоритм — **token bucket**, отдельно на **аккаунт продавца** и, как правило,
на **категорию API**. У многих методов есть **собственный лимит, строже базового**.

Базовый лимит (период = 1 минута, на аккаунт):

| Тип токена | Лимит | Интервал между запросами | Всплеск (burst) |
|---|---|---|---|
| Персональный | 300/мин | 200 мс | 20 |
| Сервисный | 300/мин | 200 мс | 20 |
| Базовый | 150/мин | 200 мс | 10 |
| Тестовый | 150/мин | 200 мс | 10 |

**Наш токен — персональный** (`npm run token:check` → `тип: personal`), живёт 180 дней,
уходит в заголовок `Authorization`.

### 1.2. Семь правил, которые нельзя нарушать

1. **Размазывать запросы по интервалу**, а не слать залпом. Интервал = период / лимит.
2. **Всплеск (burst)** — сколько можно разом. Остаток сервер отдаёт в заголовке
   `X-Ratelimit-Remaining` (есть во всех ответах, кроме 429). Дошло до 0 —
   следующий запрос без паузы вернёт 429.
3. **429 — не долбить.** Ждать ровно `X-Ratelimit-Retry` секунд (сколько до
   восстановления всплеска — `X-Ratelimit-Reset`, максимум всплеска — `X-Ratelimit-Limit`).
   Попытка раньше = снова 429.
4. **Прочие 4xx не повторять.** Это ошибка запроса, повтор бесполезен и жжёт лимит:
   в категории «Маркетплейс» **один 4xx стоит как 10 запросов**.
5. **5xx / сеть / тайм-аут** — повтор с экспоненциальным бэкоффом.
6. **Перед первым использованием нового метода — прочитать его страницу** и взять
   **его собственный лимит**, затем передать в клиент через `methodLimit`.
7. **`/ping` — максимум 3 запроса за 30 секунд** на каждый домен; автоматизировать нельзя.

Всё это уже реализовано в [`lib/wbClient.js`](../../lib/wbClient.js): ведро на
категорию + ведро на метод, синхронизация с `X-Ratelimit-Remaining`, ожидание по
`X-Ratelimit-Retry` на 429, запрет ретраев на 4xx, бэкофф на 5xx. Работать с WB
**только через него**:

```js
import { WbClient } from './lib/wbClient.js';
const wb = new WbClient({ tokenType: 'personal' });       // токен из env/.env
const { data } = await wb.get('analytics', '/api/analytics/v1/deductions', {
  query: { dateFrom, dateTo, limit: 1000 },
  methodLimit: { limit: 1, periodSec: 60, burst: 1 },      // ← из доки МЕТОДА
});
```

### 1.3. Лимиты методов, нужных для разбора штрафов

Все значения — для **персонального** токена (у базового без секрета в разы жёстче).

| Что даёт | Метод | Категория токена | Лимит |
|---|---|---|---|
| Удержания за занижение габаритов | `GET /api/analytics/v1/measurement-penalties` | Аналитика | **1 запрос / 1 мин** |
| Замеры склада | `GET /api/analytics/v1/warehouse-measurements` | Аналитика | **1 запрос / 1 мин** |
| Подмены и неверные вложения | `GET /api/analytics/v1/deductions` | Аналитика | **1 запрос / 1 мин** |
| Самовыкупы | `GET /api/v1/analytics/antifraud-details` | Аналитика | **1 запрос / 10 мин** |
| Штрафы за отсутствие маркировки | `GET /api/v1/analytics/goods-labeling` | Аналитика | **1 запрос / 1 мин**, окно ≤ 31 день |
| Детализация отчёта о реализации (за период) | `POST /api/finance/v1/sales-reports/detailed` | Финансы | **1 запрос / 1 мин** |
| Список отчётов реализации | `POST /api/finance/v1/sales-reports/list` | Финансы | **1 запрос / 1 мин** |
| Баланс | `GET /api/v1/account/balance` | Финансы | **1 запрос / 1 мин** |
| Операции при приёмке (create / status / download) | `GET /api/v1/acceptance_report[/tasks/{id}/…]` | Аналитика | 1/мин · 1/5 сек · 1/мин, окно ≤ 31 день |
| Платное хранение | `GET /api/v1/paid_storage[/tasks/{id}/…]` | Аналитика | 1/мин (всплеск 5), окно ≤ 8 дней |
| Сборочные задания FBS за период | `GET /api/v3/orders` | Маркетплейс | 300/мин, всплеск 20; окно ≤ 30 дней, **глубина ≤ 3 мес** |
| Склады продавца (наши ФФ) | `GET /api/v3/warehouses` | Маркетплейс | 300/мин |
| Список / детали / товары поставки FBW | `POST /api/v1/supplies`, `GET /api/v1/supplies/{ID}`, `…/goods` | Поставки | 30/мин, интервал 2 с, всплеск 10 |
| Продажи и возвраты | `GET /api/v1/supplier/sales` | Статистика | 1 запрос / 1 мин |

**Границы данных (не лимиты, но так же жёстко ограничивают разбор):**
детализация реализации — **с 29.01.2024**; список отчётов реализации — с 01.01.2025;
самовыкупы — с августа 2023; маркировка — с марта 2024; сборочные задания FBS —
**только за последние 3 месяца** (глубже — метод архивных заказов). Для штрафов
старше 3 месяцев атрибуция FBS по `/api/v3/orders` уже невозможна, останется
детализация реализации.

**Практический вывод по времени.** Ключевые источники — «1 запрос в минуту».
Полная выгрузка детализации реализации за квартал листается курсором `rrdId`
страницами по 100 000 строк — это **минута на страницу**. Планировать выгрузку
заранее, кэшировать результат на диск и **не перезапрашивать** одно и то же.

### 1.4. Токен

Персональный, задан переменной окружения `Wildberries_API` в настройках среды.
Достаётся только резолвером [`lib/wbToken.js`](../../lib/wbToken.js)
(`WB_API_TOKEN` → `Wildberries_API` → `.env`). Значение **никогда** не печатать
и не логировать. Проверка: `npm run token:check [-- --ping]`.

## Часть 2. Как привязать штраф к фулфилменту

### 2.1. Где вообще живут штрафы

Штрафы приходят из двух разных мест, и набор идентификаторов у них **разный**:

- **Отчёты об удержаниях** (категория Аналитика) — по типам нарушений: габариты,
  подмены/неверные вложения, самовыкупы, маркировка. Это то, что видно в ЛК в
  разделе «Удержания» и обычно выгружается в Excel.
- **Детализация к отчёту о реализации** (категория Финансы,
  `POST /api/finance/v1/sales-reports/detailed`) — там штраф идёт строкой с полями
  `penalty`, `bonusTypeName` («Штраф МП. …»), `deduction`, а рядом лежат **все
  идентификаторы сразу**: `nmId`, `sku` (баркод), **`shkId`**, **`giId` (номер
  поставки)**, `srid`, `orderId`, **`officeName` (склад WB)**, `rrDate`.

**Детализация реализации — это мост.** Она единственная связывает штраф
одновременно с товаром, экземпляром, поставкой и складом.

### 2.2. Что реально отдаёт WB по каждому типу штрафа

Схемы ответов в доке свёрнуты («Показать все» → `{}`), поэтому поля сняты
**живым запросом** — `node scripts/wb-penalties-probe.mjs` (по одному запросу на
метод, лимиты соблюдены). Факт на 2026-08-19:

| Тип штрафа | Есть в строке | Чего НЕТ |
|---|---|---|
| **Занижение габаритов** (`measurement-penalties`) | `nmId`, `subjectName`, `dimId`, замеры факт/заявка, `photoUrls`, `dtBonus`, `penaltyAmount`, `reversalAmount`, `isValid` | ❗ ни поставки, ни склада, ни `shkId` |
| **Замеры склада** (`warehouse-measurements`) | `nmId`, `dimId`, замеры, `photoUrls`, `dt` | ❗ ни поставки, ни склада |
| **Подмены / неверные вложения** (`deductions`) | `dtBonus`, `nmId`, **`oldShkId` / `newShkId`**, `oldSku` / `newSku` (баркоды), размеры/цвета, `oldVendorCode` / `newVendorCode`, `bonusSumm`, `bonusType` (напр. «Неверное вложение FBW»), `photoUrls` | ❗ номера поставки и склада нет напрямую — берутся через `shkId` |
| **Самовыкупы** (`antifraud-details`) | (за проверенный период пусто — структуру снять не удалось) | — |
| **Маркировка** (`goods-labeling`) | (за проверенный период пусто) | — |

### 2.3. Цепочки привязки

**A. FBW — штраф по конкретному экземпляру (подмена, неверное вложение):**

```
shkId (oldShkId/newShkId из отчёта об удержаниях или из Excel)
  → строка детализации реализации по shkId
      POST /api/finance/v1/sales-reports/detailed   (1 запрос/мин, курсор rrdId)
  → giId          = номер поставки FBW
  → officeName    = склад WB, где произошла операция
  → GET /api/v1/supplies/{giId}        (supplies-api, 30/мин)
      → warehouseID / warehouseName    = склад приёмки WB
      → factDate, supplyDate, quantity
  → ФФ отгрузки = наша привязка «поставка → фулфилмент» (см. 2.4)
```

**B. FBS — штраф по заказу (недовоз, отмена, просрочка сборки):**

```
srid / orderId / rid (из строки штрафа или детализации реализации)
  → GET /api/v3/orders   (окно ≤30 дней, пагинация next)
  → warehouseId          = НАШ склад-фулфилмент (точная атрибуция)
  → GET /api/v3/warehouses → имя ФФ («Мск желтая зона», «Казань», …)
```

Это **единственная точная** атрибуция к ФФ, которую даёт WB: в статистическом
`/api/v1/supplier/orders` для FBS поле `warehouseName` — это приёмка/СЦ WB
(«Подольск МП», «СЦ Чебоксары»), а не наш склад. Проверено, см.
[`fbs.md`](./fbs.md), раздел 3b.

**C. Штраф без экземпляра и без заказа (габариты, замеры):**
привязка только косвенная — по `nmId` + `dtBonus`:

```
nmId + дата удержания
  → какие поставки этого артикула приняты до этой даты
      (giId из детализации реализации / приёмки: GET /api/v1/acceptance_report)
  → если поставка одна — ФФ определён однозначно;
    если несколько — распределяем по долям (кол-во в поставках) и помечаем строку
    как «атрибуция вероятностная».
```

Занижение габаритов физически относится к **упаковке**, то есть к тому ФФ, который
её собирал. Если у артикула за окно была одна поставка — вопрос закрыт; если
несколько от разных ФФ — WB данных для однозначного ответа не даёт, и это
надо честно показывать в отчёте отдельной колонкой «уверенность».

### 2.4. Пробел, который API не закрывает

**WB не знает про наши фулфилменты в FBW.** Для поставок FBW в API есть только
склад приёмки WB (`warehouseID`/`warehouseName`: Коледино, Электросталь, …) и
служебные поля (`phone`, `supplierAssignName`). Кто физически собрал и отгрузил
поставку — информация наша, не WB.

Значит для FBW нужен **реестр привязки «номер поставки → фулфилмент»**. Варианты:

1. Явный справочник `config/fulfilments.json` (поставка → ФФ), который ведём мы;
2. Вывод по `phone` в деталях поставки, если каждый ФФ бронирует поставки со
   своего телефона (проверяется на реальных данных);
3. Вывод по складу отгрузки/транзиту, если ФФ закреплены за направлениями.

Для FBS привязка полная и автоматическая: наши склады — это и есть ФФ
(`GET /api/v3/warehouses`, снимок в [`config/warehouses.json`](../../config/warehouses.json)).

### 2.5. Порядок разбора Excel-выгрузки

1. Прочитать книгу, определить тип каждой строки по колонке «обоснование/тип
   удержания» (штраф FBW / штраф FBS / габариты / подмена / самовыкуп / маркировка).
2. Собрать по каждой строке доступные ключи: `nmId`, баркод/`sku`, `shkId`,
   номер поставки, `srid`/номер заказа, дата, сумма.
3. Один раз выгрузить и **закэшировать** справочники (лимит 1/мин — повторно не дёргать):
   детализацию реализации за период выгрузки, список наших складов, детали
   встретившихся поставок, заказы FBS за период.
4. Прогнать цепочки A / B / C и проставить каждой строке: **ФФ**, **склад WB**,
   **номер поставки**, **способ определения** и **уверенность** (точно / вероятностно / не определено).
5. Свод: сумма штрафов по ФФ, по типам, доля «не определено».

Чего заранее знать нельзя — какие колонки реально есть в конкретном файле.
Разбор начинается с чтения шапки книги.

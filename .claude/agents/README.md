# Команда агентов

Каждый файл в этой папке — один агент: роль с собственной зоной ответственности,
своим набором инструментов и своим изолированным контекстом. Агенты вызываются
по имени («спроси у `inventory-planner`…») или подхватываются автоматически,
когда запрос совпадает с их `description`.

## Состав

| Агент | За что отвечает | Модель | Пишет в |
| --- | --- | --- | --- |
| `sales-analyst` | Выручка, маржа, ABC, динамика по SKU и каналам | sonnet | `reports/sales/` |
| `inventory-planner` | Точка перезаказа, заявка на закупку, неликвид | sonnet | `reports/inventory/` |
| `pricing-analyst` | Цена безубыточности, позиция против конкурентов, акции | opus | — |
| `ads-analyst` | Окупаемость кампаний, перераспределение бюджета | sonnet | — |
| `review-triage` | Категории жалоб, системные дефекты, ответы | sonnet | — |
| `listing-writer` | Карточки товаров: заголовок, буллиты, описание, запросы | sonnet | `content/` |
| `content-planner` | Контент-план и тексты под товарный календарь | sonnet | `content/` |
| `doc-drafter` | КП, договоры, презентации, протоколы, таблицы | sonnet | `documents/` |
| `coder` | Модули `lib/`, скрипты, эндпоинты, коннекторы к API | opus | код |
| `code-reviewer` | Ревью изменений: ошибки, безопасность, совместимость | opus | — |
| `qa-auditor` | Сходимость цифр с источником, база процентов, дубли метрик | opus | — |

| `agent-builder` | Создание и починка самих агентов | opus | `.claude/agents/` |

`_TEMPLATE.md` — не агент, а заготовка. Копируйте её при создании новой роли.

## Как это работает вместе

Оркестрацию делает основная сессия: она читает `description` каждого агента и
решает, кому передать задачу. Агент получает **чистый контекст** — он не видит
вашу переписку, поэтому всё нужное должно быть либо в задаче, либо в `CLAUDE.md`,
либо в файлах, которые он прочитает сам.

Общий контекст бизнеса — в корневом `CLAUDE.md`. Его читают все агенты.
Регулярный цикл собран в навык `/weekly-review`.

Связь с уже написанным кодом — в **`docs/tools-contract.md`**. Там точные интерфейсы
`report-stock.js`, `lib/mpstats.js`, `report-niche.js`, справочника `config/skus.json`,
границы владения файлами и карта «агент ↔ инструмент».

## Статус команды

Эти 11 агентов собраны **до** интервью по процессам и являются черновиком.
После разбора интервью выяснилось, что часть ролей не совпадает с реальностью
компании, а самые тяжёлые процессы не покрыты. Что и почему требует переработки —
в разделе 6 контракта инструментов и в `docs/handoff/agent-team.md`.

## Добавить нового агента

Позовите `agent-builder` и опишите задачу. Он обязан пройти по порядку:

1. прочитать `docs/tools-contract.md` — возможно, задача уже решена кодом;
2. проверить пересечения с существующими агентами;
3. и только потом создавать файл.

Вручную: скопируйте `_TEMPLATE.md`, заполните все разделы, включая обязательный
«Инструменты, которые я использую» с точными командами вызова, затем проверьте
тремя запросами, на которых агент должен вызваться, и одним, на котором не должен.

## Правила, которые стоит держать в голове

1. **Один агент — одна зона ответственности.** Пересечение ролей путает
   оркестратор: он не понимает, кого звать, и зовёт не того.
2. **`description` важнее системного промпта.** По нему принимается решение о
   вызове. Общая формулировка = агент простаивает.
3. **Минимальные права.** Читающему агенту не нужен `Write`, аналитику не нужен
   доступ наружу. Это и безопасность, и фокус.
4. **Модель по цене ошибки.** `sonnet` — рабочая норма; `opus` там, где ошибка
   стоит денег (цены, ревью, закупка); `haiku` — механические задачи.
5. **Формат результата задаётся жёстко.** Иначе отчёты нельзя сравнивать между
   периодами.
6. **Границы пишутся явно.** Без раздела «Границы» агент додумывает задачу.

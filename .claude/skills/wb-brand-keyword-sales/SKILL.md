# Анализ своих товаров по ключевым запросам

Отчёт: **сколько штук и на какую сумму мы выкупили** товаров наших брендов, в разрезе
**ключевых фраз** и **периодов**. Данные о продажах — ФАКТИЧЕСКИЕ, из личного кабинета WB.

Логика — `lib/wbBrandKeywordSales.js`; продажи — `lib/wbSales.js`; PDF — `lib/htmlToPdf.js`;
CLI — `scripts/wb-brand-keyword-sales.mjs` (`npm run sales:by-keyword`).

Токены (env): **`MPSTATS_TOKEN`** (выдача по фразе) + **`Wildberries_API`** (продажи из кабинета).

## Алгоритм (как считается)

1. **Наши nmId по фразе.** Для каждой фразы берём поисковую выдачу WB из MPStats
   (`fetchSearchResults`) и оставляем карточки наших брендов → список наших nmId в этой
   нише (объединяя окна периодов). Бренды матчатся регистронезависимо по подстроке.
2. **Фактические продажи.** По этим nmId тянем `POST /api/v1/supplier/sales` (WB Statistics).
   Один pull с самой ранней даты периода — из него считаем все периоды (перекрываются).
3. **Агрегация по фразе × периоду.** «Выкуп» = строка `saleID` вида **S** (оплачен, не
   возвращён); возвраты (`R`) считаем ОТДЕЛЬНО (не вычитаем). Сумма — `finishedPrice`
   (розничная, что заплатил покупатель) или `forPay` (к перечислению, флаг `--sum forPay`).
4. **Отчёт** — итог по фразам, возвраты, детализация по каждому артикулу → PDF/HTML/JSON.

## ⚠️ Лимит WB (критично)

`/api/v1/supplier/sales` для токена personal/сервисного — **1 запрос в минуту, без запаса**
(`docs/wb-api/reports-statistics.md`). Один ответ — до ~80 000 строк; больше — пагинация по
`lastChangeDate`. Поэтому `pullSales` держит паузу **66 с** между страницами и ловит 429.
Отчёт за полгода = обычно 2–3 запроса ⇒ **прогон занимает 2–4 минуты, это нормально.**

## ⚠️ Дедуп только по `saleID`, не по `srid`

`srid` — идентификатор ЗАКАЗА (одна покупка = несколько позиций с одним srid; возврат имеет
тот же srid, что продажа). Дедуп по srid ТЕРЯЕТ реальные строки (особенно возвраты). Уникален
`saleID` — по нему и дедупим пограничные строки пагинации.

## Обязательный предполётный диалог

Собери у пользователя и подтверди перед запуском:
1. **Наши бренды** (как в WB, напр. `AIDEMIKO, Aizek`).
2. **Ключевые фразы** (одна или несколько).
3. **Периоды** — по умолчанию «с начала года» + «последние 30 дней»; можно менять
   (`--from` — старт «с начала года», `--days N` — длина скользящего периода).
4. **Что считать «продано»** — выкупы (по умолчанию; заказы этот метод не даёт).
5. **Сумма** — розничная `finishedPrice` (по умолч.) или `forPay` (`--sum forPay`).

## Запуск

```bash
npm run sales:by-keyword -- --brands "AIDEMIKO,Aizek" \
  --phrase "Рубашка муслиновая женская" --phrase "рубашка муслиновая мужская" --pdf
# опции: --from 2026-01-01  --days 30  --sum finishedPrice|forPay
#        --pdf [путь] --html [путь] --out [путь.json]   (без пути → авто-имя с датой)
```

Вывод по умолчанию — PDF в `reports-output/анализ-по-запросам_<бренды>_<дата>.pdf`.

## Важные оговорки (обязательно проговорить пользователю)

- **Атрибуции к запросу нет.** WB не привязывает органические продажи к поисковой фразе.
  «По запросу» = продажи наших товаров, которые попадают в выдачу по этой фразе, а НЕ
  «сколько принёс запрос».
- **Потолок выдачи MPStats ~100** товаров на фразу — товары бренда за пределами топ‑100
  выдачи в отчёт не попадут (для доминирующих в нише брендов охват близок к полному).
- **Выкупы — валовые** (возвраты показаны отдельно, не вычтены). Чистые = выкупы − возвраты.

## Программно (в каскаде)

```js
import { analyzeBrandKeywordSales, formatHtml } from './lib/wbBrandKeywordSales.js';
import { htmlToPdf } from './lib/htmlToPdf.js';
const res = await analyzeBrandKeywordSales({
  brands: ['AIDEMIKO','Aizek'], phrases: ['рубашка муслиновая женская'],
  periods: [{key:'ytd',label:'с 01.01',from:'2026-01-01',to:'2026-07-06'},
            {key:'d30',label:'30 дн',from:'2026-06-06',to:'2026-07-06'}],
});
await htmlToPdf(formatHtml(res), 'report.pdf');
```

# Сборка таблицы «для кизов»

Задача повторяющаяся: раз в период приходят три выгрузки, из них надо получить одну
плоскую таблицу — по строке на каждую позицию остатка, с GTIN и баркодом, чтобы
заказать коды маркировки.

Файлы заполняются людьми вручную, поэтому каждый раз немного разные: колонки
переставлены, цвет назван иначе, размер записан кириллицей. Скилл несёт готовый код,
который это переваривает, и — главное — знает, **о чём спросить пользователя**, вместо
того чтобы молча угадать.

## Что на входе и что на выходе

| | Таблица | Что берём |
|---|---|---|
| Т1 | **Перечень номенклатур** | Артикул продавца, Артикул WB, Размер, Баркод |
| Т2 | **GTIN коды** | GTIN |
| Т3 | **Инвентаризация** | Количество |
| Т4 | **для кизов** | только образец шапки, данных нет |

Результат — `.xlsx`, лист `Worksheet`:
`Артикул продавца | Артикул | GTIN | Размер | Баркод | Количество`
плюс лист `Проверка` с цветом, блоком и статусом каждой строки.

**Ведущая таблица — инвентаризация.** Одна строка результата = одна непустая ячейка
остатка. Т1 и Т2 только обогащают эти строки. Из этого следует контрольная проверка:
сумма «Количество» в итоге обязана совпасть с суммой инвентаризации.

## Ключ связи — не артикул, а тройка

Главная ловушка: строка артикула в трёх таблицах пишется **по-разному**, и склеивать
по ней бесполезно.

```
Т2 «005_рм» + цвет «белый»   →   Т1 «005_рмм-св_белый»
Т2 «003_рмп_1см_белый»       →   Т1 «003_РМП_белая»
Т2 «030 ржп» + цвет «белый»  →   Т1 «030_РЖП_БЕЛЫЙ»
Т3 лист «034» + «Белый»      →   Т1 «034_рмж_белый_пк»
```

Совпадает только **3-значный номер модели**. Поэтому ключ:

> **номер модели (3 цифры) + цвет + размер**

Цвета и размеры сравниваются нечётко (основы слов + префиксы), иначе `Белая`, `белый`
и `БЕЛЫЙ` окажутся тремя разными цветами. Подробности реализации — в
`scripts/kiz_lib.py`, разбор всех известных ловушек — в
[`references/formats.md`](references/formats.md).

## Порядок работы

### 1. Разведка
```bash
python3 .claude/skills/wb-kizy/scripts/inspect_inputs.py <все присланные .xlsx>
```
Скрипт сам определяет, какой файл чем является, и печатает: сколько строк, какие
размеры и цвета встречаются, есть ли дубли GTIN и неразобранные строки.

Это не формальность. Если структура файла уехала (новый формат описания, шапка в другом
месте), ты увидишь это здесь — до того, как в итоге тихо появятся пустые колонки.
Сравни номера моделей в трёх файлах: разница = позиции, для которых чего-то не хватает.

### 2. Сборка
```bash
python3 .claude/skills/wb-kizy/scripts/build_kizy.py \
  --nomenclature Т1.xlsx --gtin Т2.xlsx --inventory Т3.xlsx \
  --out для_кизов_ИТОГ.xlsx --report отчёт.json
```

Полезные ключи:
- `--exclude-kiz` — выбросить строки из блока «С кизами» (то, что уже промаркировано)
- `--gtin-width 13` — писать GTIN как есть, без дополнения до 14 знаков
- `--single-sheet` — только лист загрузки, без листа «Проверка»
- `--overrides map.json` — ручные правки сопоставления, см. ниже

### 3. Разбор отчёта
Скрипт печатает раздел **«ТРЕБУЕТ ВНИМАНИЯ»**. Разбери его целиком, прежде чем
отдавать файл, и передай пользователю своими словами:

- **нет в номенклатуре** — цвет/размер есть в остатках, но его нет в Т1. Значит, либо
  номенклатура неполная, либо цвет назван так, что не опознался. Проверь глазами по
  списку цветов из разведки.
- **нет GTIN** — позиция реальна, но кода на неё в выгрузке нет. Не выдумывай: оставь
  пусто и назови позицию пользователю, он пришлёт код.
- **подтвердить цвет** — сопоставление сработало нестрого (например, «Радуга сердечки»
  подошло к «018/мс/радуга» при наличии соседей «красный сердечко» и «коричневый
  сердечка»). Такие строки нужно показать пользователю и попросить подтвердить.

### 4. Отдать результат
Отправь файл и короткую сводку: сколько строк и штук, сколько заполнено полностью,
какие позиции без GTIN, какие сопоставления просишь подтвердить. Сумма количества
должна сойтись с инвентаризацией — если нет, скрипт сам напишет об этом.

## Пересборка самих исходников

Отдельная задача — не собрать итог, а привести в порядок сами выгрузки: свести артикулы
к написанию из номенклатуры, цвета к единому справочнику, размеры к одному ряду.

```bash
python3 .claude/skills/wb-kizy/scripts/rebuild_sources.py \
  --nomenclature Т1.xlsx --gtin Т2.xlsx --inventory Т3.xlsx --out-dir .
```

Получаются два файла: «GTIN коды» (лист на каждый номер модели, колонки
*Артикул продавца · Цвет · Размер · GTIN*) и «Инвентаризация» (лист на каждый номер,
где считали, колонки *Артикул продавца · Цвет · Статус КИЗ · размеры*). После этого оба
файла сходятся с номенклатурой по артикулу продавца, и нечёткое сопоставление в следующий
раз уже не нужно.

Ключи: `--merge-kiz` убирает колонку «Статус КИЗ» и складывает блоки «с кизами / без кизов»,
`--blank-zeros` оставляет нулевые остатки пустыми, как в оригинале.

Скрипт сам сверяет сумму количеств с исходной инвентаризацией и сообщает, если она разошлась.
Справочник цветов строится в `scripts/colors.py`: варианты написания объединяются в группы,
из каждой выбирается одна форма (мужской род и существительное выигрывают у женского —
«Белый», а не «Белая»).

## Вопросы, которые стоит задать

Не угадывай, если пользователь не сказал явно — это ровно те развилки, где ошибка
дорого стоит:

1. **Блок «С кизами».** На некоторых листах инвентаризации остаток разбит на «С кизами»
   и «Без кизов». Включать уже промаркированное в таблицу для заказа кодов? По смыслу
   обычно нет, но решает пользователь. Если включаем — помечаем колонкой «Блок».
2. **Формат GTIN.** 14 знаков текстом с ведущим нулём (как требует Честный Знак) или
   13 знаков числом. По умолчанию 14 текстом.
3. **Нулевые остатки.** В инвентаризации бывают строки цветов, где все ячейки пустые.
   По умолчанию они не попадают в итог — там нечего маркировать.

## Ручные правки сопоставления

Когда цвет принципиально не опознаётся автоматически (новый оттенок, опечатка,
переименование), не правь код — заведи файл правок:

```json
{
  "color_map": { "014|пудра": "розовый" },
  "force_art": { "016|Радуга": "016 МС сердечко радуга" }
}
```

`color_map` подменяет цвет из инвентаризации перед сопоставлением (ключ —
`номер|цвет как в инвентаризации`, в нижнем регистре). `force_art` жёстко привязывает
цвет к конкретному артикулу из Т1. Передай файл через `--overrides` и сохрани рядом с
исходниками — в следующий раз правки переиспользуются.

## Если формат уехал сильнее

Скрипты рассчитаны на человеческий хаос внутри известной структуры. Если пришёл файл
принципиально другой формы (другая раскладка инвентаризации, новый вид описания в GTIN),
сначала прочитай [`references/formats.md`](references/formats.md) — там описано, какие
именно вариации уже учтены и по какому принципу код их распознаёт. Дорабатывай
`kiz_lib.py` в том же духе: определять структуру по содержимому ячеек, а не по их
позиции. После правки прогони сборку и убедись, что сумма количества по-прежнему
сходится с инвентаризацией.

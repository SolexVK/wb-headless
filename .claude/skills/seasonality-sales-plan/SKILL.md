# Ранг сезонности — план продаж

Скилл строит **прогноз плана продаж на заданный будущий период** для товарной
линейки на Wildberries: когда входить в рынок, разгон, пик, распродажа; сколько
заказывать по дням; какие цены держать; где рынок в дефиците (спрос > предложения).
Форма сезона берётся от **отфильтрованных конкурентов-аналогов** (данные MPStats),
уровень — от собственных продаж (если есть) блендом 90/10.

Движок уже реализован в этом репозитории (`lib/*.js`, `season-plan.js`). Скилл —
это **playbook**: как правильно запустить и что отдать заказчику. Про перенос в
другую ветку/инструмент — см. `references/reuse.md`.

## Когда использовать

Пользователь просит: план/прогноз продаж на сезон, анализ сезонности товара,
«что и по чём заказывать по месяцам», «когда входить в нишу», разбор конкурентов
по сезону. Не использовать для разовых справок без построения плана.

## ШАГ 1 (обязательно). Начать с уточняющих вопросов

**НЕ запускать сбор данных сразу и НЕ переиспользовать прошлые данные** (только
если пользователь явно не попросил). Сначала задать вопросы понятным языком и
дождаться ответов. Спросить:

1. **Товар / предмет.** Какой товар анализируем? Если знают путь предмета WB —
   взять его; если нет — найти по названию в дереве категорий (см. Шаг 2).
2. **Фильтр конкурентов-аналогов:**
   - `--words` — слова в названии (любое из; учитываются словоформы);
   - `--all-words` — доп. слова-признаки (мягкий сигнал релевантности, не отсечение);
   - `--exclude` — что исключить (полоска, лето, джинс…);
   - `--brands` / `--exclude-brands` — по брендам;
   - `--price-min` / `--price-max` — ценовой коридор, ₽ (мы в среднем/высоком сегменте);
   - `--min-sales` — минимум продаж **в месяц**;
   - `--min-revenue` — минимум выручки **в месяц**, ₽ (альтернатива продажам);
   - `--limit` — сколько аналогов в группу (обычно 60).
3. **Прогнозный период** — `--from` … `--to` (например 2026-08-01 … 2027-03-31).
4. **Уровень базы:** от нашей линейки (`--group` + бленд 90/10), от цели
   (`--target-units`) или «на 1 карточку среднего конкурента» (если своих нет).
5. **Опции:** OOS-поправка и недельный профиль (по умолчанию оба включены).

Правила методологии (детали — `references/methodology.md`): окно истории —
**2 года** от текущей даты, недавний год весит больше; **база = 90% конкуренты +
10% свои**; учитываем **остатки** и подсвечиваем благоприятные периоды; корректируем
прогноз **дрейфом текущего года** по конкурентам за 60 дней.

## ШАГ 2. Найти путь предмета (если не задан)

Пути предметов лежат в дереве категорий MPStats:

```bash
node -e 'import("./lib/mpstats.js").then(async(m)=>{const r=await fetch((process.env.MPSTATS_BASE_URL||"https://mpstats.io/api")+"/wb/get/categories",{headers:{"X-Mpstats-TOKEN":process.env.MPSTATS_TOKEN}}).then(r=>r.json());for(const c of r.filter(c=>/рубаш/i.test(c.path)&&!/Акции/.test(c.path)).slice(0,20))console.log(c.path)})'
```
Заменить `рубаш` на корень нужного слова. Взять канонический путь (не «Акции/…»),
напр. `Женщинам/Блузки и рубашки/Рубашка`.

---

## ШАГ 3. Запуск (после ответов пользователя)

Требуется `MPSTATS_TOKEN` в окружении. Команда-шаблон (прогнозный режим):

```bash
node season-plan.js \
  --path "Женщинам/Блузки и рубашки/Рубашка" \
  --words "клетка" \
  --all-words "демисезон,длинный рукав,оверсайз" \
  --exclude "полоска,однотон,джинс,лето,приталенная" \
  --price-min 1800 --price-max 3900 \
  --min-sales 80 --min-revenue 100000 --limit 60 \
  --from 2026-08-01 --to 2027-03-31 \
  --oos --weekly
```

Флаги подробно — `references/flags.md`. Если своя линейка есть — добавить
`--group <ЛИНЕЙКА>` (из `config/groups.json`) → база станет блендом 90/10.
Без `--from/--to` строится исторический план за 2 года (не прогноз).

**Экономия лимита MPStats (важно):** дневные ряды берутся из графиков выдачи по
предмету (`sales_graph`/`stocks_graph`/`price_graph`) — **вся группа одним
запросом**, не по одному запросу на SKU. Прогноз обычно = 4 запроса. Способ и
стоимость видны в сводке (`method`, `requests`).

## ШАГ 4. Что делает движок (проверить, что вывод осмыслен)

Конвейер: собрать группу-аналогов с фильтром → дневной ряд группы из графиков →
**свёрнутый recency-взвешенный месячный профиль** (продажи/цена/остатки) →
устойчивый **ранг** (p90/p50) → **фазы** (вход/разгон/старт/пик/начало-конец
распродажи) кольцевой логикой → **дрейф года** (конкуренты 60 дн. vs год назад,
клэмп 0.5–2.0) → **благоприятные месяцы** (спрос выше среднего при остатках ниже
среднего) → проекция на запрошенный период → отчёты.

Санити-чек результата:
- пик сезона совпадает с типом товара (зимний → зима, летний → лето);
- ранг: ярко выраженный (p90/p50 ≥ 2), умеренный (≥1.3), слабый;
- цены — среднего/высокого сегмента (якорь «выше медианы»);
- нет предупреждений «мало данных / срез окна» без причины.

## ШАГ 5. Отдать результат — 4 файла

Каждый прогон пишет в `reports-output/`:
- **`.xlsx`** — план продаж и цен по дням запрошенного периода; строки раскрашены
  по этапам, благоприятные дни подсвечены;
- **`.html`** — визуальный отчёт: диаграммы «прогноз» и «история за 2 года», на
  каждой три линии (спрос — синий, цена — красный, остатки — фиолетовый) + подсветка
  этапов и благоприятных периодов;
- **`.csv`**, **`.json`** — те же данные для машинной обработки.

Отправить пользователю `.xlsx` и `.html` (через SendUserFile, `display: render`
для html). Кратко назвать: ранг, пик, окна фаз, диапазон цен, итог по штукам,
благоприятные периоды. Про интерпретацию колонок/цветов — `references/outputs.md`.

## Грабли (проверять при странном результате)

- **Слишком узкий фильтр** → мало аналогов, в сводке предупреждение об обрезке
  пагинации. Ослабить критерии или поднять `--max-pages`.
- **Пик-артефакт в одном месяце** (launch-спайки новинок) — гасится сглаживанием
  профиля; если всё равно резко — проверить месячный профиль в `.json`.
- **Странная сезонность у новинок** — OOS-поправка восстанавливает спрос только
  ВНУТРИ активного окна карточки (не до запуска); это уже учтено.
- **Дневной лимит MPStats (429)** — конвейер останавливается и пишет об этом;
  сбрасывается на след. сутки.

## Отбор «своих» товаров через WB API (при наличии своей линейки)

Для стороны «10% свои» точнее тянуть наши карточки/продажи через **WB Seller API**
(`lib/wbClient.js`, токен `Wildberries_API`). Лимиты WB строгие (персональный —
300 запросов/мин, burst 20, ошибка 4XX = 10 запросов) — соблюдаются встроенным
TokenBucket. Детали — `references/setup-and-limits.md`.
